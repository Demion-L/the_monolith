# Lesson: Verify a CLI's actual argument parsing before trusting a positional path argument in a smoke test — especially from inside a live repo

## Mistake

While smoke-testing `monolith mission` as part of finalizing COORDINATORIUM-001, the CLI was invoked as `monolith init --yes <scratch-dir>` from the live MONOLITH repository's own working directory, on the (unverified) assumption that the trailing path argument set the target directory. It did not: `src/cli/index.ts`'s `init` handler always calls `runInit({ targetDir: process.cwd(), ... })`, silently ignoring any positional argument. This scaffolded template defaults over 20 tracked governance/memory files in the live repository (AGENTS.md, active.md, story-index.md, execution-history.md, decisions.md, skill files, etc.) before it was caught via `git status` and reverted with `git checkout --`. No damage became permanent only because the working tree had been confirmed clean immediately beforehand and nothing was committed in between.

## Root Cause

A positional argument *looked* like the obvious way to target a directory (and is a common CLI convention), so it was used without first reading `src/cli/index.ts` to confirm the CLI actually supports it. The assumption was never checked against the code before being acted on with `--yes` (which also suppresses the overwrite confirmation prompt) from a directory that mattered.

## Prevention

**Before invoking any CLI command with a flag that suppresses confirmation (`--yes`, `--force`, `-y`) against an assumed target path, read that command's actual argument-parsing code first** — do not infer behavior from flag names or convention. If the command's target scope is ambiguous or unverified, `cd` into an isolated scratch directory first and invoke the command with no path arguments, so even a wrong assumption about argument parsing can only affect the scratch directory.

**Signal to watch for:** about to run a scaffolding/initialization command with an auto-confirm flag, anywhere other than a directory created solely for that test.

## Criteria check

- Recurs in other stories: yes — any future smoke test of a CLI command (this project's or another's) carries the same risk whenever target-directory handling isn't verified first
- Non-obvious cause: yes — a positional path argument is a near-universal CLI convention, so assuming it works is a reasonable-looking shortcut that happens to be wrong here
- Concrete prevention: yes — read the arg-parsing code first, or always `cd` into the scratch directory before invoking rather than relying on a positional argument
