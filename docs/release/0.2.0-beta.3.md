# MONOLITH `0.2.0-beta.3` — Release Notes

**Status:** prepared; **not released** (no version bump, tag, push or publish has been done). Pre-release for the `beta`
dist-tag. MONOLITH is experimental and **not a stable production release**. Changes are relative to `v0.2.0-beta.2`
(`4ebe024`). Requires Node.js >= 20.

```bash
npm install -g @latysh-development/monolith@beta
```

## Added

- **Mission Auto-Enrollment** — Core `enrollMission` (`CREATED | REUSED | SKIPPED | CONFLICT | UNAVAILABLE`), idempotent under
  the existing Durable State lock: N concurrent callers of one execution context produce one Mission.
- **Managed Execution** (opt-in, `execution.mode: "managed"`) with a Claude Code `PreToolUse` adapter:
  `monolith hook pre-tool-use | status | print-config --managed` (fail-closed snippet). See
  `docs/reference/managed-execution.md`.
- **Mission ownership** (`Mission.owner`, optional; Durable State stays schema v3) and **explicit handoff**
  (`monolith mission handoff <id> --reason "..."`); `mission checkpoint|finish` refuse a Mission owned by another worktree.
- **Session recovery** — a restarted session in the same worktree resumes its Mission; a crash never closes anything.
- **Enrollment CLI** — `monolith mission enroll | current | handoff`.
- **Execution discipline diagnostics** — Handover `execution` block and Mission Control (Development History owner,
  Handover execution section).
- **Same-worktree Story continuity** — in a managed project the hook reads the single `**Story:**` line of
  `## Current Story` (the line Finalize uses). A Mission is linked to that Story; switching Story while the previous
  Mission is still `in_progress` is a `CONFLICT` and the managed write is denied. Nothing is finished, re-linked or
  handed off automatically. A finished Mission yields a new Mission for the next Story.

## Fixed

- Rows of a "Phase" table (and of a Completion Summary) were read as planned Stories (Second Brain-style roadmap produced
  phantom Stories in Handover). Phase tables are no longer story tables; an unrecognised Roadmap is diagnosed honestly
  (`NO_PHASES_FOUND`).
- "No missions have ever been recorded" → "Operational state file is absent; historical mission records are unavailable from
  this source." (`STATE_NOT_INITIALIZED`).
- `monolith update` delivers `document-formats.md` (when absent) and the Mission/Reporting Discipline text through the
  managed `AGENT.md` block, without touching user text; an edited block is kept and reported as a conflict.
- **Managed Execution bypass closed (found during release verification):** `monolith evidence run -- <cmd>`, `monolith
  update`, `monolith init` and `monolith state adopt` were classified as "governed" and passed the hook without enrollment.
  "Governed" is now a positive allowlist of subcommands; everything else is treated as implementation.

## Compatibility

- Durable State v3 unchanged; no migration. Legacy Missions without an owner keep working and are never restricted.
- Unmanaged projects and manual `mission start|checkpoint|finish` workflows are unchanged.
- Finalize approval semantics are unchanged; a completed Mission is not a finalized Story.
- An older MONOLITH binary that rewrites `state.json` drops `Mission.owner` (the file stays valid).
- In a managed project a Mission without a Story link (created while no active Story was declared) conflicts once a Story
  is declared: finish it (`monolith mission finish`) and the next write starts a linked Mission.

## Known limitations

- Managed Execution requires opt-in; MONOLITH never edits Claude Code settings.
- The Claude Code adapter covers only the tool calls the host routes through `PreToolUse`
  (`Write|Edit|MultiEdit|NotebookEdit|Bash`). MCP tools and unknown tools are not controlled and not claimed to be.
- Ownership is coordination, not authentication. It is not a security boundary.
- An agent with file access can edit `monolith.config.json` or `.claude/settings.json` and disable the guard.
- Programs started by an allowed command (build, tests, scripts) and any writes outside hook-routed tools are not contained.
- If `monolith.config.json` is corrupt or has an invalid `execution` value, the mode is unknowable: the hook warns loudly
  and does **not** govern the write; `hook status` reports it as not enforced (fail-open with a warning, by design of the
  single configuration source).
- A stale `monolith` binary without `hook pre-tool-use` on PATH blocks every hooked call (fail closed).
- Identity is `(agent, worktree)`: `monolith mission enroll` defaults to agent `cli`, so use `--agent claude-code` to join
  the hook's Mission.
- Checkpoints require real content; MONOLITH does not generate meaningful checkpoints.
- Windows has not been verified. There is no Codex adapter yet.
