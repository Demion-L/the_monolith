# Lesson: Never publish a shared file before its payload is fully written

## Mistake

The Coordinatorium lock's create path was `open(lockPath, 'wx')` (which publishes the canonical file immediately — any other process can now see it exists) followed by a single `writeSync(fd, metadata)` call whose return value was never checked. A write failure (`ENOSPC`/`EIO`) or a short write (`writeSync` is not guaranteed to write a whole buffer in one call) after the `open` left an empty or partial *canonical* lock file behind. Because that file failed to parse, it was correctly treated as "uncertain" by the recovery logic — and per that logic's own (correct) invariant, uncertain is never auto-recoverable, so it became a permanent manual-cleanup wedge.

## Root Cause

`open(path, 'wx')` was (correctly) relied on elsewhere in this module as the atomic exclusivity primitive, and that correctness bled into an unstated assumption that the same call was also safe as a *publication* step — i.e. that "create the file" and "the file is ready to be read by others" were the same moment. They are not: creating a file and finishing writing its contents are two different events, and nothing requires them to be adjacent in time if anything goes wrong in between.

## Prevention

**Any primitive that both creates a shared, multi-byte artifact and relies on other processes observing its existence as a signal must separate "write the payload" from "publish it."** Write the full payload to a private, uniquely-named staging location first (looping on short writes — never assume one write call finishes a buffer), and only then publish via an operation that is *itself* exclusive against a pre-existing destination (a hard link, or `open(..., 'wx')` on the final name) — never a plain `rename`, which silently replaces an existing destination and reintroduces the exact race the exclusivity was meant to prevent.

**Signal to watch for:** any code where `open(path, 'wx')` (or an equivalent create-if-absent call) is immediately followed by writing the file's actual content, with the content write treated as "basically can't fail" or its return value unchecked. If the content write can fail or return a short count, and the path is already visible to other processes at that point, this bug shape is present.

## Criteria check

- Recurs in other stories: yes — any future file-based artifact meant to be observed by other processes/sessions (state snapshots, session markers, cache entries) can reintroduce this exact create-before-fully-written gap
- Non-obvious cause: yes — `open('wx')`'s atomicity is real and necessary, which makes it easy to mistake for sufficient; the gap only appears once you ask "what can another process observe between open and the write actually finishing?"
- Concrete prevention: yes — stage-then-publish via an exclusive publish step, plus a write-loop that checks the real byte count, both independently verifiable in code review
