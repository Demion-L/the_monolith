# ADR-009 — Mission Control UI: Read-Only Local Interface over Core

> **Status: PROPOSED.** Ни принято, ни реализовано. Команда `monolith ui`,
> HTTP API, Application Layer и Vue-приложение, описанные ниже, **не
> существуют**. Часть технических решений уже утверждена владельцем проекта
> (раздел «Approved by project owner»), но сам ADR остаётся `proposed` до
> независимого ревью. Он не меняет приоритеты и не назначает сроков.
>
> Редакция UI-000A (2026-10-22): выровнена с утверждёнными решениями и
> security-аудитом от 2026-10-22.
>
> Редакция UI-000B (2026-10-22): ветка перебазирована на `main` (`1965fe5`);
> зависимости (CONTEXT-001A, SEC-001, SEC-002) проверены; Q10 и Q14
> зафиксированы как утверждённые. Статус ADR не менялся.

## Context

MONOLITH хранит состояние проекта в файлах (`.monolith/state.json`,
markdown-память, ADR). Нужен способ понять «где мы находимся» (миссия,
чекпоинты, roadmap, доступность данных) без чтения многих файлов.

Ограничения: UI не должен стать вторым источником истины; Core (State Keeper,
Scriptorium, ERG) не дублируется; UI не расширяет возможности Core.

## Approved by project owner

Эти пункты — решения владельца, зафиксированные здесь для трассируемости; сам
ADR всё ещё `proposed`.

- **Frontend:** Vue 3, TypeScript, Vite, Composition API. Без библиотеки
  управления состоянием и без библиотеки роутинга в MVP, пока нет реальной
  потребности.
- **Backend:** существующий Node.js runtime; локальный HTTP API; JSON; только
  чтение; bind `127.0.0.1`; один сервер = один проект; foreground.
- **Источники данных:** `state.json`, markdown-документы и существующие
  интерфейсы Core остаются авторитетными. Без миграции в XML или иной формат;
  без новых обязательных персистентных схем в MVP. Frontend не зависит от
  формата хранения благодаря application-level read model.
- **CLI (целевой UX):** `monolith ui` запускает локальный HTTP-сервер,
  отдающий скомпилированное Vue-приложение и read-only API. Vite — инструмент
  разработки и сборки, не production-сервер.
- **Q10 — фикстуры:** разрешена разработка Vue Dashboard на синтетических
  JSON-фикстурах до закрытия SEC-001. Ограничения: никакого доступа к реальным
  проектным файлам через HTTP; никаких вызовов небезопасной валидации; никаких
  write operations; никаких изменений Core ради mock-режима.
- **Q14 — Roadmap:** в MVP строки `roadmap-index.md` отображаются как текст. UI
  не выводит статусы задач из произвольной Markdown-прозы; отдельный
  Markdown-парсер для Roadmap не создаётся.

## Proposed (требует ревью)

1. Слои: Browser UI → Local HTTP API (только `GET`) → Application Layer (read
   model с provenance и диагностиками) → Core → файлы проекта.
2. Каждый показанный факт несёт provenance (относительный путь источника);
   отсутствие данных — `UNKNOWN` + диагностика, не домысел.
3. Эпистемические статусы PROPOSED / DECIDED / IMPLEMENTED / VERIFIED не
   смешиваются и не выводятся друг из друга.
4. Детали контракта API (эндпоинты, оболочка ответа), токен запуска, размещение
   собранных ассетов — см. план, §4 и §9.

## MVP scope (UI-001)

Показываются только данные, подтверждённые авторитетными источниками;
иначе `UNKNOWN`.

1. Project Overview.
2. Current Mission.
3. Checkpoints.
4. Roadmap (строки `roadmap-index.md` как текст, без вывода статусов; Q14).
5. Базовая диагностика доступности данных и ошибок.

**Исключено из MVP:** управление агентами; Hypothesis Explorer; Knowledge
Explorer; ERG Graph View; интеграция с Reasoning Projector; Governance
Workbench; любые операции записи; продвинутая аналитика; фоновые сервисы;
новые персистентные модели данных. UI-002…UI-005 — неплановый backlog без
расширения объёма.

Не выдумываются статусы, блокеры, результаты верификации и evidence. Не
вводятся новые governance-требования. Состояние проекта не изменяется.

## Security

**Инвариант:** MONOLITH UI не должен расширять возможности MONOLITH Core по
доступу к файловой системе, исполнению кода или изменению состояния.

- **SEC-001 — Project Root Trust Boundary (CONFIRMED, OPEN).** Зарегистрирован
  в `tech-debt.md` на `main` (`1965fe5`) со статусом «OPEN, not started»;
  исправление ведётся в отдельном workstream и в `main` не влито. Резолвер
  корня: `resolveProjectRoot(targetDir)` — предложенное имя в `tech-debt.md`,
  `resolveMonolithRoot()` — имя у владельца; ни одно не существует в `src/` на
  `main` (Q13). **Gate:** UI-001 не отдаёт реальные файлы проекта по HTTP,
  пока соответствующие исправления SEC-001 не реализованы, независимо
  проверены, влиты и верифицированы. Требования: корень проекта фиксируется при
  старте; API не принимает произвольных путей (идентификаторы вместо путей);
  доступ к данным через валидированный Core; запрет выхода через symlink;
  allowlist `Host` (DNS rebinding); без разрешающего CORS; строгая CSP;
  безопасный рендер Markdown без raw HTML; никаких мутаций состояния.
  Разработка на синтетических фикстурах gate не нарушает (Q10, утверждено).
- **SEC-002 — исполнение недоверенного кода (CONFIRMED, на независимом
  ревью).** `monolith validate` динамически импортирует `project.definition.mjs`
  (проверено чтением кода). UI не исполняет JavaScript проекта неявно, не
  вызывает небезопасную валидацию; индикаторы состояния строятся на безопасных
  read-only проверках. В `tech-debt.md` SEC-002 пока не зарегистрирован.

Исправления SEC-001 и SEC-002 не входят в этот ADR и не реализованы здесь;
верификация не заявляется.

## Dependencies on other work

- **CONTEXT-001A:** COMPLETED и в `main`. `collect()`/`BriefModel` покрывают
  большую часть MVP (миссии, последний чекпоинт, Current Story, диагностики), но
  не Roadmap; на них же распространяется SEC-001; не публичный API (TD-009:
  `src/brief/index.ts` экспортирует `collect` и `BriefModel`, но `src/index.ts`
  `brief` не реэкспортирует). Зависимость полезная, не обязательная. Новый
  публичный API в рамках UI-000B не вводится; безопасный способ повторного
  использования `BriefModel` определяется до интеграции с реальными данными (Q11).
- **CONTEXT-001B:** `monolith context <topic>`, не начат; от него UI-001 не зависит.
- **SPHINX:** независимый продукт, потребляющий возможности MONOLITH (со слов
  владельца). UI от него не зависит; SPHINX-специфики в MVP нет.

## Rationale

- Read-only + проекции Core сохраняют «один источник истины» и детерминизм
  (прецедент: `monolith validate`, `monolith brief`).
- Локальный bind, отсутствие CORS и демона минимизируют поверхность; содержимое
  документов — недоверенный ввод.
- Запрет вывода связей согласуется с ADR-007 (explicit-only).

## Alternatives Considered

Ранее (исходная редакция, `b03723a` до rebase, `4cd2613` после) рассматривались: stdlib-клиент без сборки; клиентский
фреймворк с бандлингом; полный фреймворк с dev-сервером; статический экспорт.
Выбор стека сделан владельцем (Vue 3 + TS + Vite с компилированной раздачей);
сравнение сохранено в истории git. Статический экспорт остаётся возможным
дополнением вне MVP.

## Consequences

Если будет принят:
- появятся Application Layer, HTTP-слой и build-цепочка Vue/Vite (devDependencies;
  изменение `package.json` и CLI — только в UI-001 после явного одобрения);
- UI-001 заблокирован SEC-001-gate для реальных данных;
- Blockers, IMPLEMENTED и VERIFIED не имеют источника данных — в MVP не
  показываются;
- вопросы размещения собранных ассетов (`dist/` tracked, TD-003) и импорта
  `src/brief/` (TD-009) требуют решения.

Если не будет принят: ничего не меняется; план остаётся справочным.
