## 1. Назначение и область

DurEx описывает минимальный контракт для систем, где участники выполняют долгоживущие задачи, конкурируют за право выполнения,
совершают внешние действия, могут аварийно завершиться, восстанавливают работу после сбоя и должны учитывать необратимые решения.

Потенциальные области: MONOLITH Durable State, SphynX Research Workflows, корпоративные агентные workflow, фоновые задания,
human-in-the-loop. **Не утверждается**, что DurEx реализован или проверен в какой-либо из них: единственная опора — Design A
для MONOLITH Durable State, и только в его модели отказов (Mode A, ADR-018).

## 2. Семь контрактов

**DEP-1. Event Identity.** Подтверждённое событие имеет стабильную каноническую идентичность; физическое представление (отдельный
файл, строка сегмента) может меняться без изменения логического события. *Опора:* Canonical Event Identity (CEI-1…CEI-5) и
требования канонической компакции CC-1…CC-6 (Design A §35, §40).

**DEP-2. Decision Finality.** Необратимое решение фиксируется однозначно: конкурентные участники не могут подтвердить несовместимые
решения; побеждает первое опубликованное, остальные обязаны действовать по прочитанному значению. *Опора:* immutable decision
register, create-only, first-decision-wins (ADR-019).

**DEP-3. Execution Authority.** Создание задачи не равно разрешению выполнять действие. Право выполнения выдаётся отдельной
проверяемой процедурой, которая сама перечитывает актуальное состояние зависимостей (без кэша). *Опора:* `claim` → fence (Design A §20.6, §27).

**DEP-4. Fencing.** Устаревший участник не получает **новое** право выполнения после утраты полномочий. DEP **не** обещает автоматической
отмены уже начатого внешнего эффекта (в Design A — ограничение R-6, §42.2). *Опора:* fence выдаётся только из свежего `LIVE`.

**DEP-5. Failure Semantics.** Различаются: отсутствие состояния, неопределённое наблюдение, повреждение состояния, промежуточное
решение, подтверждённое решение. Неопределённость и повреждение никогда не дают права на необратимое действие. *Опора:* `MISSING`,
`UNREADABLE`, `CORRUPT`, `PREPARING`, `COMMITTED` (Design A §20.2, §37; ADR-018 D2).

**DEP-6. Recovery.** После сбоя система продолжает работу на основании подтверждённого состояния; recovery идемпотентен и не создаёт
решения, противоречащего принятому. *Опора:* roll-forward / `abort`, матрица crash-recovery (Design A §12, Приложение A §A.3).

**DEP-7. External Effect Boundary.** Явно отделяет, что гарантирует протокол и что нет:
* *гарантирует (в проверенной модели):* единственность решения, отсутствие нового права выполнения после `COMMITTED`, различимость исходов, идемпотентное восстановление внутренних шагов;
* *не гарантирует:* **exactly-once** выполнение внешних эффектов; остановку уже начатого эффекта; защиту от восстановления старой копии хранилища (может повторить эффекты);
* *требует от прикладного кода:* **idempotency** (повтор эффекта безопасен), **reconciliation** (сверка факта с внешней системой при неизвестном исходе), **business authorization** (отдельное решение о допустимости операции).

## 3. Три различаемых понятия

| Понятие | Вопрос | Чем подтверждается |
|---|---|---|
| **Execution Authority** | Имеет ли участник действительное право *начать* выполнение? | fence, выданный `claim` (DEP-3, DEP-4) |
| **Business Authorization** | Разрешена ли *этой* операции бизнес-логика? | политика предметной области — **вне DurEx** |
| **External Effect Confirmation** | Подтверждено ли *фактическое* выполнение внешнего действия? | ответ внешней системы / reconciliation — **вне DurEx** |

Fence не даёт автоматического права на возврат денег, удаление данных или изменение пользовательского аккаунта. Подтверждение внутреннего события
(`effect.intended`, `'appended'`) не означает, что внешний эффект выполнен — и тем более выполнен ровно один раз.

## 4. Traceability

Статусы: `DERIVED_FROM_DESIGN_A` — контракт прямо следует из нормативного текста Design A; `PROPOSED_GENERALIZATION` — обобщение за пределы Design A;
`NOT_YET_VERIFIED` — не проверялось независимо. Столбец «Verified Property» ссылается **только** на проверенное для Design A (ограниченные модели Security 004F, границы — отчёт 004F §H);
**результаты model checking не переносятся на DurEx как универсальный протокол автоматически.**

Независимая проверка DurEx потребуется при появлении **конкретной реализации** вне MONOLITH Durable State (отдельная модель отказов, отдельный Security Gate).

## 5. Допущения, переносимые вместе с контрактами

Контракты DEP-1…6 опираются на допущения Design A: атомарная create-only публикация (A1), real-time межкаталожная видимость на одном ядре (A2-R, FS-1…FS-6),
неизменяемость записей регистра (A6), модель отказов Mode A (процессные сбои; OS crash, внешнее вмешательство и сетевые ФС исключены). При другой среде допущения
нужно пересматривать; их перенос «по умолчанию» не допускается.

## 6. Чего DurEx не делает

Не вводит: runtime API, пакеты и модули, формат хранения, scheduler, workflow engine, систему агентов, схему авторизации, новые ADR, план коммерциализации. Не изменяет Design A,
ADR-018, ADR-019 и план FIX-004. Не присваивает `PROVEN` и не заявляет exactly-once. Tagline не является гарантией.
