# ADR-016 — Bounded State & Checkpoint History (STATE-003)

> **Статус: `proposed`. Реализация НЕ авторизована. Merge НЕ авторизован.**
> Ревизия 2 (2026-10-23), подготовка к независимому архитектурному ревью.
> Документ консолидирует директиву Mission Control (архитектура C′ выбрана,
> решения помечены **[OWNER]**) и рекомендации автора (**[REC]**).
> Исходные отчёты предыдущих исследований и отчёт SEC-RECOVERY-001 в
> репозитории недоступны и здесь не цитируются; всё, что не следует из
> директивы, кода или явно помеченного расчёта, в ADR не заявляется.
> Метки значений: **измерено** (получено запуском на этой машине),
> **расчёт** (арифметика/сериализация, не бенчмарк), **факт кода** (с ссылкой).
> Расчётные значения не являются измерениями производительности.

**Что изменилось в ревизии 2** (по замечаниям к ревизии 1; список для ревьюера):

1. **R-DEGRADE сужен** до одного допустимого случая (§7); `UNKNOWN`, конфликт и
   провал проверки сегмента, security-класс и любой неклассифицированный сбой
   больше не маскируются — мутация отклоняется. Ревизия 1 относила к
   «деградации» символьную ссылку в `history/`, конфликт sha и провал проверки
   — это было неверно.
2. **Найден дефект алгоритма архивации** (расчёт, §3.4): при полу состояния
   около или выше `HIGH` каждая мутация, создающая чекпоинт, порождала бы
   отдельный сегмент из одной записи; манифест (внутри `state.json`) рос бы на
   сотни байт за мутацию и сам поднимал пол. Добавлены `ARCHIVE_MIN_BATCH_BYTES`
   и правило необходимости (§6, шаг 4).
3. **Критическая секция ограничена по построению:** не более одного сегмента
   за вызов (`ARCHIVE_MAX_SEGMENTS_PER_CALL = 1`); первая архивация большого
   состояния сходится за несколько вызовов (§3, §6).
4. **Лимиты миссии** (§11): поля `title`/`system`/`summary` не ограничены кодом;
   минимальные защитные потолки и граница с отдельным ADR о миссиях.
5. **Миграция упрощена** (§13): замороженная копия старого валидатора не нужна и
   небезопасна (валидатор не passthrough); вместо неё — механическое
   преобразование + проверка «без потерь» относительно сырого JSON.
6. **Зависимость от lock protocol** оформлена как жёсткий гейт `G-LOCK` для
   всей реализации (§14, §15); путь «принятие остаточного риска» (Q2 ревизии 1)
   снят как противоречащий директиве.
7. Устранена циркулярность: бенчмарк AC-26 требует кода, поэтому он — критерий
   выхода фазы P3, а не условие перехода ADR в `accepted` (§15, §18).
8. Уровень 1 проверки манифеста обязан жить в чистом экспортируемом
   `validateState` (им пользуется Dashboard Read Model, а не `readState`) (§10).

## 1. Context

`state.json` хранит чекпоинты (`tactical.checkpoints`) без удержания и
компактации. Защитный потолок `MAX_STATE_BYTES = 16 MiB` (SEC-001B.1) при
достижении делает `state.json` нечитаемым/незаписываемым для `mission`
(fail-closed): новые миссии и чекпоинты записать нельзя, пока не вмешается
человек (tech-debt STATE-001). Автоматическое удаление истории запрещено.

Ограничения кода, из которых исходит проектирование (проверено по `main`,
`4ab6f09`):

- Чекпоинт ограничен только по полям: `summary` ≤ 4000, `context` ≤ 4000,
  `remainingSteps` ≤ 50 × 500 символов (`checkpoint.ts:23-26`, длина в единицах
  UTF-16 `.length`).
- Поля миссии **верхней границы не имеют**: `title`/`system` — только
  `trim()` и непустота (`mission.ts:30-45`); `summary` в `finishMission`
  сохраняется как есть, без обрезки, без ограничения длины и без проверки типа
  во время выполнения (`mission.ts:109`). Читающий валидатор проверяет только
  типы и непустоту `title`/`system` (`state-keeper.ts`, `validateMission`).
  Количество миссий не ограничено.
- Через CLI поле ограничено лишь платформой: **измерено** на этой машине (Linux),
  аргумент процесса длиной 131 071 B проходит, 131 072 B — `E2BIG`. Через API
  (`startMission`/`finishMission`) границы нет. UI read-only (ADR-010) и
  миссий создать не может.
- Каждая мутация переписывает весь файл (`mutateState` → `replaceFile`).
- Идентификатор чекпоинта — `<missionId>-CKPT-NNNN`; следующий ординал
  выводится как `max + 1` по присутствующим записям (`nextCheckpointId`).
- Критическая секция — под кросс-процессным lock (`lock.ts`, `timeoutMs`
  по умолчанию 5000 мс).
- `validateState` не passthrough: неизвестные поля молча отбрасываются
  (документировано в `state-keeper.ts`). Важно для миграции (§13).
- Версионный барьер: бинарник, знающий только схемы 1 и 2, на файле схемы 3
  завершается `StateSchemaError` до любого чтения в черновик
  (`validateState`, проверка `schemaVersion`) — тихой потери данных нет.

## 2. Decision (C′)

**[OWNER]**

- `state.json` хранит миссии и ограниченное окно `tactical.recentCheckpoints`.
- Исторические чекпоинты лежат в неизменяемых JSONL-сегментах.
- Манифест истории находится **внутри** `state.json`; манифест и актуальное
  состояние публикуются одним атомарным `replaceFile`. Сегменты записываются
  до публикации манифеста, не изменяются и автоматически не удаляются.
- Единственная схема — `schemaVersion: 3`; `history` присутствует всегда;
  `tactical.checkpoints` → `tactical.recentCheckpoints`. Обычные read/write API
  старые схемы не поддерживают, адаптеров совместимости нет.
- FORWARD-ONLY: без поддержки старых бинарников, устаревших API,
  compatibility adapters и reverse migration; неактуальная архитектура и её
  тесты удаляются. Потеря существующих данных запрещена.

Уточнения ревизии 2 (внутри C′, не меняют выбор архитектуры; **[REC]**,
подтверждение — Q9): правило необходимости и минимальной порции архивации,
один сегмент за вызов, строгая классификация R-DEGRADE (§7).

## 3. Constants (один согласованный набор) — [REC]

### 3.1 Значения

| Константа | Значение | Основание |
|---|---:|---|
| `STATE_HARD_LIMIT_BYTES` (= `MAX_STATE_BYTES`) | 16 MiB | факт кода (`state-keeper.ts:48`), не меняется; потолок чтения = потолку записи |
| `STATE_WARN_BYTES` | 12 MiB (75 %) | диагностика `STATE_NEAR_LIMIT` |
| `ARCHIVE_HIGH_BYTES` | 1 MiB | порог запуска архивации (сериализованный `state.json`), **предварительный** |
| `ARCHIVE_LOW_BYTES` | 512 KiB | цель архивации (гистерезис), **предварительный** |
| `ARCHIVE_MIN_BATCH_BYTES` | 128 KiB (= (HIGH − LOW) / 4) | **новое.** Минимальное уменьшение `state.json`, оправдывающее архивацию; защита от сегментов-«крошек» (§3.4). **Предварительный** |
| `ARCHIVE_MAX_SEGMENTS_PER_CALL` | 1 | **новое.** Ограничивает критическую секцию по построению (§3.5) |
| `RECENT_WINDOW_PER_MISSION` | 20 | предпочтительное окно; уровень 1 архивации |
| `RECENT_FLOOR_PER_MISSION` | 1 | I-LAST; уровень 2 архивации |
| `SEGMENT_CEILING_BYTES` | 2 MiB | максимум размера одного сегмента и лимит его чтения |

«Предварительный» = значение выдвинуто с аргументом, но не подтверждено
измерением; подтверждается/пересматривается критерием AC-26 на выходе фазы P3
(§15). Других значений и других аргументов, кроме перечисленных ниже, у ADR нет.

### 3.2 Размеры записей

Что известно и как получено:

- **Измерено** на остатке синтетического файла предыдущей сессии (v2, 100
  миссий, 13 007 чекпоинтов с полями ≈ 300/3×80/300 символов): 14 646 290 B, в
  среднем **1126 B на чекпоинт** (включая отступы pretty-print). Это синтетика,
  не реальное использование; реальное распределение размеров неизвестно.
- **Расчёт** (сериализация чекпоинта с максимальными по валидации полями,
  pretty-print как в `atomicWriteState`, вложенность как в файле; перепроверен
  в ревизии 2 — расхождение с ревизией 1 < 0.1 %, из-за длины `id`): худший
  чекпоинт ASCII ≈ **33 972 B**; при 3-байтовых символах UTF-8 ≈ **99 972 B**;
  при управляющих символах (JSON-эскейп `\u0001`, 6 B) ≈ **198 972 B**.

| | типичный (1126 B) | худший ASCII (33 972 B) | худший 3-байт. (99 972 B) |
|---|---:|---:|---:|
| в 1 MiB | ≈ 930 | ≈ 30 | ≈ 10 |
| в 512 KiB | ≈ 465 | ≈ 15 | ≈ 5 |
| в 16 MiB | ≈ 14 900 | ≈ 493 | ≈ 167 |
| 20 чекпоинтов (окно) | ≈ 22 KiB | ≈ 663 KiB | ≈ 1.9 MiB |

Окно в 20 штук **не гарантирует** размер: две миссии с худшими чекпоинтами уже
превышают HIGH. Гарантию размера (где она достижима) даёт цикл «HIGH → LOW +
пол I-LAST», а не счётчик окна. Окно — предпочтение уровня 1, а не триггер.

### 3.3 Пол состояния и достижимость LOW (расчёт)

Пол = Σ по миссиям (запись миссии + последний чекпоинт, I-LAST) + манифест +
накладные. Запись миссии: типичная 347 B (title 80 символов, `summary: null`);
при предлагаемых лимитах §11 (500/100/4000): ≈ 4 849 B ASCII, ≈ 14 049 B
(3-байт.), ≈ 27 849 B (управляющие). Число миссий, при котором пол достигает
порога:

| Профиль «миссия + последний чекпоинт» | B/миссия | = LOW (512 KiB) | = HIGH (1 MiB) | = WARN (12 MiB) | = HARD (16 MiB) |
|---|---:|---:|---:|---:|---:|
| типичный (347 + 1126) | 1 473 | ≈ 355 | ≈ 711 | ≈ 8 540 | ≈ 11 390 |
| худший ASCII (4 849 + 33 940) | 38 789 | ≈ 13 | ≈ 27 | ≈ 324 | ≈ 432 |
| худший 3-байт. (14 049 + 99 940) | 113 989 | ≈ 4 | ≈ 9 | ≈ 110 | ≈ 147 |
| худший с эскейпами (27 849 + 198 940) | 226 789 | ≈ 2 | ≈ 4 | ≈ 55 | ≈ 73 |
| *сегодня:* title 131 071 B + типичный чекпоинт | 132 447 | ≈ 3 | ≈ 7 | ≈ 95 | ≈ 126 |

Выводы (расчёт): (а) LOW достижим только пока пол ≤ LOW — для типичных записей
это порядка сотен миссий, для максимальных записей — единицы; **LOW — цель, а не
гарантия**, алгоритм обязан быть корректным, когда она недостижима; (б) HARD
достижим одним лишь полом (I-LAST не позволяет архивировать последние
чекпоинты и миссии не архивируются) — это остаточный риск RR-1, закрывается
только архивацией миссий (отдельный ADR, не часть STATE-003); (в) без лимитов
полей пол одной миссии не ограничен (последняя строка) — отсюда §11.

### 3.4 Дефект «крошек» и правило необходимости (расчёт)

Пусть пол F ≥ HIGH − 1 KB. В ревизии 1 после каждой мутации, создающей
чекпоинт, предыдущий последний чекпоинт миссии становился неполовым
кандидатом → `size > HIGH` и кандидат есть → архивация **одной записи** (сегмент
≈ 1 KB). Следствия: один сегмент на каждый чекпоинт; запись манифеста
(**измерено** сериализацией: ≈ 394 B на сегмент с одной миссией в `ranges`,
+≈ 75 B на каждую дополнительную миссию) растёт быстрее, чем уходит из файла
чекпоинт (≈ 1.1 KB − 0.4 KB), то есть манифест накапливается в самом `state.json`
(≈ 42 000 таких сегментов исчерпали бы 16 MiB одним манифестом), плюс
2 `fsync` каталога и файла на сегмент в критической секции. Исправление:

- **Правило необходимости** (шаг 4 §6): архивировать, только если
  `S > HIGH` **и** уменьшение `R ≥ ARCHIVE_MIN_BATCH_BYTES`; либо `S > HARD` и
  `R > 0` (без архивации мутация была бы отклонена — F4). `R` — разность
  точных сериализаций «до» и «после» (с учётом новой записи манифеста).
- Следствие: при `F ≤ LOW` правило не срабатывает (R ≈ HIGH − LOW = 512 KiB ≥
  128 KiB); при `F > HIGH − 128 KiB` архивация происходит не чаще чем раз на
  ≈ 128 KiB прироста; сегмент ≥ ≈ 100 KiB в компактной записи, накладные
  манифеста ≈ 0.4 %.
- 128 KiB выбрано как (HIGH − LOW) / 4: порядок, при котором накладные манифеста
  пренебрежимо малы, а число мутаций между архивациями остаётся умеренным.
  Другого обоснования нет; значение проверяется AC-26 (сценарий «пол ≥ HIGH»).

### 3.5 Ограничение критической секции (расчёт)

Ревизия 1 допускала до ≈ 8 сегментов за один вызов (первая архивация ≈ 14 MiB):
запись, `fsync` и повторное чтение каждого — внутри lock с `timeoutMs` 5000 мс
у ожидающих. Теперь один вызов: ≤ 1 сегмент ≤ 2 MiB.

- Худший вызов: запись ≤ 2 MiB (сегмент) + ≤ 16 MiB (`state.json`), чтение
  ≤ 16 MiB (состояние) + ≤ 2 MiB (проверка), 4 `fsync` (файл + каталог на
  сегмент, файл + каталог на состояние) против 2 у обычной мутации.
  Архивация добавляет ≤ 2 MiB записи (≈ 12.5 % к худшей обычной мутации).
- Состояние ≈ 14 MiB сходится к LOW за ≈ 7 вызовов (по ≈ 2 MiB компактных данных
  за вызов), оставаясь `≤ HARD`. Отклонение мутации по F4 оценивается **после**
  архивации того же вызова (шаг 7), поэтому один вызов, добавляющий ≤ 199 KB
  (максимум одного чекпоинта), всегда помещается, если пол помещается.
- Частичных мультисегментных сбоев (сегмент 1 записан, сегмент 2 нет) больше не
  бывает — исчезает класс сирот «хвоста плана».

### 3.6 Стоимость записи (расчёт; не бенчмарк)

Каждая мутация пишет файл целиком, поэтому её стоимость ≈ размер файла `S`, а не
размер изменения Δ (≈ 1.1 KB для типичного чекпоинта):

| `S` | байт записано за мутацию | отношение к Δ ≈ 1126 B |
|---|---:|---:|
| 512 KiB (LOW) | 0.5 MiB | ≈ 470× |
| 1 MiB (HIGH) | 1 MiB | ≈ 930× |
| 12 MiB (WARN) | 12 MiB | ≈ 11 200× |
| 16 MiB (HARD) | 16 MiB | ≈ 14 900× |

Архивация добавляет в среднем одну запись на чекпоинт (каждая запись пишется в
сегмент один раз) + запись манифеста на сегмент — порядка 0.1–0.2 % к
переписыванию 0.5–1 MiB. Основная стоимость — базовое переписывание файла;
архивация держит `S` в диапазоне LOW…HIGH там, где пол это позволяет. При
полу > HIGH стоимость мутации ≈ пол, и это остаточный риск RR-1/RR-11.

### 3.7 Вердикт по порогам

| Вопрос | Вывод |
|---|---|
| HARD 16 MiB | факт кода, не меняется |
| WARN 12 MiB | диагностический порог, без поведенческих последствий; оставить |
| HIGH 1 MiB / LOW 512 KiB | **оставить предварительными.** Аргумент «меньше переписывать» не измерен; аргумент против изменения — отсутствие данных. Найденные дефекты (§3.4, §3.5) лежали в правилах, а не в значениях, и исправлены правилами. Подтверждение/пересмотр — AC-26 |
| Максимальные checkpoint | один чекпоинт ≤ ≈ 199 KB; ≤ 1 сегмента ≥ этого размера за вызов → прирост всегда покрывается архивацией, если есть кандидаты |
| Много активных миссий | `20 × N` записей окна сводятся архивацией уровня 2 к полу; пол — таблица §3.3 |
| Достижимость LOW при I-LAST | только при `пол ≤ LOW` (§3.3); иначе F2/F2b, без цикла |
| Размер/число сегментов | ≤ 2 MiB, ≥ 1 запись; из-за MIN_BATCH практически ≥ ≈ 100 KiB (компактно); манифест ≈ 0.2 % архивированного объёма при 10 миссиях на сегмент (1069 B на ≈ 512 KiB) — рост внутри `state.json`, «стена» порядка 10⁴ сегментов (≈ 5 GiB архива при 512 KiB), RR-2 |
| Невозможность архивации | F2 (нет кандидатов), F2b (мало), §7 (ошибка архивации) |
| Бесконечные циклы | нет: ≤ 1 попытка за вызов, нет повтора, нет фонового процесса, нет самозапуска (§6) |
| Write amplification | §3.6; худший вызов §3.5 |

Отклонены: Вариант 2 «soft 4 MiB» (в 4 раза больше переписываемый файл без
выигрыша в гарантиях); Вариант 1 «segment 8 MiB» (чтение сегмента целиком в
память и более длинная критическая секция без причины: максимальная запись
< 200 KB).

## 4. Schema v3

```json
{
  "schemaVersion": 3,
  "revision": 17,
  "strategic": { "systems": {} },
  "tactical": {
    "missions": { "MIS-0001": { "…": "Mission как в v2" } },
    "recentCheckpoints": { "MIS-0001-CKPT-0041": { "…": "Checkpoint как в v2" } }
  },
  "history": {
    "archivedCheckpointCount": 40,
    "segments": [
      {
        "seq": 1,
        "file": "ckpt-000001-3fa9c1d27b4e.jsonl",
        "sha256": "<64 hex>",
        "bytes": 48213,
        "checkpointCount": 40,
        "ranges": { "MIS-0001": [1, 40] },
        "publishedAtRevision": 17
      }
    ]
  }
}
```

- `history` обязателен всегда (`{"archivedCheckpointCount":0,"segments":[]}`).
- `Checkpoint` и `Mission` не меняются. `strategic` не меняется.
- Сегмент: `<stateDir>/history/<file>`, UTF-8 JSONL, одна запись `Checkpoint` на
  строку (компактный `JSON.stringify`, фиксированный порядок ключей), строки
  отсортированы по `(missionId, ordinal)`, заголовка нет. Содержимое
  детерминировано → одинаковое содержимое даёт одинаковые `sha256` и имя.
- `file` должен соответствовать `^ckpt-\d{6}-[0-9a-f]{12}\.jsonl$`; `seq` и
  префикс хеша в имени совпадают с полями. Путей и разделителей в манифесте
  быть не может.
- Единственный источник истины о количестве по миссии — `ranges`;
  `archivedCheckpointCount` — перекрёстная проверка (равен Σ `checkpointCount`).
- Размер записи манифеста (**измерено** сериализацией): 394 B при одной миссии в
  `ranges`; +≈ 75 B на каждую следующую миссию (1069 B при 10, 7 819 B при 100,
  75 319 B при 1 000).

## 5. Data invariants (все проверяются валидатором при чтении; нарушение блокирует чтение и запись)

- **I-PREFIX** — по каждой миссии диапазоны сегментов (в порядке `seq`) образуют
  непрерывный префикс ординалов `1..k`; `recentCheckpoints` миссии — непрерывный
  диапазон `k+1..n`.
- **I-LAST** — если у миссии есть чекпоинты (в любой статусе, включая
  завершённые), её последний чекпоинт присутствует в `recentCheckpoints`;
  миссия с архивом, но без recent — нарушение.
- **I-UNIQUE** — `id` уникальны в логической истории (recent ∪ сегменты
  манифеста); осиротевшие файлы сегментов в логическую историю не входят.
- **I-CONSERVATION** — при архивации множество чекпоинтов
  `recent_before` = `recent_after ⊎ archived_new`, записи побитово не меняются;
  проверяется до публикации.
- **I-SINGLE-COMMIT** — единственная точка фиксации нового состояния и
  манифеста — `replaceFile(state.json)`; сегмент становится частью истории
  только в момент этой публикации.
- **I-FAIL-CLOSED** — повреждение манифеста или нарушение инвариантов
  запрещает запись (и чтение): `StateHistoryInvalidError`, автоисправления нет.

Дополнительно валидатор v3 проверяет: `id` чекпоинта соответствует
`<missionId>-CKPT-NNNN`, миссия существует, `seq` = 1..N без пропусков,
`publishedAtRevision` ≤ `revision`. Мутатор не имеет права менять `history`
(Core проверяет после вызова мутатора → `HISTORY_MUTATION_FORBIDDEN`).

**Чистота валидатора.** Все проверки уровня 1 (§9) выполняет чистая
экспортируемая `validateState(raw)` — не `readState`. Причина (факт кода):
Dashboard Read Model в ветке `feat/ui-001b1` читает файл через `readProjectFile`
и вызывает `validateState` напрямую, минуя `readState`; проверка, живущая только
в `readState`, для UI не сработала бы.

## 6. Archival protocol (внутри одного `mutateState`, под существующим lock)

1. **Read & validate** — безопасное чтение (ADR-014), валидация v3 и инвариантов
   (`validateState`, уровень 1).
2. **Mutate** — применить запрошенную мутацию; `history` не изменяется.
3. **Measure** — `S` = размер точной сериализации. Если `S ≤ HIGH` → шаг 7 без
   архивации (ни одной операции с сегментами).
4. **Plan** (чистая функция, без I/O):
   - Кандидаты. Уровень 1: чекпоинты за пределами окна `W = 20` каждой
     миссии; уровень 2 (если всё ещё выше LOW): далее самые старые до пола `1`.
     Внутри миссии строго по ординалу; между миссиями порядок
     `(createdAt, missionId, ordinal)` через `compareStrings` (детерминизм, не
     `localeCompare`).
   - Срез: один сегмент — префикс упорядоченного списка кандидатов, который
     останавливается при достижении LOW (по точной сериализации результата) или
     при заполнении `SEGMENT_CEILING`. Срез сохраняет префиксы ординалов по
     каждой миссии (I-PREFIX).
   - `R` = `S` − `S'`, где `S'` — точная сериализация итогового состояния (с
     новой записью манифеста).
   - Решение: нет кандидатов → архивации нет, диагностика
     `STATE_ABOVE_HIGH_UNREDUCIBLE`, шаг 7. Кандидаты есть, но `R <
     ARCHIVE_MIN_BATCH_BYTES` и `S ≤ HARD` → архивации нет, **без**
     диагностики (нормальный режим, F2b), шаг 7. `S > HARD` и `R > 0` →
     архивировать независимо от `MIN_BATCH` (иначе мутация будет отклонена).
   - План проверяется на I-PREFIX/I-LAST/I-UNIQUE/I-CONSERVATION; нарушение —
     дефект реализации: `ARCHIVE_PLAN_INVARIANT`, мутация отклоняется (§7, B7).
5. **Publish segment** — `createFile` (create-only `link()`, `0600`,
   durability `full`) в `<stateDir>/history/`. Существующий файл с тем же именем
   допускается только если он побайтно (по `sha256`) совпадает — это
   идемпотентный остаток прерванной попытки; иначе `ARCHIVE_SEGMENT_CONFLICT`.
6. **Verify** — повторное чтение сегмента безопасным читателем: размер, `sha256`,
   число строк, валидность и принадлежность записей диапазонам.
7. **Commit** — собрать финальное состояние (revision+1, манифест, урезанный
   recent), проверить `size ≤ HARD`, опубликовать `state.json` (`replaceFile`).
8. **Release** — освободить lock; предупреждения доставляются после освобождения.

Любой сбой на шагах 5–6 классифицируется **функцией классификации §7**: либо
`DEGRADE` (перейти к шагу 7 с состоянием без архивации), либо `ABORT`
(исключение, `state.json` не тронут). Других исходов нет.

Свойства:

- Не более одной попытки архивации на вызов `mutateState`: ≤ 1 публикация
  сегмента, ≤ 1 `replaceFile(state.json)` (в том числе на пути DEGRADE — это то
  же самое единственное обновление). Повторов нет. Каждая успешная архивация
  строго уменьшает `|recent|`; сегмент без записей не создаётся. Нет фонового
  процесса и самозапуска: следующая попытка возможна только при следующей
  мутации. Бесконечного цикла нет.
- Сегмент с результатом публикации `UNKNOWN` не повторяется, не удаляется и не
  переклассифицируется (§7, B1). `state.json` с `UNKNOWN` — как в ADR-012:
  исключение, без повтора.
- Подтверждённые чекпоинты не теряются ни в одном исходе: до шага 7 в
  `state.json` ничего не менялось, а сегмент без публикации манифеста в
  логическую историю не входит.

## 7. R-DEGRADE — строгая классификация ошибок

### 7.1 Решение

**[REC → Q8]** Сохранить R-DEGRADE в виде **R-DEGRADE-STRICT**: допустим ровно
один класс сбоя; всё остальное — `ABORT`. Классификация — это default-deny.
Обоснование выбора (а не удаления): архивация — новый механизм, и он не должен
делать систему менее доступной, чем сегодня в зоне ниже 16 MiB, где мутации
работают без неё. При этом приоритет — сохранность данных: DEGRADE ничего не
пишет в манифест и не меняет данные, а поэтому не может их потерять.
Безопасная классификация возможна, потому что `SafeWriteError` несёт типизированный
`code` и `publication` (`safe-write.ts:109-127`), и решение не опирается на текст
сообщений. Если ревьюер сочтёт allowlist небезопасным, запасной вариант
**R-NONE** (любой сбой архивации → `ABORT`) получается удалением строки A1 и
теста AC-18/AC-32 для неё; архитектура от этого не меняется.

### 7.2 Условия DEGRADE (все должны выполняться; вычисляются, а не предполагаются)

- **P1** Сбой на шаге 5 при публикации сегмента (или при создании `history/`).
- **P2** Исключение — `SafeWriteError` с `publication === 'NOT_PUBLISHED'`
  и `code === 'WRITE_NO_SPACE'` (это ENOSPC/EDQUOT, `safe-write.ts:256-258`).
  **Единственный код в allowlist.**
- **P3** В этом вызове нет ранее обнаруженной находки класса ABORT. Старшинство:
  любая ABORT-находка отменяет DEGRADE.
- **P4** Исходное состояние валидно (шаг 1 пройден, включая манифест и все
  инварианты).
- **P5** Состояние без архивации (результат мутации) проходит валидатор v3 и
  инварианты, и `S ≤ HARD`.
- **P6** `history` побайтно равна исходной; ни один сегмент не добавлен в
  манифест.

### 7.3 Матрица

Классификация реализуется как исчерпывающий `Record<WriteErrorCode, 'DEGRADE' |
'ABORT'>` (в стиле `FILE_CODE_MAP` UI read model): новый код ошибки — ошибка
компиляции, пока он не классифицирован; всё, что не `SafeWriteError`, — `ABORT`.

| # | Условие | Класс | Мутация | `state.json` | Диагностика |
|---|---|---|---|---|---|
| A1 | `WRITE_NO_SPACE`, `NOT_PUBLISHED`, публикация сегмента / создание `history/`; P3–P6 выполнены | **DEGRADE** | публикуется **без** архивации | один обычный `replaceFile`; если он не удался — F12/F13 | предупреждение `ARCHIVE_SKIPPED{cause: WRITE_NO_SPACE}` после освобождения lock; код возврата 0 |

Замечание о несогласованности сегментов и манифеста. Поведение «запись
продолжается, пока старый опубликованный сегмент физически повреждён» (F6) — не
R-DEGRADE, а уровень 2 (§9): физическое состояние старых сегментов при записи не
читается и не проверяется. R-DEGRADE никогда не превращает ни одну из находок
B1–B10 в успех.

### 7.4 Свойства DEGRADE

- Результат равен тому, что выдала бы та же мутация без механизма архивации;
  данные и манифест не меняются; I-* сохраняются тривиально.
- Ровно одна публикация `state.json`; второй попытки записи нет.
- Нет «липкого» режима: следующая мутация снова пытается архивировать.
- Наблюдаемость — только предупреждение вызова (и `STATE_NEAR_LIMIT`/
  `STATE_ABOVE_HIGH_UNREDUCIBLE` в `brief`). Счётчик деградаций в состоянии не
  хранится (это потребовало бы расширения схемы) — RR-4.

## 9. Integrity levels

1. **Структура манифеста — каждое чтение через `validateState`.** Чистая, в
   памяти, без доступа к сегментам. Нарушение блокирует чтение и запись (F5).
2. **Физический сегмент — при обращении к истории.** Безопасное чтение
   (граница, без symlink/hardlink, `maxBytes = SEGMENT_CEILING`), размер, `sha256`,
   число строк, записи ↔ диапазоны манифеста, отсутствие дублей с recent.
   Блокирует только этот запрос.
3. **Полная проверка — отдельная команда `monolith history verify`.** Только
   чтение, без lock, по снимку `state.json`: все сегменты, сироты, I-UNIQUE и
   I-CONSERVATION по логической истории. Код возврата ≠ 0 при проблеме.

Dashboard обычное обновление уровнем 2/3 не пользуется.

## 10. Core read contract и граница Core/UI

**Core** — физическое хранение, манифест, архивация, проверка целостности,
логические selectors, типизированные ошибки. **UI** — Dashboard Read Model,
Presentation DTO, отображение ошибок. UI не знает о сегментах, путях, структуре
манифеста и механизме архивации. Согласованные решения UI Team сохранены без
изменений: Core даёт логический Dashboard Snapshot; обычное обновление Dashboard
не читает исторические сегменты; полный счётчик чекпоинтов включает архив;
API постраничного просмотра истории не создаётся.

- Селекторы (чистые, синхронные, в `src/coordinatorium/selectors.ts`; сегодняшние
  `selectActiveMissions`, `selectRecentFinishedMissions`, `selectLatestCheckpoint`,
  `hasCheckpointOrderMismatch` переезжают туда из `src/brief/selectors.ts`;
  [REC], связано с TD-009).
- `selectDashboardSnapshot(state: CoordinatoriumState): DashboardSnapshot`:

```ts
interface DashboardSnapshot {
  stateRevision: number;
  archiveIntegrity: 'NOT_VERIFIED';          // литеральный тип: физическая целостность не проверялась
  totalCheckpointCount: number;              // recent + архив
  missions: Array<{
    mission: Mission;                        // порядок (startedAt, id), compareStrings
    latestCheckpoint: Checkpoint | null;     // по I-LAST всегда из recent
    recentCheckpoints: Checkpoint[];         // ≤ RECENT_WINDOW_PER_MISSION, по возрастанию ординала
    checkpointCount: number;                 // логическое, включая архив
  }>;
}
```

  Не раскрывает имена файлов, `seq`, `sha256`, `ranges`. Историю не читает.
  «Актуальные миссии» = все миссии в `state.json` (миссии не архивируются;
  допущение A-1).
- **Нет API постраничного просмотра.** `listCheckpointHistory` (§12) — вызов
  CLI/Core, читает сегменты одной миссии целиком, без курсора, смещения и
  лимита; UI им не пользуется (AC-25).
- Ошибки Core для UI — типизированные коды без путей и имён файлов
  (`StateHistoryInvalidError` → «источник повреждён»).
- Граница обеспечивается тестом архитектуры: код UI не обращается к
  `state.history` и `state.tactical` напрямую.
- Влияние на ветку `feat/ui-001b1` (факт кода, читалось только): модель
  вызывает `validateState` из Core и использует `Object.values(state.tactical.
  checkpoints)` и заметку `STATE_LEGACY_SCHEMA_MIGRATED` для схемы 1. После
  STATE-003 первое заменяется `selectDashboardSnapshot`, второе теряет смысл
  (FORWARD-ONLY). Это изменение UI-ветки в её собственной истории, не часть
  этого ADR.

## 11. Mission size limits

Различаются три уровня; STATE-003 вводит только первый.

| Уровень | Что | Решение |
|---|---|---|
| Отдельное поле | `title`, `system`, `summary` миссии | **вводится** (ниже) |
| Одна миссия | сумма полей + служебные поля | не ограничивается отдельным правилом; выводится из лимитов полей |
| Общее состояние | число миссий, суммарный размер | `HARD` (существует), `WARN`, диагностика пола; **счётчика-потолка нет** |

### 11.1 Лимиты полей — [REC → Q4]

Единицы — `.length` после `trim()`, как у полей чекпоинта. Это защитные
потолки, как лимиты SEC-001B.1, а не политика содержимого.

| Поле | Лимит | Аргумент |
|---|---:|---|
| `title` | 500 | на порядок больше разумного заголовка; не режет текущее использование (80 символов в синтетике — **измерено** лишь на синтетике, реальное распределение неизвестно) |
| `system` | 100 | идентификатор подсистемы |
| `summary` (в `finishMission`) | 4000 | то же, что `Checkpoint.summary` — ближайший аналог |

Тип `summary` проверяется во время выполнения (`string | null`). Пустую
строку и `null` это не меняет.

Следствие (расчёт, §3.3): запись миссии ≤ ≈ 4 849 B ASCII / ≈ 14 049 B
(3-байт.) / ≈ 27 849 B (эскейпы) вместо неограниченной (≥ 131 321 B через CLI
уже сегодня). Пол одной миссии становится ограниченным; таблица §3.3 перестаёт
быть открытой сверху.

### 11.2 Где применяются

- **Только на пути записи** (`startMission`, `finishMission`): `ValidationError`.
  Читающий валидатор лимитов **не применяет**: существующие поля больше лимита
  остаются читаемыми и не усекаются («потеря данных запрещена»; иначе файл с
  длинным `title` стал бы нечитаемым). Лимит ограничивает рост, а не прошлое
  (RR-9).
- Размещение: [REC] отдельная малая история **до** P3, независимая от архивации
  и от lock (правка валидации ввода двух функций). Альтернатива — внутри P1.
  Решение — Q4.

### 11.3 Почему нет потолка числа миссий

(а) Потолок только переносит тупик (`STATE_FLOOR_EXCEEDED`) раньше, не решая
его: при типичных записях HARD достигается на ≈ 11 400 миссиях, и никакое
разумное число не защищает от худшего случая (73 миссии с максимальными
записями, §3.3). (б) Реальная защита — архивация миссий; это **отдельный ADR**
(он затрагивает «актуальные миссии», A-1, brief и UI) и в STATE-003 не входит.
(в) Пока его нет, остаточный риск RR-1 зафиксирован, а ранние сигналы дают
`STATE_ABOVE_HIGH_UNREDUCIBLE` (пол > HIGH) и `STATE_NEAR_LIMIT` (≥ 12 MiB).

## 13. Migration decision

### 13.1 Факты (проверено в ревизии 2, 2026-10-23)

- В `main` и в трёх worktrees нет `.monolith/state.json`. Единственный
  отслеживаемый `state.json` — шаблон `templates/default-instance/monolith/
  state.json` (v2, пустой).
- В истории git `state.json` затронут двумя коммитами: `a51f2b5`
  (2026-10-21 08:59, схема 1) и `b8a320f` (2026-10-21 14:11, подъём до схемы 2).
  Схема 1 существовала в коде ≈ 5 часов; в течение ≈ 1 часа (с `aea408f`, 13:10)
  существовал переходный код, писавший чекпоинты под меткой 1.
- Поиск `state.json` в `.monolith`-путях под домашним каталогом владельца в
  этой ревизии: ничего не найдено (каталоги scratchpad сессий в `/tmp` не
  просматривались; ревизия 1 нашла там 8 синтетических файлов).
- Пакет `@monolith/core@0.1.0-alpha.0` объявляет `bin`, `private` не указан;
  `npm view @monolith/core` в публичном реестре — `E404`. Это не исключает
  приватные реестры, tarball, git-установку и другие машины.
- `monolith init` копирует шаблон v2 в каждый новый экземпляр: файлы схемы 2
  могут быть у любого, кто инициализировал экземпляр этим кодом.
- Бинарник со схемами 1–2 на файле схемы 3 отказывает громко (§1).

**Отсутствие файлов в репозитории не доказывает отсутствия пользовательских
данных.** Необходимость одноразового преобразования **не подтверждена и не
опровергнута**; решить может только владелец (Q1).

### 13.2 Решение — [REC, зависит от Q1]

**Ветка A — данные могут существовать.** Одноразовая явная команда
`monolith state upgrade [--dry-run]`, не участвующая в обычных API. Только
**v2 → v3**: схема 1 существовала часы (≈ 5 ч в истории коммитов), её поддержка
в команде не заявляется, если владелец не сообщит о существующем v1-файле
(Q1b). Процедура:

1. Под lock (требует G-LOCK, §14): безопасное чтение сырых байт ≤ 16 MiB
   (не через `readState`).
2. Разбор JSON; принимается только `schemaVersion: 2` (схема 3 → сообщение «уже
   v3», без записи).
3. **Механическое преобразование сырого JSON** (без копии старого валидатора):
   `tactical.checkpoints` → `tactical.recentCheckpoints`, добавить пустую
   `history`, `schemaVersion: 3`, `revision + 1`.
4. Валидация результата **боевым** валидатором v3 (§5; те же `validateMission`/
   `validateCheckpoint`), включая I-PREFIX (k = 0), I-LAST, I-UNIQUE.
5. **Проверка «без потерь» относительно сырого JSON:** канонический JSON
   валидированного результата обязан совпасть с каноническим JSON
   преобразованного сырого дерева. Любое расхождение (в том числе неизвестные
   поля, которые валидатор отбросил бы молча, §1) → отказ без записи с именем
   первого расхождения (без содержимого).
6. Размер результата ≤ 16 MiB (иначе отказ; см. RR-7).
7. Резервная копия `state.json.pre-v3.bak` через create-only `createFile`
   (`0600`, durability `full`; отказ, если уже существует); контрольная сумма в
   выводе.
8. Публикация `replaceFile`; повторное чтение `readState` и сравнение с п. 5.
9. Отката нет; бэкап — страховка, не API. Архивации в ходе upgrade нет.
10. Срок жизни: команда и её тесты живут один релиз, содержащий v3, затем
    удаляются (FORWARD-ONLY; конкретный релиз — Q1c).

`--dry-run` выполняет п. 1–6 без записи и печатает число миссий/чекпоинтов.

**Ветка B — данных нет (владелец подтвердил).** Ни команды, ни её кода:
файлы 1/2 отклоняются `STATE_SCHEMA_UNSUPPORTED` с сообщением, что пути
обновления нет. Миграционная инфраструктура не создаётся.

**В этой работе:** миграция не выполнялась, данные не удалялись и не
изменялись.

## 14. Security и зависимость от lock protocol

- **ADR-009:** `history/` всегда внутри `stateDir` внутри `monolithRoot`; имена
  из манифеста проверяются regex, пути не принимаются.
- **ADR-012:** все публикации (сегменты — `createFile`, `state.json` —
  `replaceFile`) идут через `safe-write.ts`; символьные ссылки запрещены (W-SYM),
  hardlink и не-regular отвергаются, режим `0600`, publication states и
  идентификационная очистка действуют; `history/` создаётся через `openParent`.
- **ADR-014:** все чтения сегментов — `readBoundedFile` с явной границей,
  `O_NOFOLLOW|O_NONBLOCK`, `nlink == 1`, лимитом `SEGMENT_CEILING`. Переходный
  `nlink == 2` сразу после `link()` обрабатывается существующим повтором
  `FILE_HARDLINKED` (`readBoundedFileStable`); постоянный — F19.
- **TM-C не поддерживается и не заявляется.** Подмена каталога `history/`
  параллельным процессом не защищена (SEC-001B.3 / ADR-013). Гарантии
  конкурентности — только lock.
- Релиз lock и stale-recovery остаются path-based (LOCK-RELEASE-001) и вне
  гарантий этого ADR.

### 14.1 Зависимость: SEC-RECOVERY-001 и ADR-015

Отчёт SEC-RECOVERY-001 в репозитории отсутствует (поиск по `main` и трём
worktrees: совпадений нет). Черновик **ADR-015** («Lock Owner Identity & Crash
Recovery», `docs/adr/ADR-015-lock-owner-identity-and-crash-recovery.md`)
появился в рабочем дереве `main` 2026-10-23 как **неотслеживаемый файл со
статусом `proposed`** (в ходе ревизии 2 ADR-016; читался, не изменялся). Он
описывает механизмы H1, H2, M1, M2 (помечены там `REPRODUCED` со ссылкой на
отчёт проверки) и план из четырёх этапов LOCK-FIX-001A…D. ADR-016 эти
воспроизведения **не повторял и не подтверждает**; в этом ADR используются
названия дефектов, соответствие этапам и требования ниже.
**На дату этого ADR ADR-015 не принят, ни один этап не влит, дефекты НЕ
исправлены; исправление не заявляется.**

> **Уточнение о текущем состоянии (2026-10-28, `main` = `2529964`).** Текст
> выше и ограничения ADR-016 не изменялись; статус остаётся `proposed`,
> реализация не авторизована. С момента ревизии 2 в `main` слиты исправления
> **H1** и **M1** (LOCK-FIX-001/LOCK-FIX-002). **H2 и M2 не исправлены**
> (этап 001C не выполнен), LOCK-RELEASE-001 открыт, ADR-015 не принят.
> **Гейт G-LOCK (§14.2) не пройден:** пункты 1, 2 (в части H2+M2) и 4
> не выполнены. Формулировка «ни один этап не влит» выше относится к дате
> ревизии 2 и сохранена как историческая.

| ID | Название (по директиве) | Этап ADR-015 (черновик) | На что опирается ADR-016 | Последствие, если не исправлено (вывод автора ADR-016) |
|---|---|---|---|---|
| H1 | mutual exclusion violation (директива: воспроизводимая потеря данных) | 001B (идентичность владельца) | два процесса в критической секции недопустимы между шагами 1 и 7; `replaceFile` не сравнивает ревизию (нет CAS), поэтому вторая публикация затирает первую | потерянное обновление: теряется подтверждённая мутация/чекпоинт; нарушается AC-21 и смысл I-SINGLE-COMMIT |
| H2 | hardlink wedge | 001C (hardlink-восстановление) | lock-файл и сегменты читаются политикой `nlink == 1`; лишняя ссылка делает файл нечитаемым | lock «застревает»; для сегмента — F19 |
| M1 | recovery livelock | 001A (deadline) | архивация удлиняет секцию и добавляет окна краха (F17); восстановление после падения должно сходиться | процесс не может ни получить lock, ни восстановить его |
| M2 | transient hardlink classification | 001C | шаг 6 читает только что опубликованный через `link()` сегмент | ложный отказ либо ложное принятие «переходного» состояния |

Черновик ADR-015 применяет классификацию `nlink` (`TRANSIENT | RESIDUAL |
STRUCTURAL`) к **lock-пути** через opt-in флаг общего читателя. Распространение
классификации на **сегменты** (F19) там не описано; ADR-016 своей классификации
не вводит и ждёт решения в рамках ADR-015 или его продолжения (RR-6).

Требования ADR-016 к lock (для авторов ADR-015; не заявление о его содержании):

- **R-LOCK-1** взаимное исключение держателей на интервале «шаг 1 … завершение
  публикации шага 7»;
- **R-LOCK-2** держатель, живой дольше обычного (секция с архивацией), не
  признаётся протухшим;
- **R-LOCK-3** восстановление после краха сходится и не может заклинить lock
  навсегда (M1, H2);
- **R-LOCK-4** единая, документированная классификация «переходная /
  постоянная лишняя ссылка» (M2), общая для lock и сегментов.

### 14.2 Гейт G-LOCK

Реализация STATE-003 **не начинается** (ни одна фаза, §15), пока не выполнено
всё из списка с приложенным доказательством:

1. ADR-015 принят (`accepted`) после независимого ревью;
2. этапы LOCK-FIX-001A…C (закрывают M1, H1, H2+M2) влиты в `main`; этап 001D
   (LOCK-RELEASE-001) желателен, но гейт не блокирует;
3. регрессионный тест воспроизводимой потери данных H1 (из SEC-RECOVERY-001)
   проходит на `main`;
4. повторная независимая проверка lock protocol (повтор SEC-RECOVERY-001)
   даёт заключение «закрыто» по H1, H2, M1, M2.

Путь «принять остаточный риск вместо гейта» ревизии 1 **снят**: он
противоречит директиве (потеря данных подтверждена) и в этом ADR не
предлагается. Отступление от гейта возможно только отдельным явным решением
владельца с новой ревизией этого ADR.

**Расхождения с черновиком ADR-015, требующие согласования владельцем** (ADR-015
не изменялся):

- ADR-015 Q4 допускает «оформить принятие остаточного риска (ADR-013 §7)» вместо
  зависимости ADR-016 P3 от этапов A–D, а ADR-015 §16 (R9) и §19 ссылаются на
  «ADR-016 P3» и «ADR-016 §12/Q2». В ревизии 2 ADR-016 гейт распространён на все
  фазы, путь риска снят, а блок зависимостей находится в §14 (ссылка устарела).
- ADR-015 ссылается на AC-26 ADR-016 как на бенчмарк-гейт задержки (больший cap
  backoff). В ревизии 2 AC-26 остаётся критерием выхода P3 и охватывает только
  критическую секцию архивации; задержку ожидания lock ADR-016 не измеряет.

## 16. Alternatives considered

- **A/B (хранение целиком в `state.json` с усечением; внешний индекс-файл):**
  отвергнуты — потеря данных либо два источника истины и два commit-а.
- **Автоудаление старых сегментов / ротация:** запрещено владельцем и
  STATE-001.
- **Режим деградированного чтения при повреждённом манифесте:** отвергнут —
  второй путь чтения; I-FAIL-CLOSED.
- **Адаптеры v1/v2 в обычном `readState`:** запрещены FORWARD-ONLY.
- **Широкий R-DEGRADE (ревизия 1: любой сбой сегмента):** отвергнут — скрывает
  security-нарушения, `UNKNOWN`, конфликты (§7).
- **Потолок числа миссий:** отвергнут (§11.3).
- **Замороженная копия старого валидатора для upgrade:** отвергнута (§13.2,
  п. 3–5).
- **Несколько сегментов за вызов:** отвергнуто (§3.5).

## 17. Consequences

Лучше: состояние ограничено по построению там, где пол это позволяет; 16 MiB
перестаёт быть тупиком для чекпоинтов; `UNKNOWN`-публикации не ломают историю;
dashboard не читает архив; сбой архивации не может ни потерять данные, ни
скрыть нарушение целостности.
Хуже: чтение полной истории миссии требует доступа к сегментам; критическая
секция при архивации длиннее (≤ 1 сегмент, не измерена); появляются новый
каталог `history/`, новая схема и новые коды ошибок; манифест и список миссий
растут без ограничения (RR-1, RR-2); тупик по миссиям не снимается этим ADR.

## 18. Acceptance criteria

Каждый критерий проверяется автоматическим тестом или явно названной ручной
проверкой. Нумерация сохранена; AC-31… добавлены в ревизии 2.

**Схема и инварианты**

- AC-01 Принимается только `schemaVersion: 3`; 1, 2, 4+ → `STATE_SCHEMA_UNSUPPORTED`. В `readState`/`mutateState` нет ветвей для старых схем (grep-тест).
- AC-02 `history` обязателен; отсутствие/неверная форма → `StateSchemaError`. `tactical.checkpoints` не принимается, `recentCheckpoints` обязателен.
- AC-03 I-PREFIX: негативные тесты — пропуск, перекрытие, диапазон не с 1, recent не непрерывен, разрыв между архивом и recent.
- AC-04 I-LAST: архивация никогда не удаляет последний чекпоинт (миссии всех статусов); архив без recent отвергается валидатором.
- AC-05 I-UNIQUE: дубль id между recent и `ranges` отвергается.
- AC-06 I-CONSERVATION: property-тест на случайных состояниях — множества и записи до/после архивации равны.
- AC-07 Манифест: порча каждого поля (`seq`, `file`, `sha256`, `bytes`, `ranges`, счётчики, `publishedAtRevision`) → чтение и запись отказывают, `state.json` не тронут; имя файла с разделителем пути отвергается.
- AC-08 Мутатор, изменивший `history`, → `HISTORY_MUTATION_FORBIDDEN`, запись не происходит.
- AC-31 Порча манифеста обнаруживается самим `validateState` (без `readState`, без fs): путь Dashboard Read Model.

**Архивация**

- AC-09 `S ≤ HIGH` → нет ни одной файловой операции с сегментами. Условие §6 выполнено → ровно один сегмент ≤ 2 MiB; итог ≤ LOW либо исчерпан сегмент; повторные мутации сходятся (состояние 14 MiB достигает ≤ LOW за конечное число вызовов); результат детерминирован (те же байты и имена при том же входе).
- AC-10 Уровень 1 (окно 20), затем уровень 2 (пол 1); меньше 1 на миссию не бывает; срез сохраняет префиксы по миссиям.
- AC-11 Нет кандидатов → публикация без сегментов, `STATE_ABOVE_HIGH_UNREDUCIBLE`. Кандидаты есть, `R < MIN_BATCH`, `S ≤ HARD` → ни одной операции с сегментами, без диагностики. `S > HARD`, `R > 0`, `R < MIN_BATCH` → архивация выполняется.
- AC-12 Каждый сегмент ≤ 2 MiB, содержит ≥ 1 запись; запись > лимита невозможна по валидации.
- AC-13 Сегменты: `createFile`, `0600`, durability `full`, существующий файл не перезаписывается; совпавший по sha принимается, иной → `ARCHIVE_SEGMENT_CONFLICT` → ABORT.
- AC-14 Провал проверки шага 6 → сегмент не в манифесте, ABORT (не DEGRADE); отдельный тест F19: сегмент с лишней ссылкой → `FILE_HARDLINKED` → ABORT, `state.json` не тронут.
- AC-15 Одна попытка за вызов: ≤ 1 публикация сегмента и ≤ 1 `replaceFile(state.json)` (счётчики); нет цикла.
- AC-35 Churn: на синтетическом состоянии с полом ≥ HIGH серия из N мутаций, создающих чекпоинты, порождает не более `⌈ΣΔ / MIN_BATCH⌉ + 1` сегментов (а не N); манифест не растёт по сегменту на мутацию.

**Сбои и R-DEGRADE**

- AC-16 Инъекция сбоя после записи сегмента и до `replaceFile` → `state.json` побайтно прежний, чтение работает, чекпоинты не потеряны (I-SINGLE-COMMIT).
- AC-17 `UNKNOWN` сегмента: без повтора, без `unlink`, мутация **отклонена** (ABORT), `state.json` побайтно прежний, в ошибке имя сегмента. `UNKNOWN` `state.json`: исключение, без повтора.
- AC-18 ENOSPC на сегменте → DEGRADE (результат побайтно равен мутации без архивации, кроме полей времени и `revision`; `history` не изменена; предупреждение `ARCHIVE_SKIPPED`); ENOSPC на `state.json` → `NOT_PUBLISHED`, исключение.
- AC-19 > 16 MiB → отказ, `NOT_PUBLISHED`, мутация не применена; ≥ 12 MiB → `STATE_NEAR_LIMIT`.
- AC-20 Kill дочернего процесса в точках F17 → `readState` успешен, I-CONSERVATION выполняется.
- AC-21 Многопроцессный тест с архивацией: нет потерянных обновлений и дублей id, общее число чекпоинтов сохранено. **Значим только при выполненном G-LOCK;** до него результат не интерпретируется как доказательство.
- AC-32 Классификатор: `Record<WriteErrorCode, …>` исчерпывающий (проверка типов); ровно одна комбинация (`WRITE_NO_SPACE`, `NOT_PUBLISHED`) → DEGRADE; все остальные коды, `UNKNOWN` и не-`SafeWriteError` → ABORT; старшинство: любая ABORT-находка побеждает DEGRADE (параметрический тест).
- AC-33 Fault-injection по каждой строке матрицы §7.3 (A1, B1–B8): на ABORT `state.json` побайтно прежний и мутация не применена; на DEGRADE — только строка A1.
- AC-34 DEGRADE при `S > HARD` без архивации → отказ `NOT_PUBLISHED`; при невалидном исходном состоянии/манифесте R-DEGRADE не достигается (F5).

**Чтение и история**

- AC-22 Подмена сегмента (изменённый байт, усечение, symlink, hardlink, FIFO, превышение размера) → типизированная ошибка с `seq`; `readState` работает.
- AC-23 `getCheckpoint` для архивного id; `listCheckpointHistory` равен списку до архивации (golden).
- AC-24 `selectDashboardSnapshot`: чистая, без fs (spy), детерминированная; `totalCheckpointCount` и `checkpointCount` включают архив; `archiveIntegrity` — литерал `'NOT_VERIFIED'`; в типе нет полей о файлах/сегментах; обычное обновление Dashboard не открывает ни одного файла в `history/`.
- AC-25 Тест архитектуры: код UI не обращается к `state.history`/`state.tactical` и не использует `listCheckpointHistory`.
- AC-26 **Бенчмарк-гейт (выход фазы P3):** на эталонной машине записать задержку записи при ≈ HIGH; критическую секцию архивации (а) одного сегмента ≈ 512 KiB, (б) одного сегмента 2 MiB при состоянии ≈ 14 MiB; (в) сценарий «пол ≥ HIGH» из AC-35; (г) чтение+валидацию состояния при 700 и 10 000 миссиях. Предлагаемый порог — p95 критической секции ≤ 50 % `timeoutMs` lock (2.5 с), иначе пересмотр констант/таймаута. Результаты фиксируются в истории, не как константы ADR.
- AC-27 `monolith history verify`: коды возврата, сироты, без lock, без записи.

**Лимиты миссии**

- AC-36 `title` ≤ 500, `system` ≤ 100, `summary` ≤ 4000 (после `trim`): граница принимается, +1 отвергается `ValidationError`; тип `summary` проверяется; состояние с полем больше лимита (устаревшее) читается и перезаписывается без усечения.

**Миграция и зачистка**

- AC-28 (если Q1 = данные могут существовать) `state upgrade`: фикстура v2 → v3 с сохранением; бэкап побайтно равен исходнику; повтор при существующем бэкапе отказывает; > 16 MiB отказывает; фикстура с неизвестным полем в миссии/чекпоинте/корне → отказ без записи; `--dry-run` ничего не пишет; при любом сбое исходный файл не тронут; на v3 — понятное сообщение.
- AC-29 Удалены `LEGACY_SCHEMA_VERSION_V1`, `migrateV1ToV2`-логика, тест с историческим кодом и тесты v1→v2 (вне `upgrade/`); шаблон `state.json` — v3; typecheck/build/тесты зелёные; обновлены AGENTS.md, индекс `docs/adr/README.md`, tech-debt (STATE-001), decisions.md.
- AC-30 Ни один документ или комментарий не заявляет поддержку TM-C.

**Процесс**

- AC-37 Перед началом P1 приложены доказательства по каждому пункту G-LOCK (§14.2); ручная проверка ревьюером. Ни один документ не утверждает, что H1/H2/M1/M2 исправлены, без ссылки на влитое исправление.

**Переход в `accepted`.** ADR переходит в `accepted` после независимого
архитектурного ревью (как ADR-013) и ответов владельца на Q1, Q4–Q9. Константы
§3 остаются предварительными до AC-26 и подтверждаются владельцем (Q3) на
выходе P3 — иначе возникала бы циркулярность «бенчмарк требует кода, код
требует `accepted`».

## 20. Open owner decisions

- **Q1** Существуют ли данные v2 (и v1) вне этого репозитория (другие экземпляры, машины, распространённые пакеты)? Определяет ветку A/B §13. **Q1b** Есть ли известный файл v1? (Если нет — команда v2 → v3 без v1.) **Q1c** Релиз, в котором команда `state upgrade` удаляется.
- **Q2** *Закрыт директивой:* гейт G-LOCK обязателен для всей реализации; принятие остаточного риска вместо гейта не предлагается. **Q2b** Согласовать с ADR-015 (его Q4 допускает путь риска; его ссылки на ADR-016 §12/Q2 устарели) — править ADR-015 вправе только владелец/его команда.
- **Q3** Утверждение констант §3 — на выходе P3 по результатам AC-26.
- **Q4** Лимиты полей миссии (значения 500/100/4000) и размещение: отдельная малая история до P3 (REC) или внутри P1.
- **Q5** `mission checkpoints <id>` по умолчанию показывает recent + «N в архиве», `--all` — всё.
- **Q6** «Актуальные миссии» = все миссии в `state.json` (допущение A-1); архивация миссий вне STATE-003 — нужен ли отдельный ADR и когда.
- **Q7** Язык ADR: русский (по директиве и ADR-010) или английский (как ADR-012…014).
- **Q8** R-DEGRADE-STRICT (REC) или R-NONE (любой сбой архивации — отказ).
- **Q9** Подтвердить уточнения алгоритма внутри C′: правило необходимости и `MIN_BATCH`, один сегмент за вызов.

## 21. Residual risks

| # | Риск | Статус |
|---|---|---|
| RR-1 | Пол (миссии + последние чекпоинты) может достичь 16 MiB; миссии не архивируются → тупик `STATE_FLOOR_EXCEEDED`. Лимиты полей (§11) ограничивают рост, но не снимают тупик | **Открыт**; решение — отдельный ADR об архивации миссий (не начат) |
