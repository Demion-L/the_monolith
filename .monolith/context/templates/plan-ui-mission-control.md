# Plan: MONOLITH Mission Control UI — архитектура и roadmap

**Статус:** PROPOSED. Это предложение, а не решение и не реализация.
**Дата:** 2026-10-22
**Режим:** planning (документация; ни одной строки runtime-кода)
**Ветка / worktree:** `feat/ui-000-mission-control-proposal` / `../the_monolith-ui-000`
**Связанный ADR:** [ADR-009](../../../docs/adr/ADR-009-mission-control-ui.md) (`proposed`)

> Что здесь НЕ утверждается: что UI будет построен, когда он будет построен,
> что он имеет приоритет над любой текущей работой, и что Reasoning Projector
> будет интегрирован. Всё ниже — материал для решения пользователя.

Все утверждения о текущем состоянии репозитория проверены чтением файлов в
worktree от коммита `938a308` (main). Там, где вывод сделан из чтения кода, а не
из запуска, это помечено **(вывод из кода, не проверено запуском)**.

---

## 1. Видение и границы

MONOLITH показывает, **где мы находимся**: фаза, миссия, чекпоинт, решения,
здоровье источников. Reasoning Projector (RP) отвечает на другой вопрос —
**как мы сюда пришли**. Направления совместимы по контрактам, но развиваются
независимо.

Инварианты, которые UI обязан сохранять:

1. **UI — не источник истины.** Любой факт на экране — проекция файла проекта
   (или результата Core над файлом). Кэш допустим только как пересобираемый.
2. **MVP read-only.** Ни одного пути записи из UI до UI-004.
3. **Core переиспользуется, не дублируется.** State Keeper читает состояние,
   Scriptorium разбирает markdown, ERG строит связи. UI-слой не парсит
   `state.json` и не разбирает frontmatter своим кодом.
4. **Неполнота видна.** Отсутствующий источник, битая ссылка, нераспознанный
   статус — это диагностика на экране, а не пустое место и не догадка.
5. **Не смешивать эпистемические статусы:** `PROPOSED` ≠ `DECIDED` ≠
   `IMPLEMENTED` ≠ `VERIFIED` (см. §3.3).

### 2.3 Актуальное vs историческое vs «Cognitive OS»

Это граница, которую UI обязан показывать, а не стирать.

- **Актуальное (рамка «toolkit», зафиксирована в `AGENTS.md` 2026-10-21):**
  Scriptorium, ERG, Coordinatorium (State Keeper, миссии, чекпоинты), `init`,
  `validate`, finalize-story и остальные skills, ADR-007, ADR-008,
  `docs/architecture/toolkit-pipeline.md`.
- **Наследие Cognitive OS (рамка «cognitive operating system», заменена toolkit
  2026-10-21, **документы сохранены**):** ADR-001 (Cognitive Loop), ADR-002
  (Cognitive Core), ADR-003 (Engineering Gate), `cognitive-core.md`,
  `engineering-gate.md`, `knowledge-lifecycle.md`, `story-lifecycle.md`,
  `knowledge-regions.md`, протоколы `cognitive-modes`, `semantic-planning`,
  `dry-run`, `hybrid-execution`, `local-llm-governance`. Часть из них
  (cognitive-modes, boot-sequence) **по-прежнему рабочие governance-контракты**,
  часть описывает концептуальный слой без runtime (`cognitive-core.md`:
  «conceptual future»; Engineering Gate: TD-005). Возраст документа не делает его
  ненужным; признак «актуален/исторический» UI должен брать из явного источника,
  а где его нет — показывать **UNKNOWN**.
- **Webway-наследие (извлечено в отдельный репозиторий 2026-10-21):**
  `docs/webway-v0.md`, `webway-dogfood-v0.*`, `webway-v1-research-plan.md`;
  **`hypotheses.md` озаглавлен «Product & Research Hypotheses — WEBWAY»** и описывает исследовательскую
  программу Webway, хотя лежит в MONOLITH и на него ссылаются ADR-001/002. Кому
  принадлежит этот файл сейчас — открытый вопрос (§9, Q3).
- **Исторические снимки:** `graph-dogfood-v1*.md` (метрики на дату), HANDOFF,
  капсулы историй.

### 2.4 Дрейф и двойственность источников (находки)

1. **ADR в двух деревьях** (`.monolith/adr` и `docs/adr`) + третья сводка в
   `decisions.md`. UI не должен выбирать «правильную» — показывать каждый
   ADR из его файла, а расхождение статусов сводки и файла — как диагностику.
2. **Гипотезы не являются адресуемыми документами.** `H7` в
   `related_hypotheses` — строка; в ERG ей не соответствует ни `id:`, ни alias
   (alias регистрируются только из `id:`/`title:` документа, ADR-007) **(вывод из
   кода, не проверено запуском)** → ожидаемо синтезированный узел-заглушка.
3. **Нет поля, различающего DECIDED / IMPLEMENTED / VERIFIED.** У ADR есть
   `status: accepted`; «Implementation status» у ADR-007 — абзац прозы.
4. **Evidence — не сущность.**
5. **SPHINX и CONTEXT-001B не определены в репозитории.** Поиск `sphinx` по
   tracked-файлам (кроме `node_modules`/`dist`) — пусто. `CONTEXT-001B` упомянут
   только в сообщении коммита `3a68109` в worktree CONTEXT-001A («Minimal
   Bootstrap», не реализован). Совместимость с ними оценить нельзя — см. §8, Q1.

## 3. Продуктовая область: Mission Control UI

Запуск: `monolith ui` (**команды сейчас нет**; это целевой интерфейс, а не факт).
Локальный web UI, без облака, аккаунтов и внешней БД. MVP read-only.

### 3.1 Экраны MVP

| Экран | Содержимое | Источник данных (через Core) | Известные пробелы |
|---|---|---|---|
| **Dashboard** | Current Phase; Active Mission; Mission Status; Last Checkpoint; Next Steps; Blockers; Project Health | `readState` (миссии, чекпоинты); `active.md`; `roadmap-index.md`; диагностики | **Blockers: нет такой сущности** (§3.2). **Current Phase** — проза в `active.md`/`roadmap-index.md`, не поле. **Next Steps** = `Checkpoint.remainingSteps` последнего чекпоинта активной миссии (явное поле) |
| **Mission Explorer** | активные/завершённые миссии, история чекпоинтов, remaining steps, provenance | `listMissions`, `listCheckpoints`, `getMission` | Strategic state отсутствует. Связь «миссия ↔ story/ADR» **не существует** (ADR-008: resume/linkage вне scope) — UI её не рисует |
| **Hypothesis Registry** | список, ID, статус, описание, evidence, связанные решения, поиск/фильтр | адаптер над `hypotheses.md` + обратный индекс `related_hypotheses` | §3.4 |
| **Knowledge Explorer** | ADR, Decisions, Protocols, Documentation; поиск; навигация по источникам | Scriptorium по корпусу (+ ERG для явных связей) | два дерева ADR; `decisions.md` вторичен |
| **Project Health** | ошибки валидации; отсутствующие источники; неразрешённые ссылки; потенциально устаревшие артефакты; диагностики | `validate` (структура), диагностики ERG/Scriptorium, диагностики чтения state | «устаревший» — только по явным признакам (§3.5) |

### 3.2 Blockers

Ни `Mission`, ни `Checkpoint` не имеют поля «blocker». `Checkpoint.context` —
свободный текст. UI **не извлекает** блокеры из текста. На Dashboard блок
«Blockers» в MVP показывает: `UNKNOWN — source field not defined`, плюс
фактические диагностические сигналы (миссия `failed`, нечитаемый state).
Введение настоящего поля — изменение схемы state и отдельная история Coordinatorium,
не часть UI.

### 3.3 Эпистемические статусы

UI показывает **сырое значение из источника** и его источник; нормализация
запрещена без отдельного решения.

| Отображаемый статус | Откуда может прийти | Что запрещено |
|---|---|---|
| PROPOSED | ADR `status: proposed`; явная пометка в документе | выводить из «нет ADR» |
| DECIDED | ADR `status: accepted` | считать это IMPLEMENTED |
| IMPLEMENTED | только явный машинно-читаемый сигнал (сегодня такого **нет**: у ADR-007 это абзац прозы) | выводить из наличия файла/теста в `src/` |
| VERIFIED | только артефакт проверки, привязанный к сущности (сегодня есть лишь проектный `integrity-result.md`) | переносить проектный PASS на отдельное решение |
| UNKNOWN | всё остальное | подставлять «вероятно» |

Если нужен сигнал IMPLEMENTED/VERIFIED на уровне сущности — это изменение
governance-схемы (новые поля frontmatter), отдельное решение вне UI.

### 3.4 Hypothesis Registry: что возможно без изменения схемы

Реестра как структуры нет. Вариант, не меняющий схем: **read-only адаптер**
строго по существующему шаблону — заголовок `^## H(\d+) — (.+)$`, строка
`^\*\*Status:\*\* \`(\w+)\``, разделы «Statement», «Current evidence»,
«Unknowns» — как **неструктурированные цитаты с provenance**. Всё, что не
распознано, — диагностика (`HYPOTHESIS_STATUS_UNPARSED` и т.п.), не
угадывание. «Связанные решения» — обратный индекс по явному
`related_hypotheses:` (ADR и memory-документы), что является **explicit
relation**. Evidence как список объектов — не строится (§2.2).

Альтернатива (отдельная история, **не** UI): ввести по-гипотезный
frontmatter-документ с `id: H1`. Это изменило бы governance-контракт и
ERG-идентичность; здесь только фиксируется как вариант.

### 3.5 Project Health: источники сигнала

Только то, что можно показать с provenance:

- ошибки/предупреждения `monolith validate`-подобных проверок структуры;
- диагностики ERG (`GraphDiagnostic`: alias collision, синтезированные
  узлы-заглушки, merged label variants);
- диагностики чтения state (отсутствует / пуст / нечитаем / legacy v1);
- неразрешённые `related_*` ссылки (значение есть, узла-документа нет);
- «потенциально устаревшее»: **только** по явным признакам — `supersedes` /
  `superseded_by` в цепочке, расхождение статуса `decisions.md` и ADR-файла,
  отчёты-снимки (`type: report`) старше текущей версии цепочки. Эвристики по
  `mtime` и «давно не менялось» не используются в MVP.

## 4. Архитектура

```
Browser UI                       (статические страницы, без записи)
    │  GET /api/v1/*   (только чтение, JSON, versioned)
Local HTTP API                   (127.0.0.1, foreground-процесс)
    │  вызывает функции чтения, не парсит файлы сам
MONOLITH Application Layer       (read model: проекции + provenance + диагностики)
    │
Core: State Keeper · Scriptorium · ERG
    │
Project Files                    (.monolith/state.json, *.md, monolith.config.json)
```

Добавляются два слоя, которых сегодня **нет**: Local HTTP API и Application
Layer. Все остальные — существующий код.

### 4.1 Application Layer (read model)

- Чистые функции «файлы → проекция», без состояния между запросами и без
  кэша в MVP (читать заново на каждый запрос — по образцу `monolith validate` и
  решению CONTEXT-001A; кэш = второй дрейфующий источник).
- Единая обёртка факта:
  `{ value, provenance: { source: <относительный путь>, kind: state | frontmatter | section | derived }, relation?: EXPLICIT | INFERRED | UNKNOWN }`.
  Номера строк не выдумываются (прецедент CONTEXT-001A).
- Единая обёртка ответа: `{ apiVersion, generatedAt, project, data, diagnostics[] }`.
- **Зависимость от CONTEXT-001A.** `collect()`/селекторы из `src/brief/`
  (миссии, последний чекпоинт, диагностики состояния STATE_ABSENT/EMPTY/UNREADABLE,
  чтение без побочных эффектов) — готовая проекция именно для Dashboard. Но этот
  код **находится в незамёрженной ветке** `feat/context-001a-brief` (2 коммита,
  340 тестов по описанию коммита). UI-001 не должен стартовать, пока пользователь
  не решил судьбу 001A (§8, условия; §9, Q2).

### 4.2 Local HTTP API (черновик контракта)

Только `GET`; любой другой метод → `405`. Ресурсы адресуются **ID сущности**, а
не путём файла.

| Эндпоинт | Этап | Содержимое |
|---|---|---|
| `/api/v1/meta` | UI-001 | версия API, корень проекта (имя, не абсолютный путь), `schemaVersion` state, доступность источников |
| `/api/v1/dashboard` | UI-001 | проекция Dashboard |
| `/api/v1/health` | UI-001 | список диагностик |
| `/api/v1/missions`, `/missions/{id}`, `/missions/{id}/checkpoints` | UI-002 | |
| `/api/v1/hypotheses`, `/hypotheses/{id}` | UI-002 | |

### 4.3 Безопасность localhost-API

Локальный сервер — всё равно сетевая поверхность. Документы проекта часто
пишет ИИ, значит, **содержимое файлов — недоверенный ввод**.

| Тема | Требование |
|---|---|
| **Bind** | только `127.0.0.1` (не `0.0.0.0`, не «localhost», который может резолвиться в `::1`/внешний интерфейс). Флага «слушать все интерфейсы» в MVP нет |
| **Порт** | по умолчанию свободный порт, выбранный системой, печатается в stdout; `--port` явный; при занятом — ошибка, не «следующий порт» молча |
| **DNS rebinding** | проверка заголовка `Host` по allowlist (`127.0.0.1:<port>`, `localhost:<port>`); иное → `403` |
| **CORS** | заголовки `Access-Control-*` **не отправляются** (same-origin only); запрос с чужим `Origin` → `403`. «Открыть API для других сайтов» — не требование |
| **Токен запуска** | одноразовый случайный токен в URL, печатаемом при старте, обязателен для `/api/*` (защита от других локальных процессов/страниц). Решение принять/отклонить — в ADR (Q6) |
| **Методы** | только `GET`/`HEAD`; записи нет вообще (структурно, а не флагом «readonly») |
| **Доступ к файлам** | API **не принимает пути**. Сервер строит индекс «ID → файл» из корня проекта и отдаёт только то, что в индексе |
| **Path traversal** | при чтении исходника: `realpath` корня проекта и `realpath` цели; цель обязана лежать внутри корня; `..`, абсолютные пути, NUL, перекодированные сегменты отклоняются |
| **Symlink** | symlink, ведущий за пределы корня проекта, не следуется; диагностика `SOURCE_OUTSIDE_PROJECT` (прецедент: `DOC_DIR_OUTSIDE_PROJECT` в CONTEXT-001A). Symlink внутри корня — допустим после `realpath`-проверки |
| **Лимиты** | whitelist расширений (`.md`, `.json`), верхний предел размера файла и числа файлов; превышение → диагностика, не падение |
| **XSS** | markdown рендерится **без сырого HTML**; ссылки — только `http(s)`/относительные; CSP `default-src 'self'` без inline-скриптов; `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer` |
| **Утечка путей** | в ответах только пути относительно корня проекта (как `monolith brief`) |
| **Жизненный цикл** | foreground-процесс; запуск `monolith ui`, остановка Ctrl+C; **никакого демона, pid-файла, автозапуска, фоновых задач**; допускается `--idle-timeout`; сервер не пишет файлов на диск (в т.ч. кэшей и блокировок) |
| **Несколько проектов** | один процесс = один корень проекта (cwd или `--project`); имя проекта и порт видны в шапке UI; переключения проектов и реестра проектов в MVP нет; два проекта = два процесса на разных портах |

### 4.4 Сравнение вариантов реализации

Ограничения репозитория: Node ≥ 20, TypeScript strict ESM, **у пакета нет
runtime-зависимостей** (только devDependencies), `dist/` закоммичен (TD-003).

| Вариант | Суть | + | − | Вывод |
|---|---|---|---|---|
| **A. `node:http` + статический клиент без сборки** (HTML + ES-модули + SVG/Canvas вручную) | сервер на stdlib; клиент отдаётся как готовые файлы | 0 runtime-зависимостей; нет build-цепочки клиента; малая атака; предсказуемая раздача `dist/` | больше ручного кода UI; для графа (UI-003) layout придётся писать или подключать библиотеку | **Рекомендуемый кандидат для UI-001/002** |
| **B. `node:http` + лёгкий клиентский фреймворк с бандлингом** (Preact/Vite и т.п.) | | удобные компоненты | появляются build-зависимость и (dev)dependencies; `dist/` разрастается | рассмотреть, если A окажется неудобным; требует явного одобрения зависимостей |
| **C. Полный фреймворк с dev-сервером** (Next и т.п.) | | богатая экосистема | тяжёлая цепочка; dev-сервер ≠ то, что мы поставляем; противоречит «без демона/без зависимостей» | не рекомендуется |
| **D. Статический экспорт** (`monolith ui --export <dir>` → JSON + HTML, без сервера) | | нулевая сетевая поверхность; удобно для шаринга снимка | не живой; снимок устаревает; дублирует данные в файлах | **дополнение**, не замена; хорошо для CI/отчёта |

Выбор стека — не решение этого документа (см. ADR-009, открытые вопросы).
Критерий выбора: минимум зависимостей и поверхности, а не популярность.

## 6. ERG Graph View

### 6.1 Режимы

| Режим | Что показывает | Ограничение |
|---|---|---|
| **GLOBAL** | подтверждённые сущности и **только явные** связи | см. §6.2 — на сегодняшнем ERG граф будет в основном из изолированных узлов |
| **LOCAL** | выбранная сущность и непосредственные соседи (in/out по явным рёбрам) | глубина 1 в MVP |
| **IMPACT** | «кто явно ссылается на выбранный узел» (обратный обход явных рёбер), с подписью «**declared dependents**» | по построению неполон: не «всё, что сломается» |

### 6.2 Что ERG реально содержит (проверено по коду и dogfood-отчётам)

1. **Узлы ERG — концепты, а не документы.** Pass 1 строит узел на каждую
   нормализованную метку заголовка/пункта списка (`src/graph/builder.ts`).
   Отчёт v1.2: 389 «реальных» узлов на 74 документа; ~86% концептов — заголовки.
   Документ — лишь основной узел (H1) плюс alias из `id:`/`title:`.
2. **Идентичность = нормализованная метка.** Одинаковые заголовки в разных
   документах **сливаются в один узел** (диагностика `info: Merged N label
   variants`, `sourceArtifacts` содержит несколько файлов). Это коллизия
   заголовков, а не «один и тот же концепт» — различить нельзя.
3. **Рёбра только explicit** (`GraphEdge.provenance: 'explicit'` — единственное
   значение в типе). Всего 16 рёбер в v1.2 (5 `related_adrs`, 4
   `related_protocols`, 4 `protocols`, 3 `referenced_by`); в `AGENTS.md` —
   «32 explicit edges / 481 nodes»; TD-001: разреженность известна и принята.
4. **Alias-хрупкость** (TD-002): переименование `id:` молча рвёт рёбра.
   Коллизии alias — «побеждает первый документ» + диагностика (ADR-007).
5. **Синтезированные узлы-заглушки** (`synthesized: true`) для целей, не
   найденных среди узлов/alias — например, ссылки на выведенные ADR-004/005.
6. **Типы связей не нормализованы по направлению:** `referenced_by` — обратная
   сторона `related_*`/`protocols`; ERG их не объединяет. UI не должен
   «додумывать» симметрию.
7. **Подавляющее большинство узлов — orphan.** Это следствие разреженности,
   а не свойство проекта.

### 6.3 Классы связей

| Класс | Определение | В MVP |
|---|---|---|
| **EXPLICIT** | ребро `GraphEdge` из frontmatter-поля (есть `sourceArtifactId`, `evidenceIds`) | **да, только это** |
| **INFERRED** | вывод из текста, сходства, совместной встречаемости | **нет**; в модели не существует; не добавлять |
| **UNKNOWN** | связи нет в данных | отображается как «связь не объявлена»; **никогда** как «зависимости нет» |

Orphan-узел подписывается «нет объявленных связей», не «изолирован».

### 6.4 Входные критерии UI-003 (проверить ДО визуализации)

1. **Identity model:** принять, что узел = концепт; выбрать, показывать ли
   пользователю граф концептов, граф документов (проекция до primary-узлов с
   `documentId`) или оба. Проекция — это представление над существующим ERG,
   не новый engine; но если для неё нужно менять Core — это отдельная история.
2. **Стабильность ID:** узел-слаг меняется при правке заголовка; `id:` документа
   стабилен, но его смена рвёт alias (TD-002). Зафиксировать, какой ID уходит в
   URL экрана.
3. **Дедупликация/коллизии:** перечислить в корпусе узлы с `sourceArtifacts.length > 1`
   и решить, показывать ли их как «объединённый концепт (N источников)».
4. **Provenance:** каждое ребро в UI несёт `sourceArtifactId`, тип поля, `evidenceIds`.
5. **Корректность связей:** прогнать построение ERG по текущему корпусу и
   составить список `related_*`, не разрешившихся в документ (в т.ч. `H1…H8`,
   `ADR-004/005/006`, `KR-n`); неразрешённое показывать как диагностику, не как узел.
6. **Orphans:** политика отображения (скрыты по умолчанию, счётчик, фильтр).
7. **Масштаб:** при ~500 узлах и ~30 рёбрах силовая раскладка бессмысленна;
   оценить необходимость библиотеки (новая зависимость — отдельное одобрение).
8. **Направление/типы:** не нормализовать `referenced_by` ↔ `related_*` без решения.

Новый ERG engine **не** создаётся. Если плотность связей недостаточна для
полезного графа — это сигнал в сторону «Corpus relationship density»
(уже кандидат в `roadmap-index.md`), а не повод строить вывод связей в UI.

## 7. Reasoning Projector (перспектива, не к реализации)

### 7.1 Что известно о RP (читалось только `README.md` и `git log` соседнего репозитория)

`../reasoning-projector` — самостоятельный проект: «Decision Intelligence
System, который восстанавливает утерянное инженерное обоснование из связанных
артефактов (инциденты, ADR, расследования, фиксы, PR)»; стек Next.js + Gradio;
в истории есть коммит «add reasoning-projector/v1 schema adapter for RP dataset
imports». Глубже его устройство в этой работе **не исследовалось**.

### 7.2 Принципы интеграции

- RP — самостоятельный проект с собственным релизным циклом; MONOLITH **не
  зависит** от него (ни импорта, ни обязательной установки, ни сетевых вызовов).
- Интеграция — **через отдельный адаптер**, направление зависимости:
  адаптер → контракт MONOLITH, а не MONOLITH → RP.
- Предпочтительная форма: MONOLITH публикует **read-only экспорт артефактов**
  (версионируемый JSON: артефакты, явные связи, provenance, ссылки на git-коммиты),
  RP (или адаптер в репозитории RP) его потребляет. Формат экспорта — тот же
  контракт, что и для статического экспорта UI (вариант D), чтобы не плодить схем.
- Встраивание в UI (iframe/виджет) не планируется; допустим deep-link
  «открыть в Reasoning Projector» при наличии адаптера.
- **Только наблюдаемое:** артефакты, события, история Git, evidence. Никакой
  реконструкции скрытых рассуждений модели. Всё неизвестное — `UNKNOWN`;
  каждое утверждение — с provenance.
- Цепочка `Hypothesis → Evidence → Decision → ADR → Implementation →
  Verification` — **пример**, не обязательная схема. Сегодня звенья
  Evidence и Verification не имеют сущностей (§2.2), Implementation — только
  через git/тесты.

### 7.3 Перспективные функции (не обещания)

| Функция | Какой вопрос закрывает | Наблюдаемая основа | Что мешает сегодня |
|---|---|---|---|
| Decision Timeline | как решение менялось во времени | git-история файла ADR, `supersedes`, даты в frontmatter/таблицах | нет единого поля даты у всех сущностей |
| Project Evolution Explorer | как проект эволюционировал | `execution-history.md`, капсулы, коммиты со story-ID в `type(SCOPE):` | story-ID — в сообщениях/прозе, не в схеме |
| Reasoning Debt Detection | где обоснование неполно | наличие разделов «Alternatives Considered»/«Rationale» в ADR (есть в шаблоне ADR); `accepted` ADR без `research`/ссылок | нужна согласованная трактовка «долга» — работа RP, не MONOLITH |
| Historical Graph | как менялась сеть связей | ERG на разных коммитах | ERG строится на момент; версия в истории — отдельная работа |
| Why Did We Do This? | почему принято решение | цепочка явных связей + цитаты из ADR | см. выше; пробелы обязаны показываться как `UNKNOWN` |

  часть MVP.

### UI-005 — Reasoning Projector Integration

- **Цель:** опциональный адаптер к RP (§7).
- **Зависимости:** контракт экспорта (из UI-001/D); готовность RP; решение
  владельца RP.
- **Deliverables:** версионируемый экспорт артефактов+связей+provenance; адаптер
  (скорее всего в репозитории RP); deep-link из UI.
- **Acceptance:** MONOLITH собирается и работает без RP; нет сетевых вызовов к
  RP из ядра; неизвестное = `UNKNOWN`; ни одного утверждения без provenance;
  нет реконструкции скрытых рассуждений.
- **Риски:** размывание границ проектов; контракт экспорта становится
  публичным API; ожидание «объяснения» там, где данных нет.
- **Сложность:** L–XL (в основном на стороне RP).
- **Условие начала:** отдельное решение; **не запланировано к немедленной
  реализации**.
