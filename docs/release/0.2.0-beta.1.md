# MONOLITH `0.2.0-beta.1` — Release Notes

**Status:** **PUBLISHED** — beta. MONOLITH is experimental and
**not a stable production release**. The CLI and API may change without notice.

| | |
| --- | --- |
| Package | `@latysh-development/monolith` |
| Version | `0.2.0-beta.1` |
| npm dist-tag | `beta` (`latest` is unchanged) |

| Release commit | `47d9a6c` |

Install from the `beta` dist-tag:

```bash
npm install -g @latysh-development/monolith@beta
```

Changes are relative to `v0.1.0-alpha.4`. Requires Node.js >= 20.

## Highlights

- **Durable State** — long-running task logs (`monolith durable ...`) and shared
  operational state kept in the git common directory (schema v3,
  `monolith state status | adopt`).
- **Coordinatorium** — missions and checkpoints (`monolith mission ...`).
- **Finalize workflow** — `monolith finalize plan` (read-only, with a deterministic
  digest) → owner approval → `monolith finalize apply --approve <digest>`. A stale or
  wrong digest is refused and nothing is written; a repeated plan or apply reports
  `ALREADY_FINALIZED`. Longer phase identifiers are supported.
- **Governance Read Model** — structured story index and phase relationships;
  `roadmap-index.md` (`Current Focus`) is the sole source of the active phase.
  The Dashboard exposes `storyIndex` and `storyState`.
- **Mission Control** (`monolith ui`) — a read-only web dashboard on `127.0.0.1`:
  Project Overview, Checkpoints, Roadmap Navigator (search, sort, paging, current-phase
  jump), Execution Graph, Hypotheses, Architecture Decisions (search, pagination) and
  Diagnostics, where validation and reconciliation can be run on demand.
- **Project Execution Graph** — built from the roadmap and the story index; a link is
  drawn only where the story index confirms that a story belongs to a roadmap phase.
- **Single Canonical Skills** — each skill template has one canonical source
  (`check:skills`). The `finalize-story` skill now includes the
  `Current Operational Focus` check.

## Backward compatibility

- `monolith update` is a preview by default; `--apply` performs it. Text of yours
  outside MONOLITH-managed blocks is never overwritten.
- A `finalize-story` skill that is byte-identical to a known older template
  (including the `0.1.0-alpha.0`–`alpha.2` and earlier `beta.1` development
  templates) is replaced by the current one. A skill you edited is kept, reported as
  `CONFLICT`, and `update --apply` exits with code 2 until you reconcile it.
- A custom `monolithRoot` is honoured by `update`; repeated runs are idempotent.

## Known limitations

- **Mobile viewport not verified.** Mission Control was not checked at a 390 px
  viewport. Desktop use is the verified path.
- **Governance consistency is structural.** `finalize` and `brief` check structural
  agreement between `active.md`, `roadmap-index.md` and `story-index.md`, and that the
  integrity/governance evidence files name the story, carry a recent date and say
  `PASS`. They do not read prose, and they do not guarantee semantic consistency of
  arbitrary documentation. Evidence files are the assistant's own attestation; MONOLITH
  does not execute those steps. The owner's approval of the plan digest remains the
  judgement of whether the content is true.
- **`Current Operational Focus` is not updated automatically.** `finalize apply`
  preserves that section of `active.md` byte for byte. Reviewing it is an
  instruction-level step of the `finalize-story` skill for the assistant, not enforced
  by the CLI. `finalize` also does not update `Current Focus` in `roadmap-index.md`.
- **Story Resolver and legacy consistency differ (D1–D5).** The Story State Resolver
  used by Mission Control and the legacy consistency check used by `brief` and
  `finalize` deliberately differ (pinned by differential tests): (D1) duplicate
  entries — legacy is first-wins and silent, the resolver reports a conflict;
  (D2) lowercase status — legacy ignores it, the resolver normalises it; (D3) scope —
  legacy compares the status strings of every id, the resolver judges lifecycle facts
  per story; (D4) conflicting phase references are reported only by the resolver;
  (D5) the public `brief` / `finalize` messages remain the legacy ones.
- **Not implemented:** `monolith status`, `monolith dry-run` (both exit 1), a
  write-enabled UI, authentication for Mission Control.
- **Mission Control** listens on `127.0.0.1` only, has no authentication and is
  read-only. Concurrent adversarial mutation of a project is unsupported; Windows is
  unverified. See [Security & Limitations](../reference/security-and-limitations.md).
- **Durable State and the Coordinatorium** are experimental.
- **Node.js:** `engines` is `>=20`. The release was verified on Node.js 24.19 (full
  test suites, build) and, from a locally built tarball, on Node.js 20.20.2
  (`--version`, `--help`, `init`, `validate`, `brief`, `finalize plan`/`apply`,
  `update`). Remote CI runs the full test suites on Node.js 22; they were not run on
  Node.js 20.
- A fresh project's `brief` reports Freshness `UNKNOWN` until state is recorded in git.

## Install and verify

A locally built tarball (`npm pack`) installs without the source repository: the
package ships `dist/` (including `dist/ui`) and `templates/` and has no runtime
dependencies. Typical first steps in a project directory: `monolith init`,
`monolith validate`, `monolith brief`; for an existing instance, `monolith update`
(preview) and `monolith update --apply`.
