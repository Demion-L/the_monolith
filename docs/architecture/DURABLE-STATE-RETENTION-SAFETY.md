# Durable State & Retention: Safety Invariants and Failure Model

**Статус: спецификация для независимого аудита. Не одобрена.** Документ описывает то, что реализовано в
`src/durable/` на ветке `feat/durable-state-001`, и то, что **проверено тестами**. Он не обещает ничего сверх
этого. Где гарантии нет, стоит `NOT GUARANTEED`; где проверка частична — `PARTIALLY_VERIFIED`.

Это не обзор event sourcing. Решения и их мотивы — в ADR-017; здесь — условия, при которых утверждения верны,
механизмы, сценарии нарушения и тесты, которыми аудитор может это перепроверить.

Обозначения. `FS` — `FsEventStore`; `MEM` — `MemoryEventStore`; «процесс» — независимый OS-процесс на одной машине.
Ссылки на код — по именам функций (номера строк меняются).

## 9.1 Scope & Assumptions

### Область

* **Одна машина, несколько независимых процессов**, общий каталог хранилища на **локальной POSIX-файловой системе**
  (проверялось на Linux). Процессы не знают друг о друге; координация только через файлы хранилища.
* Без консенсуса, без внешних блокировок, без лидера. Единственный линеаризуемый примитив — «создать файл, если его
  нет» (`createFile`: временный файл → fsync → `link()`; ADR-012). Всё остальное построено над ним.

### Поддерживаемые аварии

| Авария | Поддерживается |
|---|---|
| SIGKILL / crash процесса в любой точке | да (тесты, см. 9.5) |
| SIGSTOP/SIGCONT (процесс «замёрз» и вернулся) | да |
| Частичная запись, прерванный `link()`/`unlink` | да, в пределах описанных состояний |
| `ENOSPC`/`EIO` на записи | да как **отказ** (`StoreIoError`, ничего не опубликовано); проверено инъекцией ошибок |
| Прерванные compact / prune | да, достраиваются |
| Параллельные восстановители | да |

### Не поддерживается (явно)

* **Потеря питания / kernel panic с потерей page cache** — долговечность **не заявлена** (см. ниже и 9.5).
* **Общая ФС между хостами** (NFS, SMB, FUSE-сети): атомарность `link()` и видимость записей не гарантированы.
* **Намеренная подмена данных** писателем, имеющим доступ к каталогу (TM-C), и подмена/усечение журнала согласованной
  цепочкой — хеш-цепочка не аутентифицирует (ADR-017 §2.6).
* Повреждение ФС / носителя: обнаруживается проверкой цепочки и схемы (`LogCorruptError`), **не чинится**.
* Windows/macOS, регистронезависимые ФС.
* Скачки и расхождение часов — см. ниже: влияют только на живость.

### Допущения об атомарности и видимости

| # | Допущение | На что опирается |
|---|---|---|
| A1 | `link(2)` атомарно создаёт имя или возвращает `EEXIST` | `append`, `createFile` (событие, tombstone, pin, сегмент) |
| A2 | После возврата из `link`/`unlink`/`rename` результат виден другим процессам этой машины | все протоколы «второй маркер видит первый» (pin ↔ tombstone) |
| A3 | `unlink` одного имени атомарен | откат tombstone, удаление данных |
| A4 | Чтение каталога + файла не атомарно; читатель повторяет попытки (`READ_ATTEMPTS`) и, не сойдясь, отказывает типизированной ошибкой | компакция против читателя |
| A5 | Порядок «записал A, затем B» из **одного** процесса виден другим процессам в том же порядке | Dekker-схема pin/tombstone; доказательства нет, опирается на семантику POSIX для одной машины |

**Нет линеаризуемости между задачами.** Порядок гарантирован только внутри журнала одной задачи (`seq`). Глобального
порядка событий разных задач нет и не имитируется (9.6).

### Долговечность (fsync)

В коде при `durability: 'full'` (по умолчанию) событие, tombstone, pin и сегмент создаются через `createFile`:
fsync файла, затем `link`, затем fsync каталога (ошибка fsync каталога — предупреждение `onWarning`, достигнутая
долговечность `unknown`; ошибка fsync файла — отказ, не повторяется). `durability: 'file'` — только файл.

**Что НЕ проверено.** Тестов с реальной потерей питания / `dm-flash`/`dm-log-writes` нет. Поэтому: (а) утверждение
«опубликованное событие пережило сбой питания» **не заявляется**; (б) `unlink` при удалении данных prune и при откате
tombstone не сопровождается обязательным fsync каталога (откат вызывает `fsyncDir` «по возможности»; удаление данных —
нет). После потери питания удалённые файлы могут вернуться, а отозванный tombstone — появиться снова. Оба исхода
остаются в классе описанных состояний (9.2), но поведение после них **не тестировалось**. См. R-7.

## 9.2 State Model

Для каждого элемента: P — хранится на диске; D — вычисляется; T — переходы; C — критические операции; R — восстановление.

### Task lifecycle

* **P:** файлы `tasks/<id>/events/<seq,9>.json` и/или `segments/S<from>-<to>.jsonl`; `tombstone.json`; `refs/<child>.json`.
* **D:** `TaskState` = свёртка журнала (`foldEvents`); `status ∈ {active, completed, failed, cancelled}`; в памяти есть
  кэш, который отбрасывается при расхождении с журналом.
* **T:** `active → completed | failed | cancelled` (терминальные необратимы). Из терминального статуса — только
  `pruned` (tombstone). Из `active` в `pruned` перехода нет.
* **C:** публикация `task.created` (seq 1), терминальное событие.
* **R:** состояние всегда пересчитывается из журнала; отдельных «состояний восстановления» у задачи нет.

### Event log

* **P:** цепочка событий формата v1: `seq`, `prev`, `hash` = SHA-256 канонического JSON, `taskId` входит в хеш.
* **D:** корректность цепочки проверяет читатель (`verifyChain`), не хранилище.
* **T:** только добавление в слот `seq = head+1`; существующие события не меняются (сегмент — упаковка, не правка).
* **C:** `link()` слота.
* **R:** `AppendOutcomeUnknownError` разрешается перечитыванием: событие с тем же хешом = записано. Дубль-имя `nlink==2`
  с `.tmp.<pid>` ремонтируется читателем; любое другое — `StoreSecurityError`.

### Projection

* **P:** нет. **D:** `TaskState`, `Assessment`, `ResumePacket` — чистые функции журнала (+ `now`, `observations`).
* **T/C:** нет записи. Исключение — карантин и откат prune при обнаружении (см. N-7 в 9.9).
* **R:** пересчёт.

### Lease

* **P:** события `run.claimed {owner, epoch, leaseUntil}`, `run.heartbeat`, `run.released`.
* **D:** «жив ли lease» = `leaseUntil > now` **по часам читающего процесса** (RR-1).
* **T:** свободен → занят (claim); занят → перехвачен после истечения (takeover) → освобождён.
* **C:** `run.claimed` как CAS по `seq`.
* **R:** истёкший lease можно перехватить без участия прежнего владельца.

### Fence

* **P:** нет отдельного; `Fence{taskId, owner, epoch}` — значение у воркера, подтверждается журналом.
* **D:** fence валиден, если журнал показывает того же `owner` и `epoch` как текущих **в момент CAS записи**.
* **T:** выдаётся только `claim`; становится устаревшим при следующем `claim` (epoch+1).
* **C:** проверка при каждой записи воркера.
* **R:** устаревший воркер получает `StaleFenceError`. Внешние эффекты fence не отзывает (INV-005).

### External effect intent

* **P:** `effect.intended` → `effect.completed | effect.failed {retryable, uncertain?}`.
* **D:** состояние эффекта по ключу; «под вопросом» = `intended` без исхода или `uncertain`.
* **T:** `intended → completed | failed`. Из «под вопросом» выход — только `reconcile` (`completed` / `not-executed`) или оператор.
* **C:** публикация `effect.intended` (CAS по `status@intendedAtSeq`) **до** вызова `fn`.
* **R:** другой владелец видит неоконченный эффект как «под вопросом» и `fn` не запускает.

### Parent/child references

* **P:** поля `parentTaskId`, `dependsOn` в `task.created` (неизменяемы); pin `refs/<child>.json` у родителя.
* **D:** состояние ссылки (логическая модель, на диске не хранится):

| Состояние | Определение | Решающий признак |
|---|---|---|
| `LIVE` | задача существует, tombstone нет | `readLog`: нет tombstone |
| `PRUNE_PENDING` | tombstone есть, данные целы (удаление не начато) или их нельзя исследовать сейчас | `PRUNE_INCOMPLETE` + `withdrawTombstone` успешен либо недоступен |
| `GONE` | задачи не было, либо удаление данных начато/завершено | нет `PRUNE_INCOMPLETE`, либо `TombstoneCommittedError` |

* **T:** `LIVE → PRUNE_PENDING` (публикация tombstone); `PRUNE_PENDING → LIVE` (откат) **или** `PRUNE_PENDING → GONE`
  (начато удаление данных). `GONE` терминально. `LIVE → GONE` напрямую не бывает.
* **C:** публикация pin и tombstone; удаление первого файла данных (точка невозврата prune).
* **R:** см. Tombstone / Prune.

### Tombstone

* **P:** `tombstone.json` (create-only), содержит `headSeq`, `headHash`, итоговый статус, `outcomeDigest`.
* **D:** сам по себе не доказывает ни «удалено», ни «будет удалено» (N-6).
* **T:** создан → (отозван | остаётся навсегда после удаления данных).
* **C:** `markPruned`, `withdrawTombstone`.
* **R:** повторный `markPruned` с тем же `headHash` идемпотентен; с другим — `LogCorruptError`.

### Prune

Шаги: (1) проверка «терминальна, старше срока, нет активных ссылающихся»; (2) `markPruned` (tombstone);
(3) повторный просмотр ссылающихся (опубликованные задачи + pin'ы в пределах `referenceGraceMs`); (4а) есть ссылающаяся
→ `withdrawTombstone` + `RetentionRefusedError`; (4б) нет → удаление `events/`, `segments/`, `refs/`.
Точка невозврата — удаление первого файла данных (дальше откат отказывает).

Состояния на диске и что с ними делают:

| Состояние | Логическое | Кто выводит из него |
|---|---|---|
| нет tombstone | LIVE | — |
| tombstone, данные целы | PENDING | ссылающийся (откат) · `pruneTask` (откат или доделывание) |
| tombstone, данные частично удалены | GONE | `pruneTask`/`applyRetention` (доделывание) |
| tombstone, данных нет | GONE | — |

#### Предусловие необратимого prune на границе стора (DURABLE-SECURITY-FIX-001, F-1)

Публичные `preparePrune`, `markPruned`, `decidePrune(commit)` и `prune` стора (`FsEventStore`, `MemoryEventStore`) сами проверяют журнал и
не полагаются на то, что вызывающий его проверил: журнал верифицируется (цепочка хэшей), задача **терминальна**, и tombstone совпадает с
журналом — `headSeq`, `headHash`, `finalStatus`, `kind`, `createdAt`, `closedAt`, `outcomeDigest` (`prunedAt` — часы pruner'а, не
сравнивается). Нарушение ⇒ `RetentionRefusedError` (нечитаемый/повреждённый журнал ⇒ `LogCorruptError`); отказ **ничего не меняет на диске**.

Корректность при конкуренции (без check-then-act): проверка выполняется **после** того, как `prepare` виден в реестре, а не до.
Любой `append`, опубликованный позже, проходит G2, находит открытую попытку и закрывает её `abort`; `commit` и `abort` одной попытки
взаимоисключающи (ADR-019, first-decision-wins). Поэтому подтверждённая голова не может измениться между проверкой и `commit`. Ранняя
проверка до публикации `prepare` — только отказ без следов; авторитетна проверка после. Уже принятое решение реестра возвращается как есть,
без повторной проверки (идемпотентность, дозавершение после SIGKILL). `rollForward` уже закоммиченного prune не перепроверяет журнал:
после `commit` данные удаляются в любом случае.

Границы: проверка защищает от неверных аргументов и неверного состояния на публичном API. Она не защищает от процесса, пишущего в каталог
напрямую (ADR-018 D1: внешнее вмешательство исключено), и не расширяет Mode A. Seam `skipPrunePrecondition` существует только в
внутреннем тестовом модуле (`testing.ts`) для тестов самого протокола реестра и недоступен через публичный конструктор и точку входа пакета.

### Compact

* **P:** `segments/S<from>-<to>.jsonl` (create-only, перечитывается и сверяется побайтно), затем удаление loose-файлов.
* **T:** loose → loose+segment → segment. Каждый префикс шагов — согласованное состояние (сегмент авторитетен).
* **C:** `link()` сегмента (commit); удаление loose — необязательная чистка.
* **R:** `compact()`/`applyRetention` вызывают `sweepCompacted`: удаляется только байт-в-байт равный файл.

### Recovery

Отдельного процесса восстановления нет. Восстановление — свойство обычных операций:
чтение (ремонт `nlink==2`, повтор при исчезнувших файлах), `claim`/`findResumable` (откат prune, карантин GONE),
`compact`/`pruneTask`/`applyRetention` (достройка), `resolveUnknown` (неизвестный исход публикации).

## 9.3 Safety Invariants

Статусы: `GUARANTEED` (при перечисленных допущениях, проверено), `GUARANTEED_UNDER_ASSUMPTIONS` (требует условия,
которое хранилище само не обеспечивает), `NOT GUARANTEED`.

### INV-001: Event Log Integrity

```
ID:            INV-001
Название:      Event Log Integrity
Условие:       для любой задачи t и любого успешного чтения: события 1..n образуют цепочку
               e[i].prev = e[i-1].hash, e[i].seq = i, e[i].hash = H(canon(e[i] без hash)), e[i].taskId = t;
               иначе чтение завершается ошибкой (LogCorruptError / LogUnsupportedError), а не усечённым результатом.
Предположения: A1, A4; случайное, не враждебное повреждение.
Механизм:      verifyChain при каждом чтении; create-only публикация; строгий читатель (ADR-014); читатель, не сошедшийся
               за READ_ATTEMPTS, бросает ошибку, а не короче журнал.
Нарушение:     умышленная подмена с пересчётом хешей; усечение хвоста (валидный префикс); подмена всего журнала.
               NOT GUARANTEED против этих трёх случаев (ADR-017 §2.6).
Тесты:         fs-store.fault.test.ts («hostile or damaged directories fail closed»), store-conformance.test.ts,
               property.test.ts.
Остаточный риск: tamper-evidence отсутствует; нужен внешний якорь (не реализован).
Статус:        GUARANTEED (случайное повреждение); NOT GUARANTEED (враждебное).
```

### INV-002: Deterministic Recovery

```
ID:            INV-002
Название:      Deterministic Recovery
Условие:       состояние задачи = foldEvents(журнал), независимо от того, какой процесс, когда и в каком порядке читал;
               инкрементальное состояние (кэш + суффикс) = свёртка с нуля = свёртка префиксов.
               assess(state, events, now, observations) — чистая функция.
Предположения: INV-001.
Механизм:      единственный источник — журнал; кэш отбрасывается при несовпадении префикса (refresh, pass 0).
Нарушение:     assess зависит от now и от observations вызывающего (часы → AWAIT_EXPIRED, истечение lease): два процесса
               могут получить разные Assessment для одного журнала. Для TaskState — не нарушается.
               Расширение (DURABLE-FIX-003): withRequirements читает СОСТОЯНИЕ ДРУГИХ задач, то есть результат
               claim/findResumable зависит не только от журнала данной задачи (см. 9.6).
Тесты:         property.test.ts (150 seeds MEM, 25 seeds FS), runtime.test.ts, projection-keys.test.ts.
Остаточный риск: Assessment недетерминирован по времени и по состоянию требуемых задач — по замыслу.
Статус:        GUARANTEED (TaskState); определено, но не «детерминировано» для Assessment.
```

### INV-003: Exclusive Claim Ownership

```
ID:            INV-003
Название:      Exclusive Claim Ownership
Условие:       для задачи t и seq s не более одного run.claimed занимает слот s; epoch строго возрастает;
               пока lease виден как живой, claim другим владельцем отказывает (LeaseHeldError).
Предположения: A1; часы процессов не расходятся сильнее lease-интервала (RR-1).
Механизм:      CAS по seq (append в слот head+1); epoch = prev.epoch+1.
Нарушение:     скачок часов делает живой lease «истёкшим» → перехват при живом прежнем воркере. Журнал при этом
               остаётся корректным (INV-004), но прежний воркер может уже выполнять внешний эффект (INV-005).
Тесты:         process.test.ts («8 processes racing to claim one task: exactly one wins»), pending-prune.process.test.ts
               (TEST-4: claim одной задачи двумя владельцами → ровно один CLAIMED), runtime.test.ts.
Остаточный риск: часы (RR-1). Исключительность на уровне ЖУРНАЛА гарантирована; на уровне внешнего мира — нет.
Статус:        GUARANTEED (журнал); GUARANTEED_UNDER_ASSUMPTIONS (lease как «взаимное исключение» работы).
```

### INV-004: Fence Validity

```
ID:            INV-004
Название:      Fence Validity
Условие:       запись воркера в журнал t принимается тогда и только тогда, когда в момент CAS (owner, epoch) fence
               равны текущим по журналу. Устаревший fence → StaleFenceError, ничего не записано.
Предположения: A1.
Механизм:      проверка внутри цикла mutate на актуальном состоянии; публикация в слот head+1.
Нарушение:     fence, выданный до исправлений N-1/N-2 осиротевшей задаче (legacy fence): claim-проверка выполняется
               ТОЛЬКО при claim, поэтому уже выданный fence остаётся валидным, пока не истечёт lease/не будет нового claim.
               Новая проверка требуемых задач его не отзывает (R-6).
Тесты:         runtime.test.ts, process.test.ts, effects-concurrency.test.ts.
Остаточный риск: R-6.
Статус:        GUARANTEED (для fence, выданных этой версией — см. INV-006, INV-011).
```

### INV-005: External Effect Uncertainty

```
ID:            INV-005
Название:      External Effect Uncertainty
Условие:       для эффекта (task, owner, epoch, key): fn запускается не более одного раза на объявление
               effect.intended, как видно по журналу; исход, не доказанный как «не выполнено», не повторяется
               автоматически. Это НЕ exactly-once.
Предположения: идемпотентность внешней системы по ключу эффекта — задача приложения; classifyError/EffectNotExecutedError
               — утверждения приложения.
Механизм:      effect.intended публикуется (CAS) ДО fn; другой владелец видит «под вопросом» (EffectInDoubtError);
               прочие исключения записываются как uncertain.
```

## 9.4 Liveness Properties

Liveness **не** safety: ниже — условия прогресса, а не запреты. Любое из них может не выполниться при отказе окружения.

| Свойство | Утверждение | Условия |
|---|---|---|
| **Eventual recovery** | Незавершённая операция (prune, compact, карантин) доводится до конца или откатывается первым же вызовом соответствующей операции | достижима операция, `unlink`/`link`/запись проходят; нет перманентного `EIO`/`EROFS` |
| **Eventual claimability** | Корректная активная задача с PENDING-родителем становится claimable после одного успешного `claim`/`findResumable` (откат) | откат (`unlink tombstone.json`) выполним; иначе `RequiredTaskPendingError` на каждый вызов |
| **Нет вечных блокировок** | Зависший или убитый pruner не блокирует ребёнка: ребёнок откатывает prune сам. Брошенный pin блокирует prune не дольше `referenceGraceMs` | ребёнок вызывается кем-то (планировщик). Если никто не вызывает `claim`/`findResumable`, задача остаётся active — это не deadlock, а отсутствие драйвера |
| **Lease expiry** | Истёкший lease можно перехватить без прежнего владельца | часы процесса, выполняющего claim, корректно показывают истечение; перекос часов может задержать перехват или совершить его преждевременно (RR-1) |
| **Зависший pruner** | SIGSTOP pruner'а между tombstone и просмотром не отменяет детей; после SIGCONT он видит активного ссылающегося и отступает (идемпотентно) | гонка откат ↔ возобновившийся pruner: R-4 |
| **Временный ENOSPC** | Запись события/tombstone/pin отказывает `StoreIoError`, ничего не опубликовано; повтор после освобождения места проходит. Откат prune и удаление данных — `unlink`, обычно не требуют места | на некоторых ФС (журналируемые, copy-on-write) `unlink` под `ENOSPC` может отказать — **не проверялось на реальном заполнении диска** |
| **findResumable** | Задача не теряется из выдачи навсегда: PENDING пропускается лишь на этот вызов (при неудачном откате) и повторяется на следующем | см. выше |
| **createTask** | Создание под родителем в PENDING отказывает `ValidationError` после ожидания ≈1 с (N-4: ложный отказ создателю, если pruner откатит секундой позже) | не потеря задачи, потеря живости создателя |

**Liveness не гарантируется**, если: хранилище недоступно на запись навсегда; нет ни одного вызывающего; lease постоянно
перехватывается более быстрыми часами; процессы бесконечно конкурируют за один слот (ограничено `ContentionError`).

## 9.5 Failure Model

| Failure | Operation | Persisted State | Recovery | Guarantee |
|---|---|---|---|---|
| SIGKILL | append, до `link()` | временный файл-чужак | события нет; повтор безопасен | INV-001 |
| SIGKILL | append, между `link()` и `unlink(tmp)` | событие полное, `nlink==2` | читатель удаляет доказуемый остаток | событие **есть** (INV-001) |
| SIGKILL | `runEffect`, внутри `fn` | `effect.intended` без исхода | новый владелец видит «под вопросом»; `reconcile` | INV-005, не exactly-once |
| SIGKILL | `markPruned`, во время записи tombstone | `tombstone.json.tmp.*` | безвредный остаток; прежняя задача LIVE | N-3 (накопление мусора) |
| SIGKILL / **SIGSTOP** | pruner после tombstone, до просмотра ссылающихся | tombstone, данные целы (PENDING) | ссылающийся откатывает prune; иначе `pruneTask` достраивает | **INV-012**, INV-008 |
| SIGKILL | pruner посреди удаления данных | tombstone, часть файлов удалена (GONE) | откат невозможен; активный ссылающийся → карантин (INV-011); `applyRetention` достраивает | INV-008, INV-011 |

| SIGKILL | карантин (`task.cancelled`) | событие записано или нет | следующая проверка снова отвергает и повторяет запись | INV-011 |
| SIGSTOP/SIGCONT | создатель между pin и публикацией дольше grace | pin устарел | pruner вправе удалить родителя; опубликованная позже задача — сирота, `claim` её отвергает | INV-006 (6a да, 6b нет) |
| Crash процесса | compact после `link()` сегмента | сегмент + loose-файлы | `compact()`/`applyRetention` удаляют только побайтно равные | INV-009 |
| ENOSPC / EIO | append / `markPruned` / pin | ничего не опубликовано | `StoreIoError`, повтор после устранения | отказ, не порча. **Реальное заполнение диска для tombstone/отката не тестировалось; проверена инъекция ошибок** |
| ENOSPC / EIO | откат tombstone | tombstone на месте | `RequiredTaskPendingError`; без отмены | INV-012 (инъекция) |

| Interrupted compact | compact | сегмент и дубли | достройка | INV-009 |
| Interrupted prune | prune | см. таблицу «Prune» | см. выше | INV-008 |

## 9.6 Linearization & Ordering

Строгой линеаризуемости **нет**. Что есть:

1. **Внутри одной задачи:** полный порядок по `seq`; точка линеаризации записи — успешный `link()` слота `seq`.
   Из N конкурентных писателей в слот побеждает ровно один (`conflict` остальным).
2. **Между задачами:** порядка нет. `listTaskIds`/`findResumable` — не снимок: состав может измениться в процессе.
3. **Межобъектные протоколы** (задача ↔ родитель) держатся не на порядке, а на схеме Деккера над create-only файлами.

| Событие | Точка публикации | Что гарантировано относительно других |
|---|---|---|
| `task.created` | `link()` `events/000000001.json` | pin родителя создан **до** неё; tombstone проверен после pin |
| `run.claimed` | `link()` слота `head+1` | проверка требуемых задач выполнена **до** CAS, по состоянию на момент проверки; после CAS родитель не меняет состояние на GONE, пока ребёнок активен и виден pruner'у |
| effect intent | `link()` слота `effect.intended` | публикуется **до** `fn`; другой процесс, увидевший её, не запускает `fn` |
| tombstone | `link()` `tombstone.json` (после fsync файла) | публикуется **до** просмотра ссылающихся и **до** удаления данных |
| prune completion | **единой точки нет**: последовательность `unlink` | после удаления первого файла откат невозможен; завершение — отсутствие `PRUNE_INCOMPLETE` |
| compact commit | `link()` сегмента (после сверки) | loose-файлы удаляются **после** |

**Окно между проверкой требований и CAS в `claim`.** Проверка родителя и публикация `run.claimed` — два шага. Родитель
не может перейти LIVE → GONE между ними при выполнении INV-006 (6b), потому что `task.created` ребёнка уже
опубликован, и pruner, просматривающий ссылающихся после tombstone, его видит. При нарушении grace (6b) окно существует,
и тогда исполнение сироты возможно только в течение одного уже начатого `claim`; следующий `claim` отвергнет.
Это то же условие, что в N-1, и оно **не исправлялось** в DURABLE-FIX-003.

## 9.7 Retention Dependencies

Что нельзя удалять, пока необходимо:

| Данные | Необходимы для | Условие удаления |
|---|---|---|
| Журнал активной задачи (все события) | свёртка состояния, fence, intent эффектов | никогда, пока задача активна |
| Журнал терминальной задачи | аудит, `getLog`, исход для зависимых | `terminalRetentionMs` истёк **и** нет активного ссылающегося (pin в пределах grace тоже считается) |
| Журнал родителя/зависимости активной задачи | проверка ссылок (INV-006), допуск к исполнению | пока на него ссылается активная задача |
| События `effect.*` | предотвращение повторного эффекта (INV-005) | живут в журнале задачи; пока задача не удалена, не удаляются. После prune защита от повтора **теряется** — новая задача с тем же ключом исполнима |
| `run.claimed` последнего epoch | проверка fence | пока задача активна |
| Tombstone | опознание поздней доставки; различение GONE от «не существовало» (оба → GONE) | хранится бессрочно; удаление tombstone **не реализовано** и не должно делаться при существовании данных |

**Аудит** входит в контракт только в объёме: терминальная задача хранится ≥ `terminalRetentionMs`, затем остаётся
tombstone (`finalStatus`, `outcomeDigest`, `headHash`). Хранение полного журнала бессрочно **не обещается**. Это решение
оператора политикой retention.

## 9.10 Контракт реализации Design A (FIX-004D)

Раздел фиксирует то, что реализовано и проверено после FIX-004A…C. Он **не усиливает** гарантии разделов 9.1–9.9
и не заменяет нормативный Design A (`DURABLE-PRUNE-PROTOCOL-DESIGN-004.md` и поправки). При расхождении
приоритет у Design A. Часть формулировок разделов 9.1–9.9 написана до Design A и сохранена как историческая.

### 9.10.1 Что гарантирует Mode A и чего не гарантирует

**Mode A — отказ процесса** (SIGKILL, SIGSTOP, исключение) при исправных ядре и файловой системе, на одном хосте.

Гарантируется (проверено процессными тестами FIX-004C на конкретной среде, см. 9.10.6):
* завершённая публикация (`link`) остаётся видимой всем процессам хоста; незавершённая оставляет только staging-имя;
* после SIGKILL в любой проверенной точке компакции, prune и append `Canon` подтверждённой истории не меняется,
  восстановление идемпотентно и работа продолжается;
* подтверждённое событие (`'appended'`/`'adopted'`) не теряется, пока задача не `COMMITTED`.

**Не гарантируется (`NOT GUARANTEED`):**
* переживание сбоя ОС и потери питания: `fsync` каталога выполняется по возможности; ошибка даёт предупреждение
  `DIR_FSYNC_FAILED`, достигнутая долговечность — `durability: 'unknown'`. Это не отказ и не подтверждение. Значение
  `'unknown'` нужно читать как «долговечность после сбоя ОС не установлена»; опираться на неё нельзя;
* порядок durable-операций между файлами при сбое ОС;
* NFS, SMB, FUSE с кэшированием, несколько хостов, macOS/Windows/BSD (раздел 43.2 Design A);
* exactly-once для внешних систем (9.10.2).

**Mode B (долговечность при сбое ОС) не реализован и не заявляется.** Нет ни проверки порядка `fsync`, ни тестов
с потерей питания. Ссылка на «Mode B» в тексте — только граница, за которой гарантий нет.

**Что зависит от A2-R** (допущение «real-time межкаталожная видимость на одном ядре», FS-1…FS-6): `'appended'` как
право победителя слота (CEI-6), единственность канонического сегмента (CC), корректность `derivePruneState` при
неатомарных листингах, отсутствие двойного приобретения права (G3). При нарушении A2-R возможны ложное `'appended'`
и повторное выполнение внешнего эффекта. A2-R — документируемое ограничение поддержки, а не проверяемое свойство:
конечная проба его не доказывает.

### 9.10.2 Права runtime: `appended`, `adopted`, `conflict`

| Результат `append` | Значение | Право, выводимое из победы в слоте |
|---|---|---|
| `'appended'` | этот вызов создал первый файл слота, `Canon = событие`, G2 = `LIVE` | **возможное** — при выполнении прочих условий (fence, эпоха, состояние эффекта) |
| `'adopted'` | `Canon = событие`, но создателя слота доказать нельзя (EEXIST, свидетельство через сегмент, повтор после потерянного ответа) | **нет** |
| `'conflict'` | в слоте другое событие | **нет** |

* **События, несущие право:** `task.created`, `run.claimed`, `effect.intended`, `await.resolved`, а также любой
  новый тип по умолчанию. Для них `'adopted'` обрабатывается как проигранная гонка.
* **События только состояния** (закрытый список `ADOPTED_IS_SUCCESS_EVENT_TYPES`: `effect.completed`, `fact.observed`,
  `plan.*`, `task.completed` и др.): `'adopted'` — успех, поскольку право на действие они не дают.
* **Lost response и retry.** Если ответ потерян после успешной публикации, повтор получает `'adopted'`, а не новое право.
  Runtime при `effect.intended` без исхода идёт в `EffectInDoubtError` или `reconcile`, но не запускает `fn` заново.
* **Compaction.** После перемещения события в сегмент слот освобождается; устаревший писатель, опубликовавший туда файл,
  получает `'adopted'` или `'conflict'`, но не `'appended'` (S2).
* **Наличие события не означает права на повторное выполнение внешнего действия.** Журнал фиксирует намерение и исход,
  но не знает, что произошло во внешней системе. Гарантия — «не более одного запуска `fn`, насколько можно судить по
  журналу». Это **не** exactly-once для внешних API; её дает только ключ идемпотентности на стороне внешней системы.

### 9.10.3 Prune и Retention

* `preparePrune(tombstone)` публикует `prune-<n>.prepare.json` (create-only); номера попыток не переиспользуются.
* `decidePrune(taskId, n, outcome, tombstone?)` публикует `prune-<n>.decision.json`; первый писатель побеждает,
  возвращается значение **регистра**, а не запрошенное. Решение не изменяется и не удаляется.
* `pruneState(taskId)` / `derivePruneState`: чистое чтение, выводит `live | preparing | committed | missing | corrupt |
  unreadable | legacy` из имён и содержимого `tasks/P/`. Ничего не пишет. `corrupt`, `unreadable`, `missing`, `legacy`
  не дают права на необратимое действие.
* **Persisted decision register** — файлы `prepare`/`decision` и `tombstone.json`; сохраняются после GONE, каталог
  `tasks/P/` сохраняется.
* **G1/G2.** G1 — ранний отказ, на безопасность не влияет. G2 после публикации: при `PREPARING` писатель ограниченно
  ставит `abort`, при `COMMITTED` получает `TaskPrunedError`; опубликованный файл **не удаляется** писателем.
* **Sweeper / recovery.** После `commit` остаток (в том числе опоздавшие файлы) убирается повторным `prune(tombstone)`;
  операция идемпотентна и завершается. Убитый pruner продолжается любым процессом.
* **Запрет resurrection.** После `COMMITTED` задача не возобновляется: `append`, `compact`, `createTask`
  с тем же id и чтение состояния отклоняются; поздняя публикация не создаёт `LIVE`.
* Допустимый наблюдаемый исход: писатель с устаревшим handle удалённого каталога получает
  `AppendOutcomeUnknownError`, повтор — `TaskPrunedError` (FIX-004C, наблюдение 1).

### 9.10.4 Граница интеграции

Durable State — **внутренний компонент MONOLITH**. Он доступен через пространство имён `durable` корневого экспорта
пакета и команду `monolith durable`. Приложения, сопровождаемые MONOLITH, не обязаны его импортировать. Это не
workflow-движок и не платформа исполнения произвольных приложений. Формат событий v1 не менялся.

**Совместимость версий.** Смешанный запуск runtime разных версий над одним хранилищем небезопасен по умолчанию
(ADR-018, критерий 49): старый runtime не знает о `prune-*`. Маркер `durable-protocol.json` создаётся только явным
действием оператора (`initializeProtocolSync`); хранилище с задачами без маркера открывается только для диагностики.
Защита от старого runtime, не понимающего маркер, не заявляется.
