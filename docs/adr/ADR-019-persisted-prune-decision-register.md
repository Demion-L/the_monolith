# ADR-019 — Persisted Prune Decision Register

> **Статус: `ACCEPTED` (2026-10-26).** Принят в рамках DURABLE-ADR-FINALIZATION-005 во исполнение **D-OWN-1**
> (владелец: persisted prune decision register оформляется отдельным ADR). Источник истины — нормативный
> Design A (`DURABLE-PRUNE-PROTOCOL-DESIGN-004.md`, §1–§46) и Appendix A; этот ADR **не создаёт новую версию протокола,
> не перепроектирует регистр и не копирует Design A**: подробные алгоритмы остаются в Design A.
>
> **Принятие ≠ проверенная реализация.** Production-код (`3f49f5b`) регистра не содержит; реализация — FIX-004.
> Статус `PROVEN` не присваивается; exactly-once для внешних эффектов не заявляется.
>
> Номер: ADR-019 свободен (проверено: `docs/adr/`, все ветки и worktrees репозитория; номера 007–018 заняты, ADR-015/016 — в `main`, ADR-019 нигде не используется).
>
> **Что утверждено владельцем и что является следствием проверенной спецификации** — см. раздел «Происхождение решений».

## Context

Прежний prune (`3f49f5b`) принимает решение об удалении неявно и многократно: общего состояния, где решение зафиксировано
один раз, нет; разделяемый признак — немонотонный `tombstone.json` (появляется, снимается, пересоздаётся). Следствия:
остановленный pruner, давно прошедший проверку, удаляет данные после чужого отката (J-1, HIGH); откат, проверивший
«данные целы», стирает tombstone завершённого prune (J-2); «GONE» выводится из состояния данных и даёт ложные срабатывания
при повреждении (J-4). Источник: DURABLE-REVIEW-004 и последующие аудиты 004B…004F (Design A, §2–§3).

## Problem

Нужна точка фиксации решения, которая одновременно: (1) однократна и необратима; (2) доступна любому участнику
(ребёнок, создатель, pruner, восстановитель) без часов, блокировок и таймаутов; (3) переживает SIGKILL/SIGSTOP/перезапуск
(Mode A); (4) не требует консенсуса между машинами и не меняет формат событий v1, журнал, fence и pins.

## Decision

Принять **Design A — «регистр решения на попытку»** (Design A §1, §5, §9):

* prune состоит из попыток `n = 1, 2, …`; попытка публикует `prune-n.prepare.json`, затем решение
  `prune-n.decision.json ∈ {commit, abort}` — **create-only**, первое опубликованное значение определяет судьбу попытки для всех;
* `abort` безусловно безопасен и доступен любому; `commit` безопасен только после скана ссылающихся, выполненного **после**
  видимости `prepare.n`, и проверки головы журнала;
* данные удаляются **только** при существующем `commit` (roll-forward); откат tombstone и проверка «данные целы» упраздняются;
* `tombstone.json` (формат v1) публикуется из `commit` для совместимости, но не определяет состояние;
* записи регистра и каталог `tasks/P/` **не удаляются и не изменяются** (A6); GC регистра запрещён.

Объём: этот ADR фиксирует регистр, его наблюдение, G2 (контракт опубликованного файла), sweeper, скан ссылающихся и взаимодействие с
claim/fence. Модель отказов и семантика `MISSING` — **ADR-018** (не пересматриваются здесь).

## State model

Логические состояния вычисляются функцией `derivePruneState(P)` (Design A §20.2) из множества имён и содержимого `tasks/P/`:

`LIVE` · `PREPARING(n)` · `COMMITTED(k)` (→ `DELETING`/`GONE` — физическое наблюдение, **не монотонное**, §26.1) ·
`CORRUPT` · `UNREADABLE` · `MISSING` · `LEGACY_TOMBSTONE`.

Приоритет: согласованный `COMMITTED` > `CORRUPT` > `UNREADABLE` > `PREPARING` > `LIVE`. Терминальна только логическая
`COMMITTED`. Результат не зависит от порядка обхода каталога; `CORRUPT` не сохраняется (вычисляется заново).

## Immutable decision registers

Файлы `prune-<n>.prepare.json` и `prune-<n>.decision.json` создаются публикацией (`createFile`: tmp → `link()`), содержимое неизменно,
имена **не переиспользуются**, удаления нет (Design A §19). Закрытая схема, строгий JSON, предел 64 KiB до чтения, поле `check`
(Design A §20.2). Номер новой попытки — `1 + max` существующих; лимит `MAX_PRUNE_ATTEMPTS` — ограничение живости (§22), не safety.

## Prepare / commit / abort

* `prepare.n` — маркер pruner'а (аналог Деккера): после его видимости pruner сканирует ссылающихся и сверяет голову журнала.
* `decide(n, v)` возвращает **значение, прочитанное из регистра** (при `EEXIST` — существующее); вызывающий действует по нему, а не по своему `v`.
* `abort` публикует любой участник, видевший валидный `prepare.n`; после `commit` в той же попытке `abort` невозможен и наоборот.
* Mode B (`DV`, долговечность `commit` при OS crash) **не заявлен** (`OS_CRASH_DURABILITY_NOT_GUARANTEED`, Design A §18).

## First-decision-wins

Победитель определяется порядком create-only `link` (A1). Проигравший читает значение победителя. Это даёт P-1 (однократность)
и PO-2 (нет одновременных успешных `commit` и `abort` одной попытки). Запоздалый `commit` остановленного pruner'а в уже закрытой
попытке отвергается регистром; запоздалое удаление требует существующего `commit`.

## Create-only publication

Единственный линеаризуемый примитив хранилища — `link()` с `EEXIST` (ADR-012, допущение A1). Staging `<name>.tmp.<pid>.<hex16>` (N1)
не интерпретируется, не нумеруется и не даёт `CORRUPT`. Остальные допущения — A2-R (FS-1…FS-6, §43), A3, A5…A8 — свойства среды, **не доказаны**.

## Crash recovery

Любое состояние регистра завершается вперёд (`commit` → roll-forward) или назад (`abort` → `LIVE`, новая попытка) любым участником
(Design A §12, Appendix A §A.3): SIGKILL между шагами оставляет только состояния из таблицы; повтор идемпотентен;
SIGSTOP не удерживает ресурсов. Автоматического пути из `CORRUPT` нет (оператор). Recovery не создаёт решения, противоречащего принятому.

## Register observation

Листинг не атомарен (A7). Вердикт `CORRUPT`, у которого все причины — отсутствие имён, подтверждается поиском по имени (A8) и правилом T
(хвостовая проба; при `m = 0` — `prepare.1`), иначе `UNREADABLE(register-observation-unstable)` (Design A §32, §41.2). Два совпавших листинга
не считаются доказательством атомарного снимка.

## `UNREADABLE` и `CORRUPT`

* `UNREADABLE` — значение неизвестно (`IOERR`, нестабильное наблюдение): повторяемо, **не** разрешает ни одного необратимого действия
  (`commit`, `prepare`, roll-forward класса C, карантин, fence, `tombstone.json`); охранное правило IO-G (§41.1): при `|C| = 0` и `IOERR`
  на `decision.j` находки шагов 4–5 не выносятся.
* `CORRUPT` — установленная находка по присутствующим файлам либо подтверждённое отсутствие; требует оператора; ничего не удаляется и никто не отменяется.
* `IOERR` на `decision.j`, `j < k` не отменяет подтверждённый `COMMITTED(k)` (F4F-02). Различия `MISSING`/`UNREADABLE`/`CORRUPT`/`LIVE`/`PREPARING`/`COMMITTED` сохраняются (D-OWN-3).

## Tombstone

`tombstone.json` v1 — публикуется после `commit` и до первого `unlink` данных, байт-в-байт копия записи `commit`, create-only, не удаляется.
`tombstone.json` без регистра — `LEGACY_TOMBSTONE` (подтверждается поиском `prepare.1`, §41.2): все операции — отказ, миграция только оператором
(Design A §13.1, ADR-018 D3). `commit` по legacy автоматически не публикуется.

## Sweeper

Остаток данных после `COMMITTED` (поздняя публикация `append`/`compact`/`pin`) убирает roll-forward/sweeper (Design A §26): идемпотентен, не создаёт
`commit`/`prepare`, не возобновляет `P`, не удаляет регистр, `tombstone.json` и `tasks/P/`. Классы удаления (§30): **A** (rollback-`unlink`
опубликованного файла) — **запрещён** (F-1); **B** — cleanup loose-копий, покрытых перечитанным сегментом (CL-1…CL-4); **C** — prune cleanup при согласованном `COMMITTED`.
Полнота физической очистки — свойство живости LV-1, `OPEN`.

## Referrer scan

Скан ссылающихся начинается **после** видимости `prepare.n` и считает нетерминального ребёнка с `task.created` независимо от fence, `run.claimed` и pin
(RS-1, RS-2, F-11; Design A §27, §33). Терминальность ребёнка — только по проверяемому evidence (E-L/E-C); отсутствие файлов — не evidence.
Исключение E2 (пустой читаемый журнал + `LIVE` без регистра ⇒ не ссылающийся, §42.1) безопасно при условии, что `claim` перечитывает родителя (см. ниже).

## Claim / fence interaction

`claim` для требования `R` выводит `derivePruneState(R)` **заново, без кэша**, после публикации `task.created` ребёнка; `PREPARING` разрешается `decide(abort)`;
fence выдаётся только из свежего `LIVE`; `COMMITTED` ⇒ `TaskOrphanedError`, fence не выдаётся (Design A §20.6, §6). Единственный путь к fence — `claim`;
защита позднего ребёнка — порядок `task.created` ≺ чтение `R` ≺ `link run.claimed`. Обязательный регрессионный тест — Design A §14.1 № 50 (F4F-04).
Не покрыто: эффект, начатый до терминала ребёнка (R-6), и транзитивные зависимости (N-8).

## Safety invariants

P-1 однократность решения; P-2 удаление ⇒ `commit`; P-3 `commit` ⇒ чистый скан после `prepare`; P-4 допуск ⇒ не `commit`; P-5 безопасность `abort` (Design A §4);
INV-006/007/008/010/011/012 (`DURABLE-STATE-RETENTION-SAFETY.md`) не ослабляются. Proof obligations PO-1…PO-11 и их статусы — Design A §10, §46.4 (словарь:
`ARGUED[Mode A]`, `MODEL-CHECKED(abstract)` в границах моделей, `OPEN`, `NOT CLAIMED`; `PROVEN` не используется).

## Liveness limitations

`CORRUPT` не имеет автоматического выхода; `UNREADABLE` при устойчивом `EIO` не завершается; `MAX_PRUNE_ATTEMPTS` не сбрасывается и может заблокировать retention;
журнал ребёнка в `CORRUPT`/`UNREADABLE`/`LEGACY`/`PREPARING` или без terminal evidence блокирует prune любого родителя; регистр растёт без автоочистки;
LV-1 требует внешнего триггера; враждебный участник может ускорить исчерпание лимита. Всё это — живость, не safety (fail-closed).

## Failure assumptions

Mode A: процессный crash, SIGKILL, SIGSTOP/SIGCONT, перезапуск, конкурентные `append`/`compact`/`pin`/`claim`/`prune`, один хост, одно ядро, локальная ФС, соблюдающая A2-R. Исключены
(ADR-018 D1, D-OWN-2): внешнее удаление/изменение файлов, восстановление старых копий (может **повторно выполнить внешние эффекты**), storage rollback, OS crash/power loss (Mode B), сетевые и
кэширующие ФС, не прошедшие пробу AC-A2-1, злонамеренные участники. Нарушение A2-R даёт ложные подтверждения/пропуски скана (Design A §43.3), а не «внешнее вмешательство».
Смешанные версии runtime небезопасны и запрещены операционно (ADR-018 D3).

## Rejected alternatives

| Альтернатива | Отвергнута, потому что |
|---|---|
| **Design B** — запрет отката создателем (откатывает только pruner) | остановленный pruner пересоздаёт tombstone (J-1 с другим актором); закрыть можно только признаком «pruner мёртв» (таймаут/lease), недоказуемым при SIGSTOP |
| **Design C** — эпохи и симметричный Деккер с отзывом `commit` | отзыв — снова `unlink` с ABA; ложный карантин (нарушение INV-012); нет единой точки решения (P-1) |
| Сборка мусора `prepare.*`/`abort` | переиспользование номера `n` позволяет остановленному pruner'у создать `commit` в уже закрытой попытке (Design A §19.1) |
| Глобальный creation registry | вне scope; не закрывает исключённые режимы; новый persisted-артефакт и собственное окно краха (ADR-018 A3) |
| Mode B как заявляемый режим | недоказуем существующими примитивами (семантика ошибки `fsync`, Design A §18.6) |
| `statfs`-gate для A2-R | тип ФС не доказывает FS-3/FS-4; допустим только как диагностика |

## Consequences

* (+) Решение о prune однократно, необратимо и общее; остановленный/убитый участник не может его нарушить; нет таймаутов и зависимости от часов; формат событий v1, журнал, fence, pins не меняются.
* (+) Состояние выводится из регистра, а не из состояния данных; состояния `UNREADABLE`/`CORRUPT`/`MISSING` обрабатываются fail-closed.
* (−) Два новых имени файлов на попытку; метаданные растут без автоочистки; лишний листинг при чтении состояния; `O(число задач)` скан на prune.
* (−) Зависимость от A2-R/A5/A7/A8 (свойства среды); живость — раздел «Liveness limitations».
* (−) Расширение SPI (`preparePrune`, `decidePrune`, `pruneState` — аддитивно, опционально); новые типизированные ошибки (`PRUNE_DECISION_CORRUPT`, `PRUNE_ATTEMPT_LIMIT`).
* Поведение, меняющееся относительно ADR-017: откат tombstone заменён `decide(abort)`; карантин по `MISSING` исчезает (ADR-018 D2). ADR-017 остаётся `proposed`; supersession — по ADR-018 («Соотношение с ADR-017»).

## Implementation acceptance criteria

Реализация принимается по критериям Design A §17 (в т.ч. 1–15, 24–37, 40–72; обязательны F-1, F-11 и тест 50) и плану FIX-004 (нормативен Design A §16; соответствие пакетов критериям — Design A §46.6). Обязательные условия, повторяющие safety-контракт:

1. `FsEventStore.compact` и `MemoryEventStore.compact` выполняют K1/K2 (CC-1, CC-2, CC-4) на границе **хранилища** (FIX-004A); до этого CEI-1 условно.
2. `claim` не кэширует состояние родителя и разрешает `PREPARING` через `decide(abort)`; fence — только из свежего `LIVE`.
3. Потребители `derivePruneState` ветвятся **только** по вердикту; `UNREADABLE`/`CORRUPT`/`MISSING`/`LEGACY_TOMBSTONE` не дают права на необратимое действие.
4. Нет rollback-`unlink`: spy на `ops.unlink` допускает только staging владельца, класс B и класс C.
5. Регистр и `tasks/P/` не удаляются; нумерация не уменьшается.
6. Проба AC-A2-1 на целевой ФС выполнена и зафиксирована; `PROVEN` и exactly-once не заявляются.
7. Хранилище без version marker (в том числе пустое) открывается обычным `open` только в режиме диагностики; marker создаётся лишь явным действием оператора; неявной миграции legacy нет (Design A §46.5, критерии 17, 18, 48).
