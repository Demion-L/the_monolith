# Lesson: "Re-read, compare, then act" across two syscalls is not atomic, even when it looks already serialized

## Mistake

The first stale-lock-recovery hardening pass read a lock file, confirmed its recorded owner was dead, re-read it to compare, and then called `unlinkSync` as a separate, later statement — reasoning that "re-read immediately before deleting" was itself sufficient serialization, so no dedicated mutex was needed. That reasoning was wrong: `readFileSync` and `unlinkSync` are two syscalls, not one, and nothing stops a *different* process from completing its own entire recovery cycle (delete the stale record, create its own fresh lock) in the gap between this process's compare and this process's unlink. Reproduced empirically with two real forked processes: a paused "slow" recoverer's later unconditional unlink deleted a "fast" recoverer's brand-new, already-claimed lock, after which both processes believed they owned it.

## Root Cause

"I just re-read it right before acting" *feels* atomic because the window looks small, but a verify-then-act sequence is only as safe as the narrowest possible interleaving, not the typical one. The first pass reasoned about the common case (the gap is usually too short to matter) instead of the adversarial case (what if another process's entire cycle lands exactly in that gap). A second, independent review was needed to catch it — the author who designs a verify-then-act sequence is the person least likely to see the gap in it.

## Prevention

**Any "read state, decide based on it, then mutate" sequence that spans more than one syscall needs an explicit mutex around the decide-then-mutate portion** — not "a re-read right before acting," which only narrows the window without closing it. If the resource already has its own exclusive-create primitive (e.g. `open(path, 'wx')`), reuse that same primitive to build the mutex rather than inventing a new synchronization mechanism.

**Signal to watch for:** a design note or review comment that says "we re-read right before deleting, so it's fine" without naming the specific primitive that makes the re-read-then-delete pair atomic. If no such primitive is named, the gap still exists — ask explicitly "what stops another process from running its own full cycle in between these two lines?"

## Criteria check

- Recurs in other stories: yes — any verify-then-mutate pattern on shared file/network state (cache eviction, session cleanup, stale-record pruning) can reintroduce this exact gap
- Non-obvious cause: yes — "I re-read it right before acting" reads as a complete fix; recognizing it as incomplete requires explicitly imagining a competing process's full cycle landing in the gap
- Concrete prevention: yes — a specific question ("what primitive makes this pair atomic?") and a specific fix shape (reuse the resource's own exclusive-create primitive as a dedicated mutex)
