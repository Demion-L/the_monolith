## 1. Определения (вводятся)

* **`own`** — `createFile(events/<s>.json)` (`safe-write.ts`) **вернулся нормально**, то есть успешно завершена **атомарная публикация итогового слота через `link(staging → events/<s>.json)`** (`publication = PUBLISHED`). Создание/запись/`fsync` staging-файла `own` **не** означают: пока `link` не вернулся успехом, `own` нет; `lost-race` (`WRITE_TARGET_EXISTS`, `NOT_PUBLISHED`) — это `EEXIST`-ветка (`adopt`), а не `own`. Предупреждения после публикации (`STAGING_RESIDUE`, провал `fsync` каталога) `own` не отменяют. Источник: возврат вызова публикации, а не память и не сравнение байт. Включает случай, когда `link` вернул ошибку, но проверка идентичности (`verifyPublication`, `safe-write.ts`) установила, что под финальным именем лежит inode **нашего** staging-файла. Ошибка с `publication = UNKNOWN` — не `own`.
* **`Cov`** — множество опубликованных сегментов, покрывающих слот `s` (по имени `S<from>-<to>`), из **одного** листинга `segments/`, начатого **строго после** возврата `link` (для `adopt` — после чтения слота), §35.2 шаг 1.
* **Свидетельство `loose`** — `Cov = ∅` и содержимое слота равно `L` (при `own` — по построению). Свидетельство `segment` — `Cov ≠ ∅` и строка сегмента равна `L`.
* **`F₁(s)`** — первый файл, когда-либо опубликованный в `events/<s>.json`.

## 2. Нормативный patch

### 2.1 §35.1 — добавить инвариант

> **CEI-6 (приобретение права).** `append` возвращает `'appended'` **только если** (i) `link` вызова вернул успех (`own`), (ii) свидетельство — `loose` (`Cov = ∅` в листинге после `link`), (iii) G2 вычислил `LIVE`. Тогда файл под именем слота есть `F₁(s)`, созданный этим вызовом, и `Canon(P, s) = L`. Во всех остальных случаях, где `Canon(P, s) = L` и G2 = `LIVE` (`EEXIST` с `c = L`; `own` со свидетельством `segment`; повтор после краха), результат — `'adopted'`. Совпадение `Canon = L` **не** означает «этот вызов создал слот» и не даёт права действия, выводимого из победы в CAS. Условие (i)–(iii) **необходимо** для `appended`; обратное не утверждается: создатель `F₁(s)` может получить `'adopted'` (§5, F-G-2).

### 2.2 §35.2 — алгоритм

Шаги 0–1 (`link`, чтение слота при `EEXIST`, листинг, сравнение) **не меняются**. Меняется отображение:

```
append(P, e):
  ev = CEI(P, s, L)           # EVIDENCE(via, mode) | CONFLICT | LOST | UNKNOWN
  CONFLICT                         → 'conflict'
  UNKNOWN                          → AppendOutcomeUnknownError
  EVIDENCE(via, mode) / LOST       → G2 (§24.2)
       PRUNED → TaskPrunedError;  CORRUPT → PRUNE_DECISION_CORRUPT(published);
       UNKNOWN, либо ev = LOST → AppendOutcomeUnknownError
       CONFIRMED →  'appended'  если mode = 'own' ∧ via = 'loose'
                    'adopted'   иначе
```
`CEI` возвращает `mode ∈ {own, adopt}` и `via ∈ {loose, segment}`. Примечание 1 (удаление собственной копии — только публикатором, класс B) сохраняется. **Примечание 4 («результаты API не добавлены») заменить:** «добавлен результат `'adopted'`; формат на диске не изменяется».

### 2.3 §35.3 — теорема

Заменить формулировку теоремы на: «Если `append` вернул `'appended'` или `'adopted'`, то `Canon(P, s) = L` на момент возврата и остаётся таким, пока `P` не `COMMITTED` (как прежде). **Если вернул `'appended'`, то, кроме того, файл `F₁(s)` создан этим вызовом.**» Доказательство второго утверждения — §4 ниже (вносится в §35.3 как Л4).

### 2.11 Контракт runtime (вносится в §5.3 / §27-раздел о потребителях и в ADR-019 «Claim / fence interaction»)

* **Право, выводимое из победы в CAS, даёт только `'appended'`.** Для событий, **несущих право** (`effect.intended`, `run.claimed`, `await.resolved`, `task.created`, а также любой тип, не внесённый явно в список ниже — deny-by-default), `'adopted'` равен `'conflict'`: `mutate` перечитывает состояние и пересчитывает план.
* **Список «`adopted` = успех»** (проверен по `EVENT_TYPES`, §8.2: 21 тип = 4 несущих право + 17 ниже; ни от одного из 17 не зависит приобретение права на последующее необратимое действие): `effect.completed`, `effect.failed`, `task.completed`, `task.failed`, `task.cancelled`, `plan.declared`, `plan.step_done`, `plan.step_skipped`, `decision.recorded`, `assumption.recorded`, `assumption.retracted`, `fact.observed`, `run.heartbeat`, `run.released`, `await.registered`, `await.expired`, `await.delivery_rejected`.
* **Условие списка.** Тип входит в список только если (а) право на внешнее/необратимое действие приобретается **другим** событием через CAS, а не этим; (б) повтор тех же байт либо безвреден, либо невозможен для другого вызывающего. Новый тип события в `EVENT_TYPES` по умолчанию **вне** списка; включение — только отдельной поправкой с разбором по (а)–(б). Тест: все значения `EVENT_TYPES` классифицированы (нет типа, не отнесённого ни к списку, ни к несущим право).
* **`resolveUnknown`** возвращает `'adopted'` (никогда `'appended'`) при совпадении hash: runtime не может доказать авторство по байтам.
* Следствия: `executeEffect` не переходит к `fn()` после `'adopted'` (путь к `fn()` лежит только через возврат `mutate` по `'appended'` или через `draft = null` для уже завершённого эффекта); `deliver` → `duplicate`; `createTask` → `created: false`; `claim` → повторный цикл.

### 2.12 F-G-1 — `readLog` по фактическому покрытию слота (решение D-OWN-014; нормативно, §35.1)

**Единственное правило канонического содержимого — §35.1 (`Canon(P, s)`); `readLog`, `CanonRead` (§40.2), `CEI` и `compact` (K2) обязаны вычислять покрытие и приоритет одинаково.** Альтернативного алгоритма определения каноники не вводится; запрета непрефиксной компакции не вводится.

* **Покрытие слота.** `Cov(s) = { S : S.from ≤ s ≤ S.to }` по именам `S<from>-<to>` из **одного** листинга `segments/` данного прохода. Слот `s` «покрыт» ⇔ `Cov(s) ≠ ∅`.
* **`readLog`.** Для loose-файла `events/<s>.json`: если слот покрыт — файл игнорируется (`LOOSE_COPY_OF_COMPACTED_EVENT`); если **не покрыт** — файл читается и участвует в журнале, **даже когда `s ≤ max(S.to)`**. Условие «`s ≤ segEnd`» (максимум `to` по всем сегментам) как признак покрытия **запрещено**. Строки сегментов объединяются по `seq`; несовпадение хэшей у перекрывающихся сегментов ⇒ `LogCorruptError('overlapping segments disagree')` (как в §35.1 п. 1); loose-файл покрытого слота в сравнении не участвует (CEI-2).
* **Пропуски (gaps).** Слот между сегментами (`S1-2`, `S5-9`, слоты 3–4) без loose-файла и без покрытия — пусто (`Canon` пусто); `readLog` — штатный повтор прохода, затем `LogCorruptError('events are missing from the log')` (поведение не меняется). Слот 3–4 с loose-файлом — каноничен и виден `readLog`.
* **Пересекающиеся сегменты.** Слот покрыт, если покрывает **хотя бы один** сегмент; строки всех покрывающих обязаны совпасть.
* **После recovery.** Прерванная компакция (K3–K5 + SIGKILL) оставляет сегмент и, возможно, loose-копии: loose-копии покрытых слотов игнорируются (любой `via`), непокрытых — каноничны. Повторный `compact` (K3 `EEXIST`) и cleanup (класс B, CL-1) покрытие не уменьшают (CL-2).
* **`compactedThrough`.** Поле `LogReadResult` остаётся справочным значением `max(S.to)` (используется `retention`/`runtime.compact` как граница префикса, где компакция идёт от `compactedThrough + 1`); **предикатом покрытия не является** и в `readLog`/`CEI` не используется. Непрефиксный сегмент, поданный напрямую в `EventStore.compact`, не нарушает безопасность: непокрытые слоты остаются loose (живость — `runtime.compact` может их пропустить, не безопасность).
* **Тест (в AC-ADO-1/AC-ADO-3, пакет FIX-004A):** «слот вне префикса»: сегмент `S5-9`, loose-файлы 1–4 существуют ⇒ `readLog` возвращает события 1–9 (а не `LogCorruptError`); `append` события в слот 3 с `c = L` и `Cov(3) = ∅` ⇒ `'appended'` для **видимого** читателям события; слот 7 с loose-копией ⇒ loose игнорируется. Один и тот же набор файлов даёт одинаковое `Canon` в `readLog`, `canonRead`, `cei`, `compact` (параметризованный тест на всех четырёх путях; `FsEventStore` и `MemoryEventStore`).

### 3.3 Конкурентная публикация сегмента между `link` и `CanonRead`

* `S` опубликован **до** начала листинга: виден (П5); `Cov ≠ ∅` ⇒ `adopted`/`conflict`.
* `S` опубликован **во время** листинга или после: листинг может его не вернуть (A7). Но компактор, у которого `s` входит в диапазон, прошёл K2 **после** `F₁(s)`: слот на момент K2 — либо пуст (K2 отказывает, CC-2), либо занят уже существовавшим файлом (тогда мы не `F₁`, а это П5-противоречие). Следовательно, K2 прочитал наш файл, строка `S` = `L` (L-CC). `appended` корректен: `Canon(s) = L` и сохранится. Cleanup K5 снимает наш файл **после** публикации `S`, обнаружимость `Canon` не теряется.
* Контрпримера нет.

### 3.4 Обнаружимость покрытия при compaction и recovery

Сегмент не удаляется до `COMMITTED` (CL-2); покрытие определяется по имени `S<from>-<to>`; recovery после SIGKILL заново листит `segments/`. Каталог `segments/` создаётся до публикации сегмента и не удаляется до `COMMITTED`. После `COMMITTED` покрытие исчезает, но тогда G2 даёт `PRUNED` (П6). Идемпотентный повтор `compact` (K3 `EEXIST` с идентичным содержимым) не создаёт нового сегмента и не снимает старый.

### 3.5 Повторное создание loose-слота после удаления

Это сценарий S2. Слот свободен только если покрыт (П3), поэтому `link` успешен, но `Cov ≠ ∅` (П5) ⇒ `adopted` (строка `= L`) или `conflict`. Новый loose-файл — сирота: читатели его игнорируют (диагностика `LOOSE_COPY_OF_COMPACTED_EVENT`), публикатор снимает его по классу B (`removeOwnLooseFile`, байт-идентичный). Права на действие не возникает.

### 3.6 Контрпримеры

Для необходимого условия **не найдено**. Найден контрпример к **простому** варианту A («`own` ⇒ `appended`»): стейл-писатель, §3.5 без охраны (ii) — отсюда G1. Найден контрпример к обратной импликации (она не заявляется): создатель `F₁`, у которого сегмент появился между `link` и листингом, получает `adopted` (F-G-2).

## 4. Проверка G2: нет новых путей к внешнему эффекту после `adopted`

Единственный путь к `fn()` в `executeEffect`: `await this.fenced(f, plan)` вернулся без исключения и `announced.replay === undefined`. `mutate` возвращается без исключения лишь (а) при `draft = null` (эффект уже `completed` — `replay` задан, `fn` не вызывается) или (б) по результату `append`. После поправки (б) допускает только `'appended'` для `effect.intended`. При `'adopted'` цикл перечитывает состояние: `effectIdentity(cur)` (`status@intendedAtSeq`) не равен `effectIdentity(prior)`, потому что наше событие (или идентичное чужое) уже в журнале с новым `seq` ⇒ `EffectConflictError`. Если `refresh` вернул устаревшее состояние, цикл повторит попытку на том же `seq`, снова получит `'adopted'` и завершится `ContentionError` — `fn` не вызывается ни в одной ветке. Повторный `runEffect` увидит `prior.status = 'intended'` ⇒ `reconcile` либо `EffectInDoubtError` (штатный путь «в сомнении»).

`resolveUnknown` (без поправки возвращает `'appended'` при совпадении hash) — **существующий узкий путь** к двойному `fn()` (unknown outcome ∧ одинаковые байты у двух вызывающих). Поправка закрывает его (§2.11). Новых путей нет: `'adopted'` ни в одной ветке не приводит к `return` из `mutate` для событий, несущих право.

Остаточные эффекты (живость, не безопасность): создатель, потерявший ответ, получает `EffectConflictError`/in-doubt вместо немедленного продолжения; `createTask` после потери ответа сообщает `created: false`.

## 5. Сверка с CEI-1…5 и CC-1…6 (не ослабляются)

* CEI-1…CEI-4: `Canon(s) = L` для всех подтверждений; `'conflict'` для иного содержимого — без изменений. `'adopted'` подтверждает **не больше**, чем прежний `'appended'`.
* CEI-5: `own` — результат текущего вызова, память экземпляра/процесса не используется; повтор после SIGKILL пересчитывает свидетельство с нуля.
* CC-1…CC-6: компакция не затрагивается.
* Persisted format v1, ADR-017/018/019 (статусы), классы unlink A/B/C — без изменений.

## 8. Результаты проверок D-OWN-014

### 8.1 Проверка 1 — смысл `createFile` в G1

`safe-write.ts: createFile` = staging-файл → `fsync` → `linkSync(staging, final)` → снятие staging-имени → `fsync` каталога. Нормальный возврат — `publication: 'PUBLISHED'` — наступает **только** после успеха `link` (либо после `verifyPublication`, установившей, что под финальным именем лежит наш inode). Провал до/во время `link` без публикации → `SafeWriteError(NOT_PUBLISHED)`; `lost-race` → `WRITE_TARGET_EXISTS`; неопределённость → `WRITE_PUBLICATION_UNKNOWN`. Вывод: формулировка G1 верна по существу; **уточнена** (§1: `own` = успешная атомарная публикация итогового слота через `link`, не создание staging). Противоречия нет.

### 8.2 Проверка 2 — allowlist `adopted`

`EVENT_TYPES` (`types.ts`) = 21 тип. Несущие право (deny-by-default, `adopted` ≡ `conflict`): `task.created`, `run.claimed`, `effect.intended`, `await.resolved` (4). Список «`adopted` = успех» (17):

| Тип | Почему не даёт права на необратимое действие |
|---|---|
| `effect.completed`, `effect.failed` | фиксируют результат уже приобретённого `effect.intended`; повторное выполнение разрешает только новый `effect.intended` через CAS (`effect.failed{retryable}` права не даёт) |
| `task.completed/failed/cancelled` | терминальные записи состояния; следствий-действий нет |
| `plan.*`, `decision.recorded`, `assumption.*`, `fact.observed` | записи состояния |
| `run.heartbeat`, `run.released` | продление/снятие уже имеющегося fence (владелец/эпоха заданы и проверяются в `fenced`); новый fence они не выдают — только `run.claimed` |
| `await.registered` | **замечание (LOW, не блокер):** `created: true` — сигнал «можно отправить внешний запрос»; байты события включают `randomBytes(16)`-токен, поэтому байт-идентичный повтор возможен только для самого создателя после потери ответа — двойного приобретения нет. Условие включения: токен остаётся per-call секретом; при его замене на детерминированный тип переходит в «несущие право» |
| `await.expired`, `await.delivery_rejected` | записи состояния (`delivery_rejected` — отчёт о проигранной доставке) |

Прочие типы отсутствуют: список + несущие право = `EVENT_TYPES` (раздел покрывает всё множество). Вывод: каждый тип списка не даёт права; deny-by-default для остальных сохранён и для новых типов. Противоречия нет.

### 8.3 Проверка 3 — F-G-1 и семантика `Canon(s)`

Подтверждено по `fs-store.ts`: `readLog` (≈ стр. 846, 862) игнорирует loose при `seq <= segEnd = max(S.to)`, тогда как `canonRead`/`cei`/`compact` K2 используют `from ≤ s ≤ to`; `FsEventStore.compact` принимает непрерывный диапазон, **не обязательно с начала** (проверка `contiguous range ending at throughSeq`). Расхождение реально, затрагивает только непрефиксный сегмент; fail-closed (читатель видит `LogCorruptError`, а CEI подтверждает — невидимое событие). Исправление §2.12 вводит **ту же** семантику покрытия, что §35.1 `Canon(P, s)`: покрытие по слоту, gaps (пусто), overlapping (все покрывающие совпадают), recovery (loose покрытых слотов игнорируется) — без нового алгоритма; `compactedThrough` остаётся справочным. Противоречия и новой safety-проблемы нет.
