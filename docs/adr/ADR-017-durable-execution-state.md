# ADR-017 — Durable Execution State (DURABLE-001)

> **Статус: `proposed`.** Реализация находится в ветке `feat/durable-state-001`
> (worktree `worktrees/durable-state-001`), в `main` не влита. Принятие и merge —
> решение владельца. Документ описывает то, что реализовано и проверено в этой ветке;
> всё, что не проверено, помечено как ограничение (§9).
>
> Связь с неотслеживаемыми ADR-015 (lock owner identity) и ADR-016 (bounded state):
> они лежат в рабочей копии `main` как `proposed`, не включены в эту ветку и не
> изменялись. Ниже они цитируются как внешние источники, **утверждения ADR-015 о
> воспроизведённых дефектах lock здесь не перепроверялись**.

## 1. Контекст: что представлял собой «Durable State» до этого ADR

Единственный существующий механизм долговечного состояния — Coordinatorium
(`src/coordinatorium/`, `.monolith/state.json`, ADR-008). Он решает задачу
«реестр dev-миссий и чекпоинтов проекта», а не «непрерывность исполнения
агентной задачи». Относительно требований эксперимента (процесс умирает, ответы
приходят через дни, в произвольном порядке и повторно, мир меняется):

| # | Проблема | Якорь в коде / факт |
|---|---|---|
| P1 | **Привязка к домену.** Схема — это `missions` и `checkpoints`; сторонний проект (SphynX, корпоративная платформа) не может положить в неё задачу без подмены смысла. TD-006 фиксирует то же. | `types.ts`: `TacticalState{missions,checkpoints}`; `state-keeper.ts` ID-деривация по `tactical.missions` |
| P2 | **Снимок, а не журнал.** Состояние — один JSON, переписываемый целиком на каждую мутацию (`replaceFile`). Нет истории событий, нет «состояния на момент отправки запроса», нельзя ответить «что изменилось, пока ждали». Чекпоинт — свободный текст. | `mutateState` → `atomicWriteState` |
| P3 | **Нет корреляции и идемпотентности внешних результатов.** Нет понятия «ожидаемый ответ», токена, дедупликации, обработки порядка/повтора/опоздания. | отсутствует |
| P4 | **Нет учёта побочных эффектов.** После краха нельзя узнать, какие внешние действия выполнены, какие нет, какие под вопросом. | отсутствует |
| P5 | **Нет основы для трёх сценариев продолжения:** ни допущений с их значением на момент решения, ни доказательств, ни решений с обоснованием, ни детерминированной классификации «можно продолжить / нужно учесть изменения / план недействителен». | отсутствует |
| P6 | **Неограниченный рост и fail-closed потолок.** Достигнув 16 MiB, `state.json` перестаёт читаться/писаться для `mission` (STATE-001). Политики удержания нет; ADR-016 (C′) предлагает её для Coordinatorium, но `proposed` и требует forward-only миграции схемы. | `MAX_STATE_BYTES`; tech-debt STATE-001 |
| P7 | **Взаимное исключение держится на lock-файле с эвристикой живости процесса (PID).** ADR-015 сообщает о воспроизведённых дефектах (H1: чужой PID-namespace → удаление lock живого владельца; H2: крах между `link()` и `unlink()` → постоянный wedge из-за `nlink==2`; M1/M2). Исправление живёт в другой ветке (`fix/lock-fix-001`) и не влито. | `lock.ts`; ADR-015 §1 |
| P8 | **Нет fencing.** Один писатель предполагается, но «зависший» процесс, чей lock перехватили, продолжит писать. | отсутствует |

Вывод оценки: исправлять это переделкой Coordinatorium нецелесообразно — P1/P2/P3/P4/P5
требуют другой модели (журнал событий + проекция), а P6/P7 затрагивают схему и
протокол lock, судьба которых решается ADR-015/016 отдельно. Поэтому построен
новый универсальный слой рядом, Coordinatorium **не изменён**.

## 2. Решение

`src/durable/` — журнал событий на задачу, хеш-цепочка, проекция, оценка
возобновления, удержание. Пять принципов:

1. **Источник истины — неизменяемый журнал событий задачи.** `TaskState` —
   чистая свёртка журнала (`projection.ts`), не хранится как авторитет, всегда
   восстановима, допускает «машину времени» (`foldUntil(seq)`).
2. **Запись — compare-and-set на номер следующего события, без lock-файлов.**
   Единственный линеаризуемый примитив хранилища: «создать слот `seq`, если он
   свободен» (`createFile` из ADR-012: temp → fsync → `link()`). Из N конкурентных
   писателей выигрывает один; остальные получают `conflict`, перечитывают и
   принимают решение заново. Нет владельца, которого надо объявлять мёртвым, —
   класс дефектов P7 отсутствует по построению.
3. **Универсальность.** Ядро знает: задача, событие, допущение, наблюдение, эффект,
   ожидание (await), доставка. Всё прикладное (`kind`, `goal`, `input`, payload,
   `result`) — непрозрачный JSON. Бэкенд — интерфейс `EventStore` (FS и memory
   реализованы, один набор conformance-тестов для обоих).
4. **Идемпотентность вместо «восстановления».** Любая операция, повтор которой
   после краха вероятен, при тех же параметрах — no-op, при других — ошибка.
   Агентный код пишется как процедура, которую можно запускать с начала сколько
   угодно раз (демонстрация §7).
5. **Честность о внешнем мире.** Хранилище не может сделать внешний эффект
   exactly-once. `runEffect` фиксирует намерение до и результат после; после краха
   состояние точно говорит, что выполнено, что точно не выполнено и что **под
   вопросом** (`EffectInDoubtError`, `reconcile`) — угадывания нет.

### 2.1 Модель

События (формат v1, закрытое множество; неизвестный тип — `LogUnsupportedError`,
не пропускается): `task.created`, `run.claimed|heartbeat|released`,
`plan.declared`, `plan.step_done|step_skipped`, `decision.recorded`,
`assumption.recorded|retracted`, `fact.observed`, `effect.intended|completed|failed`,
`await.registered|resolved|delivery_rejected|expired`, `task.completed|failed|cancelled`.

Конверт: `{v, taskId, seq, at, type, actor, data, prev, hash}`; `hash` — SHA-256 от
канонического JSON (ключи отсортированы) всего, кроме самого `hash`; `taskId` входит
в хеш. Подмена бита, удаление, перестановка, перенос события из другой задачи —
обнаруживаются при чтении. Терминальное событие запечатывает журнал.

Соответствие требованиям эксперимента:

| Вопрос из постановки | Где ответ |
|---|---|
| К какой задаче относятся результаты | токен ожидания `dsc1.<taskId>.<awaitId>.<nonce128>`; `deliver(token, …)` маршрутизирует без индекса и без живого процесса |
| Почему запрошены | `await.registered.purpose/request`, `decision.recorded{rationale, basedOn}` |
| Состояние на момент отправки | `await.registered.basisSeq` + `getStateAt(seq)` / `foldUntil` |
| Что изменилось за время ожидания | `diffStates(stateAtSend, now)` в `ResumePacket.sinceSend`; события других акторов после `basisSeq` |
| Какие действия выполнены / нет / под вопросом | реестр эффектов; `Assessment.unresolvedEffects{inDoubt}` |
| Что осталось сделать | `plan` (DAG шагов), `Assessment.nextSteps` |
| Можно ли безопасно продолжить | `assessTask` → `direct | adaptive | recovery | waiting | closed` |
| Произвольный порядок, повторная доставка | идемпотентный `deliver`: ключ идемпотентности **в пределах await**; дубль — `duplicate` без записи; второй, иной результат — `conflict` (в журнал пишется ограниченная запись, см. §2.5; сверх лимита ответ `recorded:false` без записи); опоздавший — принят с `late: true` |
| Не зависеть от живого процесса / LLM-сессии | всё состояние в журнале; `ResumePacket` — детерминированный документ |

### 2.2 Классификация продолжения (`assess.ts`, чистая функция)

Сравнивает **записанные допущения** (значение на момент решения, `blocking|advisory`)
с **текущими значениями**: `fact.observed` от других акторов и/или живые наблюдения,
переданные вызывающим (живое значение приоритетнее). Ядро не умеет «смотреть на мир» —
это делает приложение, — но знает, на что опирался план.

* `recovery`: сломано blocking-допущение; эффект под вопросом; ожидание просрочено;
  работа есть, а плана нет; шаги остались, но ни один не может выполниться.
* `waiting`: ничего не готово, но ожидаются ответы.
* `adaptive`: изменилось advisory-допущение; кто-то другой менял мир/план после
  отправки запроса; результат пришёл с опозданием; blocking-допущение невозможно
  проверить (настраивается `unverifiedBlocking`).
* `direct`: ничего из перечисленного, следующий шаг известен.

Классификация консервативна: сомнение никогда не трактуется в пользу `direct`.
`Reasoning Projector` в этом ADR **не реализуется**: `resumePacket()` — вход для него
(цель, решения с `basedOn`, допущения с доказательствами, наблюдения, эффекты, ожидания,
диф «с момента отправки», таймлайн).

### 2.3 Исполнитель: lease + fencing

`claim` выдаёт `Fence{owner, epoch}`; epoch строго растёт. Жив ли lease, решает
`leaseUntil` (истёк → можно перехватить). Любая запись воркера проверяет, что он
по-прежнему текущий владелец **на момент CAS**, поэтому «зависший» воркер после
перехвата получает `StaleFenceError`, а не вклинивается. Внешние участники
(`deliver`, `observe`, `cancel`) fence не требуют.

### 2.3a Внешние эффекты: конкурентность и неопределённый исход (DURABLE-FIX-001, D-1, D-5)

Хранилище не делает внешний эффект exactly-once. Гарантируется только следующее.

**Конкурентные вызовы `runEffect` с одной идентичностью.**
* Внутри одного `DurableTasks` вызовы с одним (task, owner, epoch, key) делят *одно* исполнение `fn`; остальные ждут и получают результат (`replayed: true`) либо ту же ошибку.
* Между экземплярами и процессами: запись `effect.intended` — compare-and-set по идентичности эффекта в журнале (`status@intendedAtSeq`). Из N вызовов, принявших решение по одному состоянию, объявляет и запускает `fn` ровно один; остальные получают `EffectConflictError` (`EFFECT_CONFLICT`), `fn` не вызывается. Файловых блокировок нет.
* Другой владелец (смена lease, рестарт, падение процесса) видит незавершённый эффект как «под вопросом» (`EffectInDoubtError` либо `reconcile`).
* Fence принадлежит одному воркеру. Один fence в двух процессах вне контракта: `fn` всё равно запускается один раз, но `reconcile` не отличает живого соседа от мёртвого.

**Три исхода вызова.** `fn` вернулась → `effect.completed`. `fn` бросила `EffectNotExecutedError` (или `classifyError` вернул `'not-executed'`) → `effect.failed`, повтор разрешён (`retryable`, по умолчанию да). Любая другая ошибка (в том числе таймаут) **не доказывает**, что внешняя операция не выполнена → `effect.failed {retryable:false, uncertain:true}`: эффект «под вопросом», повторно не запускается; решение только через `reconcile` (`completed` / `not-executed`) или оператора. `assess` даёт `recovery` / `EFFECT_IN_DOUBT`. Поле `uncertain` необязательное (версия формата 1 не менялась); старый читатель видит `retryable:false` и тоже не повторяет. Записи старых логов без `uncertain` сохраняют прежний смысл.

Идемпотентность внешней системы по ключу эффекта остаётся единственным способом сделать повтор безвредным.

**Ограничения D-5 (DURABLE-FIX-002).**
* `classifyError` и `EffectNotExecutedError` — утверждения приложения. Если приложение возвращает `'not-executed'` для ошибки, которая этого не доказывает (например, таймаут чтения ответа), хранилище поверит и разрешит повтор; обнаружить это оно не может. Исключение, брошенное самим `classifyError`, трактуется как неопределённый исход (безопасная сторона).
* **Старые журналы.** До D-5 любое исключение `fn` записывалось как `effect.failed {retryable: true}` без поля `uncertain`. Новый код читает такие записи как *достоверный* сбой и, в соответствии с прежним контрактом, допускает повтор. Были ли они на самом деле неопределёнными (таймаут после выполнения), по журналу не восстановить, поэтому они **не** объявляются безопасными задним числом: для эффектов, записанных старой версией, повтор возможен, и перед включением новой версии на живых данных оператору следует просмотреть `effect.failed` с `retryable: true`, чьё описание — внешняя операция с побочным эффектом (`monolith durable packet <id>`), и при сомнениях закрыть/пересоздать задачу либо задать `reconcile`.


### 2.4 Хранилище (FS)

```
tasks/<id>/events/<seq,9>.json        одно событие, неизменяемо
tasks/<id>/segments/S<from>-<to>.jsonl упакованные проверенные события (компакция)
tasks/<id>/tombstone.json              признак удалённой по retention задачи
```

Безопасность I/O — существующие примитивы `src/root`: `createFile`/`openParent`
(ADR-012: границы, запрет symlink, `O_EXCL`, fsync, identity-cleanup),
`readBoundedFile` (ADR-014: без symlink, регулярный файл, `O_NOFOLLOW`, лимиты).

**Крах между `link()` и `unlink(tmp)`** оставляет полное событие с двумя именами
(`nlink==2`); строгий читатель ADR-014 отвергает такой файл навсегда — это в точности
класс H2 для событий. Здесь второе имя — **доказуемый остаток**
(`<файл>.tmp.<pid>.<rand>` того же каталога с тем же dev/ino): читатель удаляет
ровно его и перечитывает. Любая другая вторая ссылка — `StoreSecurityError`.

**Пост-публикационный барьер.** «Зависший» писатель, чей слот за время паузы был
упакован компакцией (файл удалён после публикации сегмента) или удалён prune, мог бы
своим `link()` форкнуть журнал. Компакция и prune публикуют маркер (сегмент /
tombstone) **до** удаления; поэтому после своего `link()` писатель проверяет «покрыт ли
мой seq сегментом / есть ли tombstone» и, если да, забирает свой файл (только свой —
по совпадению байт) и сообщает `conflict` / `TaskPrunedError`.

**Алгоритм чтения (порядок существен).** Сначала листинг файлов событий, затем листинг
сегментов (сегмент публикуется раньше, чем удаляются покрытые им файлы, поэтому событие,
которого нет в первом листинге, гарантированно есть во втором). Свободные файлы читаются
сразу после листингов, и только потом разбираются сегменты (неизменяемые; при повторе не
разбираются заново). Исчезнувший файл или дыра → повтор (до 8 проходов), затем
`LogCorruptError`, но не укороченный журнал. Обе ошибки порядка найдены процессным тестом
«писатели + компактор + читатели» и стресс-прогоном, а не ревью.

### 2.4a Prune родителя против создания дочерней задачи (D-7)

«Проверил — удалил» и «проверил — создал» через процессы не атомарны. Схема Деккера на create-only примитивах, без lock-файлов и без новых типов событий: создатель сначала ставит **pin** (`tasks/<parent>/refs/<child>.json`), затем проверяет tombstone (виден → ребёнок не публикуется, `ValidationError`), затем публикует `task.created`. Prune сначала публикует tombstone, затем снова смотрит опубликованные задачи и pin'ы; нашёл ссылающуюся → `withdrawTombstone` (допустимо, пока данные целы и цепочка сходится с `headHash` tombstone) и `RetentionRefusedError`. Маркер, опубликованный вторым, видит первый, поэтому хотя бы одна сторона отступает. Если данные уже частично удалены, tombstone не отзывается: отказ с явным сообщением, дальнейшее удаление не выполняется.
Живость: pin без задачи за ним блокирует prune лишь `referenceGraceMs` (10 мин). Pin'ы удаляются вместе с данными родителя; для не удалённых родителей остаются мелкие файлы. Методы стора `pinReference/listReferences/markPruned/withdrawTombstone` опциональны; стор без них сохраняет прежнюю (слабую) проверку.

#### 2.4b Допуск к исполнению: требуемая задача проверяется в момент запуска (DURABLE-FIX-002, N-1, N-2)

**Причины.** (N-1) Создатель, простоявший дольше `referenceGraceMs` после pin (SIGSTOP, suspend), теряет защиту: pruner вправе игнорировать истёкший pin и удалить родителя. Возобновившись, создатель публикует `task.created` (активная задача), а отмена («компенсация») выполнялась только в его же процессе. Убитый между публикацией и компенсацией, он оставлял в хранилище активную задачу с удалённым родителем, и `claim` её выдавал. (N-2) Создатель пропускал проверку, если *по его часам* grace ещё не истёк; при опережающих часах pruner'а получалась та же картина без всякого сбоя.

**Протокол.** Безопасность больше не опирается ни на компенсацию создателя, ни на часы. Разделены два понятия: *состояние журнала* (задача `active`, событие `task.created` записано) и *разрешение к исполнению* (вычисляется из текущего состояния требуемых задач — `parentTaskId` и `dependsOn`, прямых ссылок):

* `claim` перед записью `run.claimed` проверяет требуемые задачи; если одна из них **GONE** (отсутствует или её удаление уже началось, §2.4c), бросает `TaskOrphanedError` (`TASK_ORPHANED`) и не пишет `run.claimed`. Если удаление требуемой задачи лишь *незавершено* (**PRUNE_PENDING**), `claim` откатывает prune (§2.4c) либо, если откатить сейчас нельзя, бросает `RequiredTaskPendingError` (`REQUIRED_TASK_PENDING`, `retryable`), тоже не пишет `run.claimed` и **ничего не отменяет**. Так как `fence` выдаёт только `claim`, ни `runEffect`, ни другие операции воркера не достижимы для сироты, и внешний эффект не может быть запущен.
* `findResumable` не предлагает такую задачу; `assess` и `resumePacket` возвращают `claimable: false` и причину `REQUIRED_TASK_GONE` (`severity: recovery`) либо, для незавершённого prune, `REQUIRED_TASK_PRUNE_PENDING`. `verify` остаётся диагностикой журнала и не меняет семантики: хэш-цепочка сироты корректна.
* **Карантин** — `task.cancelled` (актор `durable`) при обнаружении сироты (**только GONE**, никогда PENDING) любым из этих путей. Операция идемпотентна (отмена отменённой — no-op), конкурентные вызовы дают одно событие, использует терминальный резерв (§2.5). Это *очистка*, не гарантия: если запись не состоялась (SIGKILL, `ENOSPC`), задача остаётся `active` в журнале, но каждая следующая проверка по-прежнему её отвергает, а следующее обнаружение повторяет запись.
* Проверка создателя после публикации (`assertReferencesSurvived`) выполняется всегда, без сравнения с часами; она даёт немедленную обратную связь (`ValidationError` и отмену при GONE), но не является условием безопасности. Родитель в PRUNE_PENDING задачу создателя не отменяет (§2.4c).
* **Побочные записи чтения (N-7, LOW, не исправлено).** `assess` и `resumePacket` по названию — чтения, но при GONE выполняют карантин (`task.cancelled`), а `findResumable` кроме того откатывает PRUNE_PENDING. Для PRUNE_PENDING `assess`/`resumePacket` записи **не** делают. Побочная запись идемпотентна, не нужна для безопасности и сводится к одному событию на задачу; вызывающий, которому нужен строго read-only доступ, должен использовать `getLog`/`getState`. Устранение (чистый `assess` без карантина) потребует изменить поведение, на которое опираются существующие тесты, и в DURABLE-FIX-003 не делалось.

**Почему это выдерживает SIGKILL в любой точке и не зависит от часов.** Сторона pruner'а: tombstone → просмотр ссылающихся. Сторона запуска: `task.created` уже опубликован → `claim` читает родителя. Если `claim` не видит tombstone, то tombstone публикуется позже чтения, значит просмотр pruner'а (после tombstone) увидит активную задачу и откажет. Если видит — задача не запускается. Это тот же аргумент «второй маркер видит первый», но роль маркера создателя играет сама опубликованная задача, а не pin, поэтому истечение pin'а (`referenceGraceMs`) влияет только на живость (брошенный pin перестаёт блокировать prune), но не на безопасность. Убийство создателя, `claim`'а или карантина в любой момент оставляет либо задачу, которую следующая проверка отвергнет, либо корректное состояние.

**Границы гарантий.**
* Гарантия: никакая активная задача с pruned/отсутствующей прямой требуемой задачей не получает fence через `claim` и не предлагается `findResumable`; это относится и к сиротам, оставленным предыдущими версиями (миграция не нужна, формат событий v1 не менялся).
* Требуется линеаризуемость `append`/публикации tombstone/чтения (как для остального протокола). Проверено на локальной ФС одного хоста. Общая ФС между несколькими хостами (NFS и т. п.) **не заявлена и не проверялась**; безопасность не использует сравнение часов разных процессов, но опирается на атомарность `link/rename` и видимость записей, которые NFS в общем случае не гарантирует.
* Часы: `referenceGraceMs` и срок lease по-прежнему сравнивают время разных процессов (RR-1), но скачок часов (NTP, suspend/resume) может лишь преждевременно освободить брошенный pin или продлить его блокировку; допуск к исполнению от этого не зависит. После длительной остановки процесса его следующая проверка выполняется по свежему состоянию.
* **Транзитивные зависимости не отслеживаются (N-8, принятое ограничение).** Проверяются только *прямые* ссылки (`parentTaskId`, `dependsOn`), и требование считается выполненным, если требуемая задача существует и не pruned, **независимо от её статуса**. Карантин сироты C (`task.cancelled`) не отменяет и не блокирует задачу G, которая требует C: C по-прежнему существует, и G остаётся допущенной к исполнению. Каскадной отмены потомков нет; G защищена лишь от удаления своих *прямых* требований. Если приложению нужна семантика «потомок отменённой не запускается», оно должно проверять статус требуемых задач само либо отменять потомков явно.
* Цена: проверка выполняется в `claim`/`assess`/`findResumable` только для задач со ссылками. Ожидание «до ~1 с» (`SETTLE_ATTEMPTS`) осталось только в `createTask` (отказ создания новой задачи при pruned родителе, ничего не теряется); для допуска к исполнению оно **удалено**: оно превращало зависший pruner в необратимую отмену корректной задачи (N-6, §2.4c).

#### 2.4c Семантика tombstone и устранение N-6 (DURABLE-FIX-003)

**Дефект N-6 (MEDIUM, найден DURABLE-REVIEW-003).** Tombstone публикуется *до* просмотра ссылающихся. Pruner, остановленный (SIGSTOP) или убитый сразу после публикации, оставляет tombstone при целых данных и при уже существующей корректной активной дочерней задаче. До исправления `claim` считал такой tombstone окончательным отсутствием родителя после ~1 с ожидания и отменял ребёнка (`task.cancelled`); откат prune его уже не возвращал. Временное состояние удаления смешивалось с окончательным.

**Логическая модель ссылки** (ничего нового на диске, enum не публикуется): `LIVE` — задача существует, tombstone нет; `PRUNE_PENDING` — tombstone есть, но данные ещё целы (удаление не начато) либо их нельзя исследовать сейчас; `GONE` — задачи не было, либо удаление данных начато или завершено (prune зафиксирован). Различает состояния не время, а данные: диагностика `PRUNE_INCOMPLETE` и результат `withdrawTombstone`.

| Состояние | `claim` | `findResumable` | `assess`/`resumePacket` | Карантин |
|---|---|---|---|---|
| LIVE | допускает | предлагает | `claimable` по обычным правилам | нет |
| PRUNE_PENDING, активный ссылающийся | откатывает prune (`withdrawTombstone`), допускает; если откат не удался — `RequiredTaskPendingError` | откатывает и предлагает; при неудаче пропускает до следующего вызова | `claimable:false`, `REQUIRED_TASK_PRUNE_PENDING`, **без записи** | **нет** |
| GONE | `TaskOrphanedError` | не предлагает | `claimable:false`, `REQUIRED_TASK_GONE` | да, идемпотентно |

**Когда карантин допустим:** только при GONE. Основание: prune зафиксирован лишь после того, как pruner прошёл повторный просмотр ссылающихся и начал удалять данные; корректного ребёнка, опубликованного до этого просмотра, pruner обнаружил бы и отступил. Остаётся окно истёкшего pin'а (`referenceGraceMs`): создатель, простоявший дольше grace, мог опубликовать задачу после того, как pruner зафиксировал удаление; такая задача — настоящая сирота, и карантин для неё верен (N-1).

**Почему откат ссылающимся допустим.** Откат выполняет только активная задача, чей `task.created` уже опубликован. Любой pruner, проходящий повторный просмотр после этого, её увидит и откажет; pruner, уже прошедший просмотр *до* публикации задачи, обязан был видеть её pin (до истечения grace) либо pin не мог появиться после tombstone. Откат — удаление одного файла `tombstone.json`, идемпотентен, отказывает (`TombstoneCommittedError`, подкласс `LogCorruptError`) после удаления первого же файла данных. События журнала при откате не пишутся.

**Крахи.** SIGKILL/SIGSTOP pruner'а после tombstone: данные целы → ребёнок откатывает prune сам (не нужен ни живой pruner, ни retention); без ссылающихся `applyRetention`/`pruneTask` доделывает удаление. SIGKILL посреди удаления: данные частичны → GONE, откат невозможен, `applyRetention` доделывает. SIGKILL во время отката: откат — одна операция `unlink`, состояние до неё (PENDING) или после (LIVE). Ошибка записи при откате (EIO, ENOSPC) → `RequiredTaskPendingError`, ничего не отменено, следующий вызов повторяет. Параллельные восстановители идемпотентны (второй видит отсутствие tombstone).

**Таймаут** не принимает решения о GONE: он лишь ограничивает ожидание в `createTask`. Вечной блокировки нет, пока достижим хоть один вызов `claim`/`findResumable`/`applyRetention` и запись `unlink` проходит.

**Честные границы.** (1) Откат и удаление данных не атомарны относительно друг друга: гарантия опирается на то, что pruner, начавший удалять, видел отсутствие активных ссылающихся; нарушить это может только создатель, простоявший дольше `referenceGraceMs` между pin'ом и публикацией (условие *отдельное* от этого исправления, см. Safety Specification, INV-006). (2) Выданный `fence` ребёнка не затрагивается: пока ребёнок активен, prune его родителя отказывает, а тот, кто уже прошёл просмотр, не мог видеть ребёнка, которого ещё не было. (3) N-4 (транзитный tombstone отказывает *создателю* новой задачи) не исправлялся — это живость создателя, не потеря задачи.

Спецификация инвариантов, модель отказов и матрица верификации: `docs/architecture/DURABLE-STATE-RETENTION-SAFETY.md`.

### 2.5 Жизненный цикл информации

* **Журналы активных задач ограничены:** `maxEventsPerTask` (50 000) ограничивает *обычные* события, событие ≤ 256 KiB;
  при достижении — `LogTooLargeError` (продолжать в новой задаче через `parentTaskId`).
  Над лимитом есть резерв `terminalReserveEvents` (16, 0 = строгий потолок): `run.claimed`/`run.released` могут занять все слоты кроме последнего, терминальные события (`complete`/`fail`/`cancel`) — любой. Задача на лимите всегда может быть закрыта (при истёкшем lease — `claim`, затем `complete`; `cancel` fence не требует). Абсолютный потолок — `maxEventsPerTask + terminalReserveEvents`. Heartbeat — обычное событие.
  **Отклонённые доставки** (`await.delivery_rejected`): payload > 4 KiB заменяется `{$truncated, bytes, sha256}`; хранится не более 8 записей на await и 64 на задачу, дальше ответ `conflict` с `recorded:false` без записи (виден seq события, разрешившего await). Наблюдаемость сверх лимита — только счётчик `rejectedDeliveries` первых записей.
  **Физическая нехватка места** (`ENOSPC`, `EDQUOT`, `EIO`) — не логический лимит: `StoreIoError` с `errnoCode`, ничего не опубликовано, задача остаётся активной, терминальные события подчиняются той же физике и проходят после освобождения места. Резерв слотов от этого не защищает.
* **Прерванные операции завершаются через публичный API (D-4).** `compact()` при следах сегмента без удаления loose-файлов вызывает `store.sweepCompacted`: удаляется только файл, байт-в-байт равный событию сегмента; отличающийся сохраняется. `pruneTask()` при существующем tombstone доделывает удаление (tombstone — доказательство прежней проверки), но заново проверяет ссылающиеся задачи. `planRetention` показывает «finish interrupted compaction/prune», `readLog` даёт диагностику `PRUNE_INCOMPLETE`.
* **Компакция** (`compact`, `retention`): события упаковываются в сегменты ≤ 4 MiB
  (читатель принимает до 16 MiB), сегмент создаётся (`link`), перечитывается и
  сверяется побайтно, **только затем** удаляются файлы; каждый префикс шагов —
  согласованное состояние, повторный запуск достраивает прерванное. Содержимое событий
  не меняется; `keepTail` и минимальный батч (защита от сегментов-«крошек») по умолчанию
  100.
* **Prune** — только терминальные задачи старше `terminalRetentionMs`, на которые не
  ссылается **активная** задача (`parentTaskId`/`dependsOn`); план — чистая функция
  (dry-run), исполнение заново проверяет условия по живому журналу. Порядок: tombstone
  (create-only) → повторный просмотр ссылающихся (опубликованные задачи и pin'ы) → при находке tombstone отзывается (данные ещё целы), иначе удаление данных; tombstone хранит id, итоговый статус, хеш головы и
  дайджест исхода — поздняя доставка в удалённую задачу опознаётся (`ignored: task-pruned`),
  а не «воскрешает» её. Активные задачи никогда не удаляются. Задача с повреждённым
  журналом в план не попадает.
* Файлы-остатки (`*.tmp.*`) автоматически не удаляются ни по возрасту, ни по имени, ни по
  PID: удаляется только второе имя, доказуемо принадлежащее уже опубликованному файлу
  (тот же dev/ino); остальное лишь сообщается диагностикой (согласуется с FS-CLEAN-001).

### 2.6 Границы гарантий целостности (D-6)

Хеш-цепочка (`prev`, `hash` = SHA-256 канонического JSON, `taskId` в хеше) — **не** средство аутентификации. Что она даёт и чего нет:

| Угроза | Обнаруживается? | Пояснение |
|---|---|---|
| Случайное повреждение (битрот, обрезанный/испорченный файл) | да | хеш события не сходится → `LogCorruptError` |
| Неконсистентность журнала (дыра в seq, переставленные/удалённые *серединные* события, событие чужой задачи, нарушение правил свёртки) | да | проверка `seq`, `prev`, `taskId`, строгая свёртка |
| Умышленная подмена тем, кто может писать в каталог хранилища | **нет** | атакующий пересчитывает хеши всей цепочки — алгоритм открыт, ключа нет |
| Усечение хвоста (удалены последние N событий) | **нет** | оставшийся префикс — валидная цепочка; задача лишь «откатывается». Исключение: явный tombstone хранит `headHash`/`headSeq` удалённой задачи |
| Подмена всего журнала задачи согласованной цепочкой | **нет** | то же |

Чтобы закрыть умышленную подмену и усечение, нужен доверенный внешний якорь (например подпись/HMAC с ключом вне хранилища либо внешняя публикация `headSeq/headHash`). Это отдельное архитектурное решение, **в ADR-017 не реализовано**: HMAC, anchor-сервис и иная security-инфраструктура не добавлялись. Модель угроз: TM-A (случайные отказы и конкурентные честные процессы) поддерживается; писатель с доступом к каталогу хранилища считается доверенным. Токены ожидания — capability: читающий журнал может подделать доставку; CLI скрывает секретную часть токенов (`--reveal-tokens` показывает).

## 3. Что сознательно НЕ сделано

* Coordinatorium не мигрирован на новый слой и не изменён (нет миграции данных, нет
  риска для существующих гарантий). Реализация C′ из ADR-016 для `state.json` — отдельное
  решение владельца (его Q1 не снят).
* Reasoning Projector, планировщик/очередь доставки, транспорт, аутентификация
  отправителей.
* Вторичные индексы (список задач и `findResumable` читают журналы всех задач).
* Крупные payload (> 256 KiB) — хранить снаружи и передавать ссылку.
* Native-слой ФС / TM-C (ADR-013): динамическая подмена каталогов не отражается.

## 5. Матрица отказов (FS-бэкенд)

| Момент креша / ситуация | Состояние на диске | Поведение |
|---|---|---|
| до `link()` события | временный файл-чужак | события нет; повтор безопасен |
| между `link()` и `unlink(tmp)` | событие полное, `nlink==2` | событие **есть**; читатель удаляет доказуемый остаток |
| после публикации, до `effect.completed` | `effect.intended` без исхода | `EffectInDoubtError` / `reconcile`; не перезапускается вслепую |
| после `registerAwait`, до отправки | await без `effect.completed` | повтор той же процедуры: тот же токен, отправка выполняется |
| сегмент создан, файлы не удалены | дубликаты (сегмент авторитетен) | читается корректно; повтор `compact` достраивает |
| tombstone создан, данные не удалены | задача читается как pruned | повтор `prune` достраивает |
| «зависший» писатель в упакованный/удалённый слот | свой файл на мгновение | откат своего файла, `conflict` / `TaskPrunedError` |
| неизвестный исход публикации | — | перечитывание: событие с тем же хешом = записано |
| `fn` бросила, исход внешней операции неизвестен | `effect.failed {retryable:false, uncertain:true}` | не повторяется; `reconcile` или оператор |
| сегмент создан, loose-файлы не удалены (прерванная компакция) | дубликаты, сегмент авторитетен | `compact()`/`applyRetention` удаляют только побайтно совпадающие |
| tombstone создан, данные не удалены | задача читается как pruned, `PRUNE_INCOMPLETE` | `pruneTask()`/`applyRetention` доделывают, предварительно проверив ссылающихся |
| крах/остановка pruner'а между tombstone и повторным просмотром (PRUNE_PENDING) | tombstone при целых данных | `claim`/`findResumable` ссылающейся задачи откатывают prune (`withdrawTombstone`), ребёнок **не отменяется**; `pruneTask()` тоже отзывает при ссылающейся, иначе доделывает (§2.4c) |
| крах pruner'а посреди удаления данных (GONE) | tombstone, часть файлов удалена | откат невозможен; ссылающаяся активная задача получает `TaskOrphanedError` и карантин; `applyRetention` доделывает удаление |
| ошибка записи при откате tombstone | tombstone на месте | `RequiredTaskPendingError` (retryable), без отмены; повтор после устранения причины |
| диск заполнен | событие не опубликовано | `StoreIoError` (`errnoCode`), задача активна; не `LogTooLargeError` |
| повреждение/подмена/дыра | — | `LogCorruptError`, без авто-ремонта; другие задачи не затронуты |
| событие неизвестного формата | — | `LogUnsupportedError` |

## 6. Проверка

Команды: `npx vitest run` (весь репозиторий), `npx vitest run src/durable`,
`node dist/scripts/durable-demo.js run --dir <каталог> --scenario direct|adaptive|recovery`,
`monolith durable verify`. Итоговые числа и мутационные проверки — в отчёте
эксперимента и в выводе тестов; тесты не ослаблялись, существующие тесты не менялись.

Классы проверок: контракт хранилища (оба бэкенда); семантика API; крах/состязания
(инъекция ошибок `ops`, подмена каталога прав, пауза писателя в точке между проверкой и
публикацией); реальные процессы (конкурентные писатели, гонка claim/delivery,
**SIGKILL между `link()` и `unlink`**, «шторм» убийств, компактор + писатели + читатели
одновременно); property-тест случайных последовательностей (инварианты: цепочка,
инкрементальное состояние = свёртка с нуля = префиксы, `assess` не падает);
сквозная демонстрация в трёх сценариях. Мутации защитных механизмов (пост-барьер, ремонт
остатка, авторитет сегментов) ломают соответствующие тесты.

## 7. Демонстрация

`src/scripts/durable-demo.ts` — четыре отдельных OS-процесса: агент стартует задачу и
**убивается SIGKILL в момент отправки третьего запроса**; «через три дня» внешняя
система отвечает в обратном порядке, с дублем и с противоречащим ответом (процесса
агента нет); другой агент меняет мир; агент запускается снова, не зная, что это
рестарт, и по журналу получает `direct`/`adaptive`/`recovery`. Третий запрос
опознаётся как «под вопросом» и разрешается через `reconcile` по внешней системе.

## 8. Совместимость

DURABLE-FIX-001 (ответ на независимое ревью): формат событий v1 и версия не менялись; добавлено лишь необязательное поле `uncertain` в `effect.failed` (старые логи читаются как раньше, старый читатель на новых записях остаётся безопасным). Новое: `EffectState.uncertain`, `Assessment.unresolvedEffects[].uncertainFailure`, `DeliveryResult.conflict.recorded`, `StoreIoError.errnoCode`, `EffectConflictError`, `EffectNotExecutedError`, `StoreDiagnostic PRUNE_INCOMPLETE`, опции `terminalReserveEvents`/`referenceGraceMs`, опциональные методы `EventStore`. Поведенческое изменение: обычная ошибка `fn` больше не оставляет эффект повторяемым (нужен `EffectNotExecutedError`/`classifyError`). Словари `TaskState` — объекты без прототипа (сериализация та же). Каталоги `refs/` появляются в каталоге задачи при создании дочерних задач.

DURABLE-FIX-003 (N-6): формат событий v1, формат tombstone и раскладка каталогов не менялись. Добавлено: `RequiredTaskPendingError` (`REQUIRED_TASK_PENDING`), `TombstoneCommittedError` (подкласс `LogCorruptError`), причина `REQUIRED_TASK_PRUNE_PENDING`, `PRUNE_INCOMPLETE` в `MemoryEventStore`. Поведенческое изменение: `claim` на родителя с незавершённым prune больше не бросает `TaskOrphanedError` и не отменяет задачу. Интерфейс `EventStore` не изменён. Журналы, записанные прежними версиями, читаются без миграции.

Новая подсистема, существующие форматы и API не затронуты. `src/index.ts` добавляет
пространство имён `durable` (имена ошибок пересекаются с Coordinatorium, поэтому не
плоский реэкспорт). CLI: `monolith durable list|show|assess|packet|verify|retention`
(`retention` без `--apply` — dry-run).

## 9. Ограничения и остаточные риски

* **RR-1 Часы.** Lease и дедлайны сравниваются по часам процессов; перекос часов между
  хостами может привести к преждевременному перехвату. Fencing не даёт воркерам
  чередовать записи в журнал, но уже начатый внешний эффект «зависшего» воркера он не
  отменяет — для этого нужны идемпотентные внешние операции (ключ эффекта).
* **RR-2 Внешние эффекты.** Хранилище гарантирует «не более одного запуска `fn` на объявление, насколько
  видно по журналу» (§2.3a), но не exactly-once: после сбоя или неопределённого исхода внешняя операция
  могла выполниться. Исход «под вопросом» разрешает только приложение (`reconcile`); безвредный повтор
  возможен лишь при идемпотентности внешней системы по ключу эффекта.
* **RR-3 Масштаб чтения.** Чтение журнала — O(события) (до компакции — по файлу на
  событие); `listTasks`/`findResumable`/`planRetention` — O(задачи × журнал). Измерений на
  больших объёмах не проводилось.
* **RR-4 Размер.** Событие ≤ 256 KiB; активная задача ≤ 50 000 обычных событий + резерв 16 (§2.5).
* **RR-5 Платформа.** Гарантии — POSIX/Linux на локальной ФС с поддержкой `link()`.
  Windows/macOS не проверялись; NFS/SMB вне гарантий (`link()` и fsync семантика).
  Регистронезависимые ФС: id `Job` и `job` конфликтуют.
* **RR-6 Модель угроз.** TM-A поддерживается; TM-B — см. ADR-013/014; **TM-C не
  поддерживается**. Токен ожидания — capability-строка в журнале: тот, кто читает журнал,
  может подделать доставку; аутентификация отправителя — задача транспорта.
* **RR-7 Ошибки диска.** `ENOSPC`, `EIO` и т. п. поднимаются как `StoreIoError` (с `errnoCode`) без
  «деградации»; `ENOSPC` на записи события проверен тестом, остальные коды — только по общему пути.
  **Долговечность (R-8).** Видимость события в page cache (в т. ч. другим процессом) — не доказательство
  сохранности после сбоя питания. Опубликованное событие надёжно лишь при `durability: 'full'`, когда fsync
  файла и каталога завершились успешно. Сбой fsync каталога после публикации (`DIR_FSYNC_FAILED`, достигнутая
  долговечность `unknown`) означает, что запись опубликована, но её сохранность неизвестна; fsync файла при
  ошибке не повторяется. Хранилище сообщает об этом через `onWarning`; решение (остановить воркера, повторить
  эффект после проверки) принимает приложение. `durability: 'file'` слабее: запись каталога может не пережить сбой.
* **RR-8 Зависимость от ADR-014.** Читатель строг (без symlink). Если ADR-014 ослабят или
  ужесточат (например, запретят даже ремонт остатка), нужен пересмотр §2.4.
* **RR-9 Нет автоматической миграции формата.** Формат событий v1 фиксирован; v2 потребует
  явного решения (читатели v1 на v2 отказывают громко).
