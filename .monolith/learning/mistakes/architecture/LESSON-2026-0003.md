# Lesson: Never combine liveness with age via OR in stale-resource recovery

## Mistake

The original Coordinatorium file-lock design paired a PID-liveness check with a 30-second age fallback, reasoning the age branch would catch a PID-reuse edge case liveness alone couldn't. The two conditions were combined with OR, not "liveness first, age only as a narrow tie-breaker" — so the age branch could fire against a demonstrably live, still-working owner. Reproduced empirically: a forked process held the lock, stayed alive and provably still running, and a second process stole it once the age threshold passed.

## Root Cause

"Add an age fallback for robustness" sounds like pure defense-in-depth, so it read as safe at review time. It wasn't: an OR of two conditions, each individually sufficient to grant recovery, means the *weaker* condition (age) can override the correctness of the *stronger* one (liveness) at any time. The flaw is invisible until you ask "can this branch fire when the other one says 'alive'?" — which nothing in the original design prompted anyone to ask.

## Prevention

**When a recovery/preemption decision combines multiple signals**, write out each signal's individual truth table entry and ask explicitly: "does any single signal alone grant the unsafe outcome, regardless of what the other signals say?" If yes, that signal must gate (AND), never fall back (OR), unless the unsafe outcome is actually acceptable.

**Signal to watch for:** a reviewer or implementer proposes an age/timeout/count-based fallback "just in case" alongside a correctness-bearing check (liveness, ownership, version). That phrasing is the tell — a fallback for a check that is supposed to be authoritative is usually a correctness bug waiting to be found under the right timing.

## Criteria check

- Recurs in other stories: yes — any future lease/lock/ownership mechanism (session locks, cache invalidation, job claiming) can reintroduce exactly this shape of bug
- Non-obvious cause: yes — the bug is only visible once you enumerate "can the weak signal fire while the strong signal says no," which the original design never did
- Concrete prevention: yes — a specific question to ask of any multi-signal recovery decision before shipping it
