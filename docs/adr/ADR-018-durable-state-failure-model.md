## Context

Design A (`DURABLE-PRUNE-PROTOCOL-DESIGN-004.md`) заменяет откатываемый tombstone на регистр решения на попытку
(`prepare.n` / `decision.n`, create-only, необратимый `commit`). Аудит 004C не нашёл safety-нарушений в заявленной
модели (Mode A, процессные сбои), но выявил три вопроса, которые не решаются текстом дизайна и требуют
решения владельца:

1. **Модель отказов не зафиксирована в ADR.** Формулировки §21 («каталог не удаляется, чтобы исключить ABA») и
   §20.5 («восстановить `tasks/P/` из резервной копии») противоречат друг другу и допускают прочтение «протокол
   защищает от внешнего удаления» (C-3).
2. **Семантика `MISSING`.** Design A делает `MISSING` существующей задачи fail-closed (без карантина), что
   несовместимо с ADR-017 §2.4b/§2.4c, где «GONE» включает «задачи не было» и ведёт к необратимому карантину
   детей (C-9).
3. **Совместимость и миграция.** Все задачи, обрезанные старым runtime, становятся `LEGACY_TOMBSTONE`;
   инструмента миграции нет; смешанные версии небезопасны (C-11, раздел I.2 отчёта).

Принцип: *Correctness before complexity. Evidence before confidence.*

## Decision

### D1. Модель отказов Mode A

Mode A гарантирует безопасность (safety) и восстановимость (recovery) при **всех** перечисленных условиях:

* конкурентное исполнение нескольких процессов на одной машине;
* атомарная публикация файла (`createFile`: tmp → `link()`, A1) в пределах заявленных предпосылок A1–A8;
* process crash, SIGKILL, SIGSTOP/SIGCONT, повторный запуск процессов;
* recovery после частично завершённых операций;
* конкурентные `append`, `compact`, `pin`, `claim`, `prune`.

Из гарантий Mode A **исключены**:

| Исключённый режим | Последствие |
|---|---|
| произвольное внешнее удаление внутренних файлов и каталогов `tasks/` | воскрешение/ABA возможно и необнаружимо (D2, D4) |
| внешнее изменение содержимого файлов | может быть обнаружено как `CORRUPT` (самопроверка `check`), но не предотвращается и не восстанавливается |
| восстановление отдельных файлов или каталогов из старых копий | откат части состояния (дети и решения «из будущего»); допустим только **полный** откат всего хранилища. **Восстановление старой копии может привести к повторному выполнению внешних эффектов** (журнал «забывает» уже совершённые эффекты и подтверждённые решения); защита от этого сценария **не заявляется** |
| rollback состояния файловой системы | как выше (включая повторное выполнение внешних эффектов); произвольный storage rollback не защищён |
| OS crash / power loss durability (Mode B) | `OS_CRASH_DURABILITY_NOT_GUARANTEED`; возможны потеря `commit` и ложный карантин — `NOT CLAIMED` |
| неатомарные операции там, где протокол требует атомарности (`link`, поиск по имени) | вне модели; сетевые ФС — out of scope |
| файловая среда, не обеспечивающая **A2-R** (real-time межкаталожная видимость на одном ядре; свойства FS-1…FS-6, Design A §43): NFS/SMB/FUSE с кэшированием, 9p/virtiofs с кэш-режимами, облачные синхронизируемые каталоги, не проверенные union/overlay-ФС и любая ФС, не прошедшая пробу соответствия | возможны ложное подтверждение (`'appended'` для неканонического события) и пропуск проверки входа `compact` (CC-1) — **не «внешнее вмешательство», а свойство среды**; CEI-1…CEI-5 и CC-1/CC-5 заявлены только при A2-R. ext4/tmpfs пробой Security 004E не опровергнуты (один хост, одно ядро), но **формально не доказаны** |
| злонамеренный участник с доступом к хранилищу | `check` — защита от случайной порчи, не от подмены (граница — ADR-012/013) |

**Исключение OS crash не отменяет обработку ошибок ввода-вывода.** В пределах контракта: ошибка чтения регистра или
каталога ⇒ `UNREADABLE` (повторяемо, без необратимых действий); неподтверждённое (нестабильное) наблюдение и `IOERR` ⇒ `UNREADABLE`, а не
`CORRUPT` (Design A §32.3, §37); ошибка публикации ⇒ `StoreIoError`/`AppendOutcomeUnknownError` без молчаливого подтверждения;
ошибка `fsync` каталога в Mode A — предупреждение `DIR_FSYNC_FAILED`, которое не объявляет долговечность и не
скрывается. Никакая ошибка ввода-вывода не трактуется как `GONE`, `COMMITTED`, разрешение на карантин, на
создание fence или на удаление.

### D2. Семантика `MISSING`: fail-closed

Принято владельцем (D-OWN-3). Состояния `MISSING`, `UNREADABLE`, `CORRUPT`, `LIVE`, `PREPARING`, `COMMITTED` **различаются** и не сводятся друг к другу; `MISSING` не является ни `GONE`, ни `COMMITTED`, ни `CORRUPT`.

`MISSING` (нет `tasks/P/`) **не** интерпретируется как `GONE`, `COMMITTED`, разрешение на карантин детей, на
создание нового fence, на `prepare`/`commit` или на prune. Случаи разделены:

| # | Случай | Поведение |
|---|---|---|
| 1 | **Создание действительно новой задачи** (`append` с `seq = 1`; `createTask` для самого создаваемого ребёнка — если же `MISSING` его *требование* `P`, действует п. 2) | разрешено: каталог создаётся публикацией события. Задача без событий **и без сегментов** считается новой. |
| 2 | **Существующая задача, каталога нет** (`claim`, `findResumable`, `pruneTask`, `append` с `seq > 1`, `compact`, `pinReference`, `createTask` с требованием `P`, G2, `assess`, `resumePacket`) | **Политика:** fail-closed — ничего не создаётся; нет карантина, fence, `task.cancelled`, `prepare`/`commit`; решение — оператору. **Класс результата по операции определяет исполнимый контракт Design A (§20.3, §24.2, §31, §38.1), а не этот ADR:** отказ `PRUNE_DECISION_CORRUPT(task-dir-missing)` — для `claim`, `findResumable`, `append (seq>1)` (независимо от G1, Design A §31) и `compact`; отказ `pruneTask`; `parent-missing` — для `pinReference`/`createTask`; для G2 (публикация уже выполнена) — исход неизвестен (`AppendOutcomeUnknownError` / retryable `StoreIoError`), файл не удаляется; `assess`/`resumePacket` — диагностика без записей. При расхождении по политике побеждает этот ADR, по классу ошибки — Design A. |
| 3 | **Повреждённое или неполное состояние** (`CORRUPT`, `UNREADABLE`, нестабильное наблюдение) | fail-closed: отказ, без необратимых действий; `CORRUPT` — оператор, `UNREADABLE` — повтор. `CORRUPT` не сохраняется и вычисляется заново; неподтверждённое наблюдение (класс «по отсутствию») `CORRUPT` не даёт (Design A §32); **транзитный `IOERR` на файле, от значения которого зависит вердикт (в том числе `decision.k`), даёт `UNREADABLE`, а не `CORRUPT`** (Design A §37, §41.1 — после Amendment-004F алгоритм соответствует этому пункту, ранее — нет). |
| 4 | **Legacy task** (`tombstone.json` v1 без регистра) | `LEGACY_TOMBSTONE`: все операции — отказ; ни удалений, ни отмен; автоматической миграции нет (D3). Состояние «регистра нет» **устанавливается поиском по имени `prepare.1`**, а не листингом `tasks/P/` (Design A §41.2): листинг без `prune-*` не отличает legacy от здорового регистра, созданного во время листинга. |
| 5 | **COMMITTED task** | терминально; `claim` ⇒ `TaskOrphanedError`; карантин детей допустим (Mode A — сразу); записи ⇒ `TaskPrunedError`; остатки убирает sweeper; `P` не возобновляется. |

**Дети несуществующего требования (C-9).** Ребёнок, чьё требование `MISSING`, остаётся `active` в журнале и
получает не-retryable отказ `claim`. Автоматического `task.cancelled` нет (прежнее поведение ADR-017 §2.4b для
«отсутствует» **заменяется**). Выход — оператор: восстановить хранилище целиком либо явно отменить ребёнка
существующей операцией `cancel`. Это сознательное смещение от «автоматическая необратимая очистка» к
«сохранить данные и потребовать решения».

### D3. Совместимость

* **Legacy tombstone.** Старый `tombstone.json` без `prune-*` — `LEGACY_TOMBSTONE`. Консервативно: `createTask`,
  `claim`, `append`, `compact`, `pinReference` — отказ; удаление данных и `task.cancelled` запрещены.
* **Запрет автоматического превращения legacy в v2.** Ни runtime, ни `verify`/CLI/sweeper не публикуют `commit`
  по legacy tombstone и не создают регистр. Неполнота данных может быть порчей (J-4), а legacy-tombstone означал
  «намерение, возможно отзываемое».
* **Условия операторской миграции** (Design A §13.1; инструмент вне scope этого ADR): (1) все процессы runtime —
  старые и новые — остановлены, подтверждает оператор; (2) `derivePruneState(P) = LEGACY_TOMBSTONE`, файл валиден;
  (3) снята копия `tasks/P/`; (4) явное подтверждение намерения; результат — `COMMITTED(1)` с `migrated: true`
  либо архивирование tombstone вне `tasks/P/` ⇒ `LIVE`.
* **Компакторы `≤ 3f49f5b`.** `FsEventStore.compact` на `3f49f5b` не проверяет вход (Design A §40.6); сегмент, опубликованный им, может нарушить `Canon`. Смешанные версии поэтому небезопасны и для компакции, не только для prune.
* **Остановка несовместимых runtime.** Перед миграцией и перед включением нового runtime над существующим
  хранилищем все runtime версий `≤ 3f49f5b` останавливаются. SIGSTOP-нутый старый pruner, возобновившись после
  запуска нового runtime, может удалить данные без регистра — окно закрывается только остановкой.
* **Mixed-version execution не считается безопасным по умолчанию.** Старый runtime не знает о `prune-*`: во время
  `PREPARING` он видит «tombstone нет» и допускает `claim`. Запрет — операционный (условие релиза).
* **Version marker.** `<root>/durable-protocol.json` (`{v:2}`, create-only, неизменяем) создаётся **только явным
  действием оператора**, а не как побочный эффект открытия хранилища: создание при открытии не доказывает
  отсутствия работающего старого runtime. Хранилище с задачами и без маркера новый runtime открывает только для
  диагностики. **Bootstrap нового пустого хранилища** (нет задач, нет маркера) — Design A §46.5: обычное открытие маркер не создаёт и хранилище не мутирует; инициализация (create-only `durable-protocol.json` в *пустом* хранилище) — явное действие оператора; для непустого хранилища bootstrap не применяется. Неявной миграции legacy при открытии нет. Наличие маркера не делает смешанные версии безопасными.
* **Ограничение защиты от старых runtime.** Старый runtime маркер игнорирует и не может проверить; защиты от него
  нет, есть только запрет на уровне процесса развёртывания.
* Формат событий v1, журнал, существующие fence и pins не меняются.

### D4. Воскрешение при внешнем удалении — не исправлено

Если `tasks/P/` удалён внешним процессом, система не может отличить ранее существовавшую задачу от новой.
`append(seq = 1)` создаёт «новую» `P`; дети, не получившие карантин, проходят `claim` и получают fence.
Это **не исправлено технически** в текущем Design A, и ADR **не заявляет** защиты от воскрешения при внешнем
удалении. Допущение A6 (записи регистра не удаляются и не изменяются никем, включая оператора) — предпосылка, а не
механизм. Отличать от D4 нарушение **A2-R** (D1, последняя строка исключённых режимов): оно возникает без
внешнего вмешательства, на неподдерживаемой файловой среде, и даёт ложное подтверждение, а не воскрешение.

### D5. Область ADR

ADR-018 фиксирует модель отказов, семантику `MISSING` и правила совместимости. Persisted-протокол (регистр
`prepare/decision`, G2, sweeper, `derivePruneState`, claim/fence) оформлен **отдельным ADR-019** (D-OWN-1, принято):
ADR-018 не принимает и не переопределяет Design A, а ADR-019 не пересматривает модель отказов и политику `MISSING`.
При расхождении по политике (`MISSING`, граница гарантий) побеждает ADR-018; по алгоритму и классу ошибки — Design A (§46 > …).

## Rationale

* **Fail-closed вместо `GONE` для `MISSING`.** В Design A `tasks/P/` не удаляется ни одним шагом протокола ⇒
  `MISSING` — всегда внешнее вмешательство, а не результат prune. Необратимое действие (карантин) по признаку
  «порча/вмешательство» нарушает принцип INV-012 (карантин только при подтверждённом исходе). Fail-closed сохраняет
  данные и перекладывает решение на оператора ценой живости.
* **Явное исключение вместо иллюзии защиты.** FS-only архитектура с необратимостью, записанной в файлах `tasks/P/`,
  неустойчива к удалению этих файлов; аудит это подтвердил моделью. Честная граница лучше формулировки,
  подразумевающей защиту.
* **Разделение «новая задача» и «чтение существующей».** Единственная неоднозначность — `seq = 1` при `MISSING`;
  она принимается явно (D2.1, D4), остальные чтения fail-closed.
* **Marker явным действием.** Автосоздание при открытии создало бы ложное ощущение, что старые runtime исключены.

## Alternatives considered

| Альтернатива | Отвергнута, потому что |
|---|---|
| **A1. `MISSING` ⇒ `GONE` ⇒ карантин (ADR-017 §2.4c as-is)** | любое внешнее удаление/порча приводит к необратимой отмене детей; нарушает INV-012; в Design A `MISSING` не вытекает из prune |
| **A2. `MISSING` ⇒ fail-closed (выбрано)** | безопасна; цена — дети внешне удалённого родителя остаются `active` до оператора |
| **A3. Глобальный creation registry** (create-only корневой `tasks-index`, никогда не удаляется протоколом; `MISSING` + запись в реестре ⇒ `PRUNE_DECISION_CORRUPT(task-dir-missing)` даже для `seq = 1`) | вне scope: (а) защищает только от удаления `tasks/P/` по ошибке, но не от удаления корня и не от восстановления из копии — то есть не закрывает исключённые режимы D1; (б) вводит новый persisted-артефакт и протокол упорядочивания «запись в реестре ↔ первое событие» с собственным окном краха (запись без события, событие без записи) и общей точкой конкуренции для всех задач; (в) Mode A исключает внешнее удаление, поэтому требования к такой защите нет. Остаётся кандидатом на отдельное усиление, если владелец расширит модель отказов; аудит 004C пометил его как опциональный hardening |
| **A4. Операторский / политиковый карантин детей при `MISSING`** | требует новой политики и решения «кто и когда»; оператор уже имеет `cancel`; отложено |
| **A5. Включить Mode B (OS-crash durability)** | недоказуем существующими примитивами (семантика ошибки `fsync`); не заявлен |
| **A6. Автомиграция legacy при открытии** | превращает возможно-отзываемое намерение в необратимый `commit` без подтверждения; отвергнута |

## Consequences

* (+) Safety в заявленной модели не зависит от интерпретации отсутствия файлов.
* (+) Граница гарантий явная; исчезает двусмысленность §21/§20.5.
* (−) Живость: дети внешне удалённого/повреждённого родителя не очищаются автоматически; `LEGACY_TOMBSTONE`-задачи
  блокируют операции до ручной миграции; `CORRUPT` и `UNREADABLE(unstable)` требуют оператора/повтора.
* (−) Воскрешение при внешнем удалении возможно и необнаружимо (D4).
* (−) Идентификаторы выведенных задач «сгорают» навсегда; регистр растёт без автоматической очистки (Design A §19).
* Поведение, меняющееся относительно ADR-017 (после принятия): карантин по `MISSING` исчезает.

## Compatibility

Сводка — D3. Дополнительно: аддитивные ошибки `PRUNE_DECISION_CORRUPT` (причины включают `task-dir-missing`,
`legacy-tombstone-unmigrated`), `PRUNE_ATTEMPT_LIMIT`; `EventStore` — три опциональных метода; новые исходы G2.
Публичные сигнатуры не меняются; принятие новых экспортов — решение ревью.

### Соотношение с ADR-017 (supersession — только после принятия)

ADR-017 имеет статус `proposed`; поэтому до принятия обоих документов формального «замещения» нет. Ниже —
предложение, как оформить его при принятии ADR-018.

| Положение ADR-017 | Что меняется | Почему | Остаётся действительным |
|---|---|---|---|
| §2.4c, «Логическая модель ссылки»: `GONE` — «задачи не было, либо удаление данных начато или завершено» | `GONE` = согласованный `COMMITTED`; «задачи не было» ⇒ `MISSING` (fail-closed, D2) | `MISSING` — не результат prune; порча не даёт права на необратимое действие | различение `LIVE`/pending/`COMMITTED`; таблица реакций `claim`/`findResumable`/`assess` для `LIVE` и `COMMITTED` |
| §2.4b: `claim` при «GONE (отсутствует или удаление началось)» ⇒ `TaskOrphanedError`; карантин при «обнаружении сироты (только GONE)» | для «отсутствует» — отказ без карантина; карантин — только при `COMMITTED` | см. выше | идемпотентность и терминальный резерв карантина; N-8 (транзитивные зависимости не отслеживаются) |
| §2.4a/§2.4c: откат prune через `withdrawTombstone` (`unlink tombstone.json`) | заменяется `decide(n, abort)` в регистре Design A | откат — check-then-act (J-2); остановленный pruner пересоздаёт tombstone (J-1) | схема «маркер ссылающегося — pin/`task.created` — виден pruner'у» как идея; живость pin (`referenceGrace`) |
| §2.4c «Честные границы» (1) | заменяется доказательством P-3 и RS-1…RS-4 Design A | J-1 | остальные пункты |
| §2.6, §9 (границы: одна машина, локальная POSIX ФС) | не меняются; уточняются D1 | — | полностью |

Оформление после принятия: в ADR-017 добавляется заголовок «Частично замещён ADR-018 (§2.4a–§2.4c)» и ссылки; текст
ADR-017 **не** правится молча, а изменяется отдельным коммитом в рамках FIX-004D по решению владельца. Если
ADR-017 будет принят вместе с ADR-018, правка вносится до принятия, supersession-метка не нужна.

## Security assumptions

A1 `link()` атомарен, `EEXIST`; A2 видимость после возврата — в сильном прочтении **A2-R** («real-time межкаталожная видимость на одном ядре»: FS-1…FS-6, Design A §43; **не доказано**, эксперименты ext4/tmpfs — наблюдения); A3 `unlink` атомарен; A5 порядок записей одного
процесса виден другим в том же порядке (**не доказан**); A6 записи регистра не удаляются и не изменяются никем
(предпосылка, не механизм); A7 листинг возвращает имена, существовавшие на протяжении всего листинга, и **не**
является атомарным снимком; A8 поиск по имени линеаризуем относительно `link`. A5, A7, A8 — свойства реальной ФС,
не model-checked. Модель отказов — D1. Угроз со стороны злонамеренного участника нет (ADR-012/013).

## Known limitations

* Воскрешение при внешнем удалении `tasks/P/` (D4).
* Внешние эффекты: протокол не гарантирует exactly-once; восстановление старой копии хранилища может повторить уже выполненные эффекты (D1); эффект, начатый до терминала ребёнка, не останавливается при удалении родителя (R-6, Design A §42.2). Idempotency, reconciliation и бизнес-авторизация остаются на стороне прикладного кода.
* Внешнее удаление/изменение файлов и произвольный storage rollback исключены из Mode A (D-OWN-2) и не защищены.
* Суффиксное усечение регистра (удаление последнего `decision` без `tombstone.json`) неотличимо от `PREPARING` (O-4, принято).
* Вывод `CORRUPT` из отсутствия имён опирается на A5/A6/A8 (Design A §32), не на атомарность листинга.
* Живость: LV-1 (полнота физической очистки) требует внешнего триггера; `MAX_PRUNE_ATTEMPTS` без сброса;
  ребёнок с нечитаемым журналом без terminal evidence блокирует prune любого родителя.
* Не покрыты моделями: корректность реализации, транзитивные зависимости в скане (N-8), A5/A7/A8 на реальных ФС и сильное (real-time) прочтение A2 (A2-R) для различных каталогов (Design A §35.5, §43). Несколько детей в скане (до двух) покрыты bounded-моделью Security 004D (`model_terminal_evidence.py`) для предыдущей редакции RS-4. Security 004E (`DURABLE-SECURITY-DELTA-004E`) прогнал модели на тексте 004E; Security 004F (`DURABLE-SECURITY-FINAL-DELTA-004F`, `APPROVED_FOR_ADR_DECISION`) прогнал **ограниченные** модели на тексте Amendment-004F (CC-1…CC-6, IO-G, правило T при `m = 0`, ветвь «пустой журнал» claim/fence): 0 нарушений **в границах обхода** (≥3 компакторов, >1 SIGKILL, `BAD` в нескольких файлах, несколько детей не охвачены). Это не формальное доказательство и не проверка реализации; A2-R остаётся `ARGUED[Mode A]`.
* Исход `compact` (CC-1) на `3f49f5b` **не реализован**: проверка входа — требование FIX-004A; до реализации CEI-1 условно.
* Живость: пустой журнал ребёнка при `CORRUPT`/`UNREADABLE`/`LEGACY`/`PREPARING` блокирует prune родителей до разрешения состояния ребёнка (Design A §42.1); уже начатый внешний эффект ребёнка не охватывается (R-6, §42.2).

## Migration requirements

1. Инструмент операторской миграции `LEGACY_TOMBSTONE` — **отдельная задача**; создаётся до любого релиза,
   затрагивающего хранилища с задачами, обрезанными старым runtime (C-11). Для текущего `0.1.0-alpha.0`
   (релизов с этим форматом нет) допустим документированный ручной порядок Design A §13.1.
2. Явное действие оператора по созданию `durable-protocol.json` (в том числе для нового пустого хранилища: обычное открытие маркер не создаёт и хранилище не мутирует, Design A §46.5; подтверждено владельцем).
3. Остановка всех runtime `≤ 3f49f5b` до включения нового; запрет смешанных версий — условие релиза.
4. Миграция не запускается автоматически и не вызывается из `open`, `verify`, CLI-диагностики, sweeper.
5. Формат на диске этим ADR не изменяется; изменение формата — FIX-004 после принятия.

| Код | Решение | Статус | Где отражено |
|---|---|---|---|

| D-OWN-2 | Из Mode A исключены внешнее удаление, внешнее изменение файлов, восстановление старых копий, произвольный storage rollback; восстановление старой копии может повторно выполнить внешние эффекты; защита не заявляется | `ACCEPTED` | D1, D4, «Known limitations» |
