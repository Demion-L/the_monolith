## Context

MONOLITH хранит состояние проекта в файлах (`.monolith/state.json`,
markdown-память, ADR). Нужен способ понять «где мы находимся» (миссия,
чекпоинты, roadmap, доступность данных) без чтения многих файлов.

Ограничения: UI не должен стать вторым источником истины; Core (State Keeper,
Scriptorium, ERG) не дублируется; UI не расширяет возможности Core.

## Approved by project owner

Эти пункты — решения владельца, зафиксированные здесь для трассируемости; сам
ADR всё ещё `proposed`.

- **Frontend:** Vue 3, TypeScript, Vite, Composition API. Без библиотеки
  управления состоянием и без библиотеки роутинга в MVP, пока нет реальной
  потребности.
- **Backend:** существующий Node.js runtime; локальный HTTP API; JSON; только
  чтение; bind `127.0.0.1`; один сервер = один проект; foreground.
- **Источники данных:** `state.json`, markdown-документы и существующие
  интерфейсы Core остаются авторитетными. Без миграции в XML или иной формат;
  без новых обязательных персистентных схем в MVP. Frontend не зависит от
  формата хранения благодаря application-level read model.
- **CLI (целевой UX):** `monolith ui` запускает локальный HTTP-сервер,
  отдающий скомпилированное Vue-приложение и read-only API. Vite — инструмент
  разработки и сборки, не production-сервер.
- **Q10 — фикстуры:** разрешена разработка Vue Dashboard на синтетических
  JSON-фикстурах до закрытия SEC-001. Ограничения: никакого доступа к реальным
  проектным файлам через HTTP; никаких вызовов небезопасной валидации; никаких
  write operations; никаких изменений Core ради mock-режима.
- **Q14 — Roadmap:** в MVP строки `roadmap-index.md` отображаются как текст. UI
  не выводит статусы задач из произвольной Markdown-прозы; отдельный
  Markdown-парсер для Roadmap не создаётся.

## Proposed (требует ревью)

1. Слои: Browser UI → Local HTTP API (только `GET`) → Application Layer (read
   model с provenance и диагностиками) → Core → файлы проекта.
2. Каждый показанный факт несёт provenance (относительный путь источника);
   отсутствие данных — `UNKNOWN` + диагностика, не домысел.
3. Эпистемические статусы PROPOSED / DECIDED / IMPLEMENTED / VERIFIED не
   смешиваются и не выводятся друг из друга.
4. Детали контракта API (эндпоинты, оболочка ответа) и размещение собранных
   ассетов — см. план, §4 и §9. Токен запуска не вводится (F-8, см. Security).

## MVP scope (UI-001)

Показываются только данные, подтверждённые авторитетными источниками;
иначе `UNKNOWN`.

1. Project Overview.
2. Current Mission.
3. Checkpoints.
4. Roadmap (строки `roadmap-index.md` как текст, без вывода статусов; Q14).
   Поле `Checkpoint.remainingSteps` отражает состояние на момент конкретного
   чекпоинта и не представляется как актуальный план проекта (F-6).
5. Базовая диагностика доступности данных и ошибок.

**Исключено из MVP:** управление агентами; Hypothesis Explorer; Knowledge
Explorer; ERG Graph View; интеграция с Reasoning Projector; Governance
Workbench; любые операции записи; продвинутая аналитика; фоновые сервисы;
новые персистентные модели данных. UI-002…UI-005 — неплановый backlog без
расширения объёма.

Не выдумываются статусы, блокеры, результаты верификации и evidence. Не
вводятся новые governance-требования. Состояние проекта не изменяется.

## Security

**Инвариант:** MONOLITH UI не должен расширять возможности MONOLITH Core по
доступу к файловой системе, исполнению кода или изменению состояния.

### Статус зависимостей (проверено по `main`, `fcd6481`)

| Элемент | Статус | Влияние на UI |
|---|---|---|
| **SEC-001A** — containment `monolithRoot` ([ADR-009](ADR-009-monolith-root-containment.md), `accepted`) | **MERGED + PUSHED в `main`** (подтверждено владельцем): 459/459 тестов, typecheck, build, security smoke PASS, независимый review завершён | Core-гарантии доступны (G1). Их использование в UI ещё не реализовано и не протестировано |
| **SEC-001B** — TOCTOU, дополнительная защита файловых операций | **OPEN** | Блокер для **write-enabled** UI. Для read-only UI остаточный риск оценивается отдельно (см. ниже); **не** блокирует разработку dashboard на фикстурах |
| **SEC-002** — `monolith validate` выполняет недоверенный JavaScript через динамический `import()` `project.definition.mjs` | **IMPLEMENTATION IN PROGRESS** (отдельный worktree; здесь не изменялся) | До завершения: UI не вызывает `monolith validate`, не импортирует `project.definition.mjs`, не запускает пользовательский JavaScript |

Фактический контракт Core (`src/root/index.ts`, `main`):
`resolveMonolithRoot(targetDir, config?) → ResolvedMonolithRoot { projectRoot,
projectRootReal, monolithRoot, rootAbs, source }`; при нарушении или битом
`monolith.config.json` бросает `RootContainmentError` (fail closed).
`assertContainedFile(root, relFromRoot)` / `checkContainedFile(root, relFromRoot)`
проверяют фиксированный файл **внутри `monolithRoot`** через realpath всех
компонентов. Check-then-use гонки (TOCTOU) Core не закрывает — это SEC-001B.

**Остаточный риск SEC-001B для read-only UI** (оценивается при реализации G2, а
не принимается заранее): между проверкой и чтением файл может быть подменён
symlink-ом локальным процессом с правами владельца проекта. Для read-only
сервера на `127.0.0.1` это не даёт нового класса доступа сверх прав самого
пользователя, но может привести к чтению файла вне проекта. Решение о
приемлемости фиксируется в UI-001 до подключения реальных данных.

### Security gate: G1 и G2

**G1 — Core Root Containment.** Корректное определение корня проекта и
ограничение файловых операций разрешённой областью. Основа — SEC-001A.
- Использовать `resolveMonolithRoot`; не создавать собственный резолвер и не
  дублировать логику containment Core.
- Корень проекта фиксируется при запуске сервера и далее не меняется.
- Произвольный project root через HTTP не принимается.
- Наличие резолвера **не** означает, что чтение любого файла безопасно (F-4,
  ниже).
- *Статус:* SEC-001A интегрирован и проверен на уровне Core. Использование этих
  гарантий UI ещё должно быть реализовано и протестировано.

**G2 — UI HTTP Security.** Защита локального HTTP API и доступа к данным
проекта. Обязательные требования:
1. HTTP-сервер слушает только `127.0.0.1`.
2. Проверка `Host` по allowlist.
3. Проверка `Origin` для API-запросов, когда заголовок присутствует.
4. Отсутствие permissive CORS.
5. Только read-only API.
6. Никаких произвольных filesystem paths из запросов.
7. Фиксированный список источников данных MVP.
8. Проверка containment каждого читаемого файла.
9. Безопасная обработка symlink.
10. Markdown отображается как экранированный текст.
11. CSP для статического frontend.
12. Ошибки API не раскрывают абсолютные пути и содержимое файлов.
13. Никакого исполнения проектного JavaScript.
14. Никаких write operations.

G2 реализуется и проверяется в рамках UI-001. **До успешной проверки G2
подключение реальных проектных данных через HTTP запрещено.** Разработка и
тесты на синтетических фикстурах gate не нарушают (Q10, утверждено).

### Containment каждого читаемого файла (F-4)

`readState()` (`src/coordinatorium/state-keeper.ts`) принимает каталог и сам
containment не проверяет; его проверяют вызывающие (`coordinatorium/cli.ts`,
`brief/collect.ts`). Новый UI-адаптер, вызывающий низкоуровневое чтение
напрямую, обошёл бы защиту Core.

> Каждый файл, читаемый UI, должен проходить проверку containment относительно
> корня проекта, зафиксированного при запуске сервера. Наличие
> `resolveMonolithRoot` само по себе не освобождает новые read-only адаптеры от
> этой проверки.

Для MVP:
- используется только **фиксированный набор** необходимых источников; не
  создаётся универсальный файловый браузер и индекс всех документов; API не
  принимает пути (F-5);
- `assertContainedFile`/`checkContainedFile` покрывают файлы внутри
  `monolithRoot`. Источники вне `monolithRoot` (если появятся в наборе) требуют
  проверки относительно `projectRootReal` — это уточняется в UI-001 без
  введения нового резолвера в рамках UI-000D.

**Требования к security regression tests (UI-001; в UI-000D не реализуются):**
- нормальный файл внутри проекта читается;
- symlink, ведущий за пределы проекта, отклоняется с диагностикой, без
  раскрытия абсолютного пути и содержимого;
- отсутствующий файл → диагностика, не падение;
- повреждённый или недоступный источник → диагностика, не падение;
- попытка обратиться к неразрешённому пути через API отклоняется.

### Токен запуска (F-8)

Предварительное решение владельца: для read-only MVP отдельный токен запуска
не вводится. Обязательные условия: `127.0.0.1`; allowlist `Host`; ограничения
`Origin`; отсутствие CORS; отсутствие cookie-аутентификации; отсутствие write
operations. Решение не отменяет security review HTTP API (Q6 — закрыт
предварительным решением, подтверждается ревью G2).

### SEC-002

`monolith validate` динамически импортирует `project.definition.mjs`
(проверено чтением кода). UI не исполняет JavaScript проекта неявно, не
вызывает небезопасную валидацию; индикаторы состояния строятся на безопасных
read-only проверках (диагностики чтения Core). SEC-002 не реализуется и не
верифицируется в этом ADR.

## Dependencies on other work

- **CONTEXT-001A:** COMPLETED и в `main`. `collect()`/`BriefModel` покрывают
  большую часть MVP (миссии, последний чекпоинт, Current Story, диагностики), но
  не Roadmap; на них же распространяется SEC-001; не публичный API (TD-009:
  `src/brief/index.ts` экспортирует `collect` и `BriefModel`, но `src/index.ts`
  `brief` не реэкспортирует). Зависимость полезная, не обязательная. Новый
  публичный API в рамках UI-000B не вводится; способ внутреннего
  использования `BriefModel` определяется при реализации UI-001 (Q11); новый публичный API
  в UI-000D не вводится.
- **CONTEXT-001B:** `monolith context <topic>`, не начат; от него UI-001 не зависит.
- **SPHINX:** независимый продукт, потребляющий возможности MONOLITH (со слов
  владельца). UI от него не зависит; SPHINX-специфики в MVP нет.

## Rationale

- Read-only + проекции Core сохраняют «один источник истины» и детерминизм
  (прецедент: `monolith validate`, `monolith brief`).
- Локальный bind, отсутствие CORS и демона минимизируют поверхность; содержимое
  документов — недоверенный ввод.
- Запрет вывода связей согласуется с ADR-007 (explicit-only).

## Alternatives Considered

Ранее (исходная редакция, `b03723a` до rebase, `4cd2613` после) рассматривались: stdlib-клиент без сборки; клиентский
фреймворк с бандлингом; полный фреймворк с dev-сервером; статический экспорт.
Выбор стека сделан владельцем (Vue 3 + TS + Vite с компилированной раздачей);
сравнение сохранено в истории git. Статический экспорт остаётся возможным
дополнением вне MVP.

## Consequences

Если будет принят:
- появятся Application Layer, HTTP-слой и build-цепочка Vue/Vite (devDependencies;
  изменение `package.json` и CLI — только в UI-001 после явного одобрения);
- UI-001 не подключает реальные данные по HTTP до успешной проверки G2; G1 (SEC-001A) уже в `main`;
- Blockers, IMPLEMENTED и VERIFIED не имеют источника данных — в MVP не
  показываются;
- вопросы размещения собранных ассетов (`dist/ui/` коммитится в Git — предварительное решение владельца; `build`/`prepare` не меняются без отдельного решения; TD-003) и импорта
  `src/brief/` (TD-009) требуют решения.

Если не будет принят: ничего не меняется; план остаётся справочным.
